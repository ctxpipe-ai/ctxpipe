# T05 Skill bundle packaging

## What

- `apps/backend/ingest-skills/`: one folder per skill (`SKILL.md`, `scripts/`, `schema.json`) and `bin/` with the stage helpers. The first skill is a placeholder `discover-roots`. T10 and later tickets give the real skills. A folder name must be the same as its `SKILL.md` `name`.
- `bin/ctxpipe-stage`, `bin/ctxpipe-delete`, `bin/ctxpipe-finish` (Node ESM, shared code in `bin/stage-lib.mjs`; `--root <dir>` for tests). They read the root-owned `/ctxpipe/step.json` (`workspaceId`, `baseCommit`) and write to `/ctxpipe/out`. `ctxpipe-stage` records the blob at the base commit. `ctxpipe-finish` writes `patch.json` in the T06 format: `create` with no `baseBlob`, `update` and `delete` with the recorded blob (else the blob at `baseCommit`), and the delete `reason`.
- `skill-bundle.ts`: the `/ctxpipe` paths and `readIngestSkillBundle` (name `ingest-<16 hex>`).
- `ingest-prepare.ts`:
  - `prepareIngestSandbox` (once per sandbox): makes the Vercel agent user, the layout, the bundle (always copied again), and the root-owned OpenCode config.
  - `sealIngestCheckout`: root clones a user copy to `/ctxpipe/context/<workspaceId>` or `/ctxpipe/source/<handle>`.
  - `startIngestStep` (before each step, as root): fetches the shard ref, checks out the base commit detached, places `<workspaceId>.index.json`, empties `/ctxpipe/out` and `/ctxpipe/home`, and writes `step.json`.
  - `ingestAgentUser`: refuses unsandboxed mode.
- `ingest-root.ts`: `dockerRunAsRoot` (Docker exec as uid 0) and `vercelRunAsRoot` (Vercel SDK `sudo`). Both run the same scripts.
- `ingest-opencode.ts`: the config is the shared chat provider block (`workspaceChatOpenCodeProvider`) plus `instructions: []`, `skills.paths`, no plugins or MCP, and `skill: {"*": "deny", <bundle>: "allow"}`. The env has the three isolation flags, `HOME=/ctxpipe/home`, and `OPENCODE_CONFIG=/ctxpipe/opencode/opencode.json`. `ingestAgentCommand` runs a command as the agent with only that env (`sudo -n -u ctxpipe-agent` on Vercel). `assertIngestOpenCodeVersion` stops on any version but 1.18.34.
- Backend and worker Dockerfiles copy `apps/backend/ingest-skills`.

## Why

Concept sections 3, 6, and 8; ADR-052. OpenCode 1.18.34 reads `AGENTS.md`, `opencode.json`, `.opencode/`, `.claude/skills/`, and `.agents/skills/` from the cwd up to the git root, and global config from `HOME`. The default Vercel user has passwordless sudo, so root ownership alone does not protect anything there; the agent runs as a user with no sudo.

## Tests

- `skill-bundle.test.ts` (7): the hash, and a folder name that differs from its `SKILL.md` name.
- `stage-helpers.test.ts` (11): real git and the T06 validator; create, update, delete; blobs at the base commit after the checkout moved on; refusal paths.
- `ingest-root.test.ts` (5): the Vercel `sudo` call, the agent user per provider, the unsandboxed refusal, and the `sudo -u` agent command.
- `ingest-sandbox-skills.contract.test.ts` (7, Docker; each test makes its own sandbox):
  - Docker and a Vercel-like image (default user with passwordless sudo): the agent cannot `sudo -n true`, cannot change the skills, the config, the checkouts, or `step.json`, and can write `/ctxpipe/out` and `/ctxpipe/home`.
  - Sealing a checkout with symlinks to `/etc/shadow` and `/etc` does not change them.
  - The version check.
  - A hostile clone gives the same prompt and tools as an empty one. A `read` of a file next to a hostile nested `AGENTS.md` adds no hostile text. A control run without the flags shows the hostile prompt.
  - Config planted in `HOME` reaches the prompt in the same step (control) and is gone in the next step.
  - The helpers run at a base commit fetched from a shard ref, the index is root-owned, and the T06 validator accepts `patch.json`.

## T12 must prove

- On a real Vercel sandbox: `ctxpipe-agent` cannot `sudo`, and root prepare through the SDK `sudo` option works. There were no Vercel credentials in the local env, so only the Vercel-like Docker image proves it now (also an open risk in ADR-052).

## Risks

- On Docker the agent and the default user are the same user. The default user writes the bundle staging copy; root copies it and refuses symlinks and special files in the copy.
- A process that the agent leaves running can outlive its step. T09 must start one OpenCode process for each step and stop it at the end.
- An empty `HOME` each step means OpenCode loads its provider package again each step. T03 must allow that fetch, or T02 must put the package in the image.
- The flags are OpenCode 1.18.34 behavior; the version check and the contract test stop an untested upgrade.
