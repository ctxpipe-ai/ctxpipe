# T05 Skill bundle packaging

## What

- `apps/backend/ingest-skills/`: one folder per skill (`SKILL.md`, `scripts/`, `schema.json`) and `bin/` with the stage helpers. The first skill is a placeholder `discover-roots` (one root per folder with a known manifest). T10 and later tickets give the real skills.
- `bin/ctxpipe-stage`, `bin/ctxpipe-delete`, `bin/ctxpipe-finish` (Node ESM, shared code in `bin/stage-lib.mjs`). They read `/ctxpipe/out/step.json` (`stepDir`, `contextDir`), which the host writes before each step. `ctxpipe-finish` writes `patch.json` in the format that the T06 validator reads: `create` with no `baseBlob`, `update` and `delete` with the blob at the context checkout's `HEAD`, and the delete `reason`. A staged file that did not change makes no op.
- `src/domain/ingestion/skill-bundle.ts`: `readIngestSkillBundle` (name `ingest-<16 hex>` from a SHA-256 of path, mode, and content), `installIngestSkillBundle` (copies to `/ctxpipe/skills`, writes the `.bundle` marker last, and skips a sandbox that already has the same bundle), and `startIngestStep` (makes the step folder and writes `step.json`).
- `src/domain/ingestion/ingest-opencode.ts`: `ingestOpenCodeConfig` and `ingestOpenCodeEnv`. The config has `instructions: []`, `skills.paths: ["/ctxpipe/skills"]`, no plugins and no MCP, and the permission `skill: {"*": "deny", <bundle skills>: "allow"}`. The env sets `OPENCODE_DISABLE_PROJECT_CONFIG`, `OPENCODE_DISABLE_CLAUDE_CODE`, and `OPENCODE_DISABLE_EXTERNAL_SKILLS`, and puts `/ctxpipe/skills/bin` first on `PATH`. The agent cwd is `/ctxpipe/out`, not a checkout.
- Backend and worker Dockerfiles copy `apps/backend/ingest-skills`. The chat sandbox image does not change.
- Read-only layout (`ingestLayoutScript`, `installIngestSkillBundle`, `sealIngestContext`): prepare runs one root script. Root owns `/ctxpipe`, `/ctxpipe/skills`, and `/ctxpipe/context/<workspaceId>`. Only `/ctxpipe/out` belongs to the sandbox user. The bundle and a checkout cloned as the sandbox user are moved into place by root. A system `safe.directory` entry lets the sandbox user read the checkout with git.
- `ingest-root.ts`: `dockerRunAsRoot` (a Docker exec as uid 0) and `vercelRunAsRoot` (the Vercel SDK `sudo` option). Both run the same script, so the hosted path gets the same layout at prepare.
- `assertIngestOpenCodeVersion`: prepare stops with a clear error when the sandbox OpenCode is not 1.18.34, the version whose flags the contract test proves.

## Why

Concept sections 3, 6, and 8; ADR-052. OpenCode 1.18.34 reads `AGENTS.md`, `opencode.json`, `.opencode/` (agents, commands, skills, plugins), `.claude/skills/`, and `.agents/skills/` from the cwd up to the git root. A probe showed that a hostile clone replaces the build agent prompt and adds `AGENTS.md` to the system prompt when the flags are off. The `skill` permission alone already hides the repository skills and the built-in `customize-opencode` skill.

## Tests

- `skill-bundle.test.ts` (5): the name stays when nothing changes, and changes when one script changes, a file becomes executable, or a file is added.
- `stage-helpers.test.ts` (9): real git and the real T06 validator. Create, update, and delete are accepted end to end; no op for an unchanged file; a second stage keeps the edit; absolute paths; path escape, missing reason, missing file, staged-and-deleted, and no active step are refused.
- `ingest-root.test.ts` (4): the Vercel runner sends `sh -c <script>` with `sudo: true` and fails with the stderr; the layout script and its owner check. No Vercel sandbox runs here.
- `ingest-sandbox-skills.contract.test.ts` (5, Docker, lane `ingest sandbox skills`): install and the skip by marker; as the sandbox user, writes, deletes, `chmod`, and `mv` in `/ctxpipe/skills` and the context checkout fail, and a write under `/ctxpipe/out` works; the version check passes on 1.18.34 and fails on a fake 9.9.9; a stub model in the sandbox records the OpenCode request. A hostile clone gives the same system prompt and tools as an empty repository, and `opencode debug config` and `debug skill` show nothing from it. A control run without the flags shows the hostile prompt. The helpers run in the sandbox, and the host validator accepts their `patch.json` from a git bundle of the context repository.

## Risks

- The Vercel root path is proven only by a unit test of the SDK call. The first hosted ingest run (T12) proves `sudo` on Vercel.
- `/ctxpipe/out/step.json` is writable by the agent. The helpers check that `stepDir` is under `/ctxpipe/out`, and the host validator checks every op.
- T02 and T09 must call `installIngestSkillBundle`, `sealIngestContext`, and `assertIngestOpenCodeVersion` at prepare.
