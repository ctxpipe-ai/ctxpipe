# T03: Ingest capability and closed egress

## What

- **Capability** (`workspace-chat-run-capability.ts`): `mintWorkspaceIngestRunCapability` and
  `verifyWorkspaceIngestRunCapability`, purpose `workspace-ingest-model`. Claims: org, org slug,
  run, shard, and the owner of the shard lock. The capability is valid only while that owner holds
  the shard lock (`ingest:<run>:<shard>`, not expired) and the run is an unfinished
  `repository-ingestion-v2` run of the org. Each purpose has its own Zod schema with a literal
  `purpose`, so a chat capability never parses as ingest, and the reverse.
- **Model proxy** (`routes/v1/workspace-chat-openai.ts`): accepts the ingest capability and
  attributes the call to the shard thread.
- **Docker** (`ingest-sandbox-egress.ts`, `dockerIngestSandboxProvider`): `create` opens the
  shard's vault with `unmatchedHosts: "deny"` and `ingestCredentialRules` only (Git fetch of the
  source and destination repositories, the model proxy, the tool bridge). The container gets the
  vault's proxy session and CA. `destroy` deletes the container, the vault, then revokes the
  shard's GitHub token. `refreshIngestSandboxEgress` replaces the rules for a later step (same
  rule names). `setRunVaultRules` is the new Agent Vault helper for that.
- **Hosted** (`vercel-sandbox-provider.ts`): `hostedNetworkPolicy({ ingestRepositories })` has no
  `"*"`. It has the GitHub fetch rules of those repositories, and during a step, the step's model
  proxy and tool bridge rules. `conversationFirewall(host, { ingestRepositories })` keeps it
  closed at step start and end. `vercelIngestSandboxProvider` wraps the conversation provider with
  that firewall, no Workspace base, and a read token for the run's repositories.
- **Tokens** (`run-git-tokens.ts`): an ingest shard records its tokens under
  `ingest:<run>:<shard>:<label>:<window>`, apart from chat `run:` keys.
  `revokeFinishedIngestGitTokens` is the sweep's backstop for finished or unknown runs.
- **Webhook** (`github.ts`): a push to `refs/ctxpipe/*` returns early (no tip check, ingestion, or
  connector sync).
- `ingestSandboxThreadId` moved to `chat-lifecycle.ts`: the capability module must not import the
  OpenWorkflow client at import time.

## Why

ADR-052 and the T03 spike (`spikes.md`). The sandbox never pushes: the host pushes ingest refs.

## Tests

- `workspace-chat-openai.ingest.integration.test.ts` (6, real Postgres and OpenWorkflow runs):
  the model proxy accepts an ingest capability; chat and ingest do not cross; refused after the
  next step takes the lock, after lock expiry, on another shard, after the run is cancelled; no
  mint for a lock it does not hold, another org's run, or an unknown run; forged payload and
  another secret.
- `ingest-sandbox-egress-native.contract.test.ts` (2, Docker, real Agent Vault, closed network):
  model proxy and bridge get the step's Bearer; `git clone`/`fetch` works; `git push` to the Git
  server and to github.com is refused; `example.com` (HTTP and HTTPS), other paths, GitHub
  receive-pack and REST API get `403`; a direct connection gets `000`; no credential is in the
  container environment; a refresh gives the next step's capability; destroy removes the
  container and vault and revokes the token. No Agent Vault fails closed; a failed create
  deletes the vault and revokes the token.
- `vercel-sandbox-provider.test.ts` (+4): ingest policy has no `"*"`, only fetch paths of the
  run's repositories, exact backend paths during a step; chat keeps `"*"`; the firewall stays
  closed at step start and end (msw for the Vercel API).
- `run-git-tokens.integration.test.ts` (+1): ingest tokens are apart from chat; the sweep revokes
  them only after the run, and retries a failed revoke.
- `github.test.ts` (+1): a push to `refs/ctxpipe/ingest/…` starts no tip check and no ingestion.

## Risks and follow-ups

- **Vercel was not tested live.** The proof is the policy object. Open question: does Vercel
  refuse a path with no rule on a listed host (for example `git-receive-pack` on github.com)? If
  it forwards it without a credential, GitHub refuses the push (no token), so the risk is low.
- Host dev (`agent-vault-dev`) does not force traffic through the proxy. The contract test moves
  the container to an internal network, as DinD and AWS do. T09 should not run ingest on host
  dev with real data.
- Sandbox Git URLs must be `https://github.com/<owner>/<name>.git` (with `.git`).
- T09 wires it: build the provider for the deployment's isolation, mint the capability per step
  while it holds the shard lock, call `refreshIngestSandboxEgress` (Docker) or `openTurn` and
  `closeTurn` (hosted), and call `destroy()` in `destroy-sandbox`.
- The ingest vault session TTL is the shard limit plus 15 minutes.
