# T07 Context index

## What

`apps/backend/src/domain/ingestion/context-index.ts` builds `<workspaceId>.index.json` for the sandbox. The host stages it. The agent reads it before it writes.

Each entry holds: `path`, `kind`, `title`, `summary`, `links`, `sources`, and `owned`.

- The units come from the projection rows at the pinned revision (`listWorkspaceUnitsAtRevision`).
- The raw files come from the same revision in git (one `git cat-file --batch`).
- `title`: front matter `name`, else the first heading.
- `summary`: front matter `summary` or `description`, else the first paragraph. Cap: 160 characters.
- `links`: paths of other units in the projection, resolved with `resolveHydrateLink`. Cap: 10 per entry.
- `sources`: normalized URLs, only for a file with `generated_by: ctxpipe-extract`. Cap: 5.
- `owned`: `fileOwnership(raw, sourceUrl) !== "foreign"`. This is the T06 predicate. A shared file is owned.

## Why

Concept section 4.2: the agent must update or link to existing context, not only add files.

## Bounds

At most 2000 entries and 256 KB of JSON. When a cap applies, owned entries stay first, then the others in path order. The result is sorted by path. `total` and `truncated` tell the agent what is missing.

## Tests

`context-index.integration.test.ts` (real Postgres, real git, units from `hydrateKnowledgeTree`): expected entries; a file a human took over (no `generated_by`) is not owned; a file of another source is not owned; same revision gives the same bytes; a revision with no projection gives no entries; the cap.

## Risks

- The unit rows hold no title or summary column yet, so the host reads git. The index needs a repository directory at the revision.
- A text-heavy first paragraph can be a poor summary.
- `patch-validator.test.ts` has slow tests (one takes 13 s under load). Use `--testTimeout 60000` on a busy machine.
