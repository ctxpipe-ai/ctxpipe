# T02: Ingest sandbox definition and slot policy

## What

- `apps/backend/src/domain/workspaces/ingest-sandbox.ts`: `ingestSandbox()`, the second stock
  `defineSandbox` (`workspace-ingest:<image>`, `reuse: "thread"`, `snapshot: "none"`). The thread
  is `ingest:<runId>:<shard>` (`ingestSandboxThreadId`). Stock TanStack hashes the thread into the
  sandbox key, so the thread is the readable key. The thread is also the name of the shard lock.
- The sandbox uses the chat store (`postgresSandboxInstanceStore({ kind: "ingest" })`), the chat
  locks (scoped to the Workspace fence), and the provider that the caller builds as for chat.
  Docker and Vercel take slots. An unsandboxed run takes none (only an operator selects it).
- Row: `kind = "ingest"`, `conversation_id` = the ingest thread, `latest_run_id` = the run id. No
  migration: `kind` is a text column.
- Slots (`conversation-sandbox-lifecycle.ts`): one shared wrapper for chat and ingest. Chat at 50
  fails with `SandboxCapacityError` (no change). Ingest at 50 in total or 40 ingest fails with
  `IngestSandboxSlotsFull`. `ingestSandbox().ensure()` then waits outside every lock (poll, 5 s by
  default) until a slot is free or its signal aborts. Limits are committed constants in
  `chat-lifecycle.ts` (`ORG_INGEST_SANDBOX_LIMIT = 40`, `INGEST_SHARD_LIMIT_MS = 60 min`).
- Sweep (`sweepConversationSandboxes`): an ingest row goes when its run is unknown, finished, or
  belongs to another org (`unfinishedOrgWorkflowRunIds` reads `openworkflow.workflow_runs`), when
  it is older than the shard limit (from `created_at`), or after a failed delete. A held shard
  lock keeps the row for the next retry. A kept row schedules the next sweep at its limit. Each
  `ensure()` also schedules a sweep at `created_at + 60 min`.

## Why

ADR-052 section 7. The wait (not a failure) at capacity is outside the locks because the stock
`ensure` holds the Workspace fence and the sandbox lock during `create`. A wait inside them
would block chat starts and the sweep in the same Workspace.

## Tests

- `ingest-sandbox.integration.test.ts` (7, real Postgres, local-process sandboxes): chat at 50
  (40 ingest) fails; an ingest start at 50 in total waits with no row and stops on abort; row
  shape and attach; sweep deletes an orphan (unknown run); keeps an unfinished run's row until
  the limit, and keeps it while the shard lock is held; deletes after the run is cancelled; a
  run of another org does not keep it.
- `ingest-sandbox-native.contract.test.ts` (2, Docker, lane "native sandbox ownership"): ensure
  creates, attaches (same container, file kept), and creates again after `docker rm -f`; the
  sweep is queued at the limit; destroy removes the container and row. The 41st ingest start
  waits while a chat start succeeds, and starts when a slot frees.
- Regression: `sandbox-lifecycle-native.contract.test.ts` 11/11.

## Risks and follow-ups

- T03 builds the ingest provider (Agent Vault `deny`, Vercel firewall without `"*"`) and the
  capability. T09 passes the run's provider, holds the shard lock (`threadId`) for each step, and
  calls `destroy()` in `destroy-sandbox`.
- `workspaceId` must be a Workspace of the run. The row is deleted with that Workspace.
- Waiters have no order: a start takes the first free slot it sees. The 60-minute shard limit
  bounds each wait.
- The sweep keeps a row only for an unfinished `repository-ingestion-v2` run (`version is null`)
  whose top-level input `orgId` is the row's org. T09 must use `INGESTION_V2_WORKFLOW_NAME` and
  `IngestionV2RunInput` from `domain/ingestion/ingestion-run.ts`.
- A create refuses a Workspace that the org cannot see (chat and ingest).
- An unsandboxed ingest run logs a warning: it takes no slot and has no closed egress.
