# P1-1 Scopes and tool annotations

## What

- `oauthProvider` knows `ctxpipe:read` and `ctxpipe:write`. A token with `ctxpipe:write` expires after 1 hour (`scopeExpirations`); other tokens keep 4 hours.
- The protected resource metadata for `/mcp` gives `scopes_supported: ["ctxpipe:read", "ctxpipe:write"]` only. It no longer copies the OIDC scopes from the authorization server.
- The `/mcp` 401 challenge has `scope="ctxpipe:read"` (with no credential and with a token that is not valid).
- `auth/mcp-scopes.ts` holds the scope rules. `withAuth.ts` only stores the token scopes in `c.var.oauthScopes` (opaque row `scopes`, JWT `scope` claim).
- Granted scopes: an OAuth grant with `ctxpipe:write` gets read and write. Each other principal gets read: a grant with `ctxpipe:read`, a grant from before the scopes, a session, a personal API key, an org API key.
- The scope of a tool comes from its annotation: `readOnlyHint: true` needs read; each other tool needs write (fail closed). The transport disables the tools outside the granted scopes, so `tools/list` does not show them. A `tools/call` for such a tool gets HTTP 403 with `error="insufficient_scope"` and `scope=` set to the full needed set.
- `ctx_advisor` has `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: false`, `openWorldHint: false`.
- The consent page shows each scope as text. `ctxpipe:write` is a check box that is off by default. Without the tick, the consent request leaves the write scope out.

## Why

CTX-586 design v2, section 4 (option A, approved).

## Tests

- `apps/backend/src/routes/mcp.scopes.integration.test.ts` (10 cases, real Postgres, real Better Auth OAuth flow, MCP SDK `Client`): 401 challenges, metadata, consent without write gives a token without write (write tool hidden, 403), consent with write (tool listed and runs, token at most 1 hour), legacy opaque grant, personal key (header and bearer), org key and session cookie all read only. All 10 fail on the base commit.
- `apps/ui/src/features/auth/OAuthConsent.test.tsx`: 3 new cases (write off by default, tick to allow, no box for a read-only request). They fail on the old component.
- MCPJam protocol conformance (`routes/mcp.conformance.test.ts`) passes.

## Risks and follow-ups

- **Existing OAuth clients (fixed).** Data migration `*_mcp_scopes_on_oauth_clients` appends `ctxpipe:read` and `ctxpipe:write` to `oauth_clients.scopes` when they are missing. The user still ticks write at consent.
- **Refresh tokens.** The authorization server metadata lists `offline_access`; the resource metadata and the challenges do not. A client that asks for `ctxpipe:read offline_access` gets a refresh token, and the refreshed token stays read only. A client that asks only for the challenge scope gets no refresh token.
- API key `permissions` are not used. All keys are read. A write-capable key needs its own design.
- P1-2a changes the org resolution in `withAuth.ts`; this ticket only adds the `oauthScopes` lines and the `scope=` on the challenges there.
