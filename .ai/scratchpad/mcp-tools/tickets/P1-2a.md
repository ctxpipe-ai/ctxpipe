# P1-2a Multi-org grant: storage and per-call check

## What

- Table `oauth_grant_organizations (grant_id, api_key_id, organization_id, created_at)`. Each row sets exactly one of `grant_id` and `api_key_id` (check `oauth_grant_organizations_one_owner`). Unique on `(grant_id, organization_id)` and on `(api_key_id, organization_id)`. Both foreign keys cascade.
- OAuth consent: `consentReferenceId` returns a grant id (`ogr_*`) from `findOrCreateOAuthGrant`. It reuses the newest consent of the same client whose grant holds the selected org, or a legacy consent bound to the org id. Better Auth calls the hook on authorize and on consent, so the value must be stable. The client id comes from the request (`client_id` query, or `client_id` in the signed `oauth_query` body field) through `withOAuthRequestContext`.
- JWT claim `https://ctxpipe.ai/grant_id` for grant ids. Legacy org-id references keep `https://ctxpipe.ai/organization_id`.
- Context variable `oauthOrganizationId` is now `oauthReferenceId` (grant id, legacy org id, or null).
- `resolveCallOrg(principal, orgSlug)` in `auth/call-org.ts` (P1-3 calls it with the tool `org` argument). The principal's org set intersected with live membership decides. Unknown and not-allowed orgs both give `org_not_found`. With no org named, a set that holds one org uses it; otherwise `org_required`.
  - Grant id: its rows. No rows (revoked or all unticked): no org.
  - Legacy reference (org id): a one-org set.
  - Personal API key: its rows; no rows: every current membership (legacy).
  - Org API key: its one org (no membership check).
  - Cookie or session token: every membership.
- `withNetworkOrgContext` uses `resolveCallOrg` with `?orgSlug=` or the path slug. This stays only until P1-3 tools take the org from their argument; tools ignore `?orgSlug=`.
- Storage helpers for P1-2b: `setGrantOrganizations`, `setApiKeyOrganizations`, `revokeOAuthGrant`.

## Why

ADR-051 and the ADR-026 amendment: one grant covers a set of orgs, each call names one org, and a set change or a membership change acts on the next call with no new token.

## Tests

- `auth/oauth-grant-orgs.integration.test.ts` (20, real Postgres): set + member allowed; outside set, unknown, and foreign org give the same `org_not_found`; set member without membership denied; membership removed mid-session; untick with no new token; revoked grant; legacy reference; one-org default and `org_required`; org key naming another org; personal key with and without a set; session; check constraint and uniqueness; consent grant reuse and legacy consent reuse; over HTTP with opaque tokens, including the tool path that ignores `?orgSlug=`.
- `auth/oauth-organization.test.ts`: claim mapping and client id parsing.
- `auth/withAuth.test.ts`: fake DB updated. Two cases that depended on JS slug comparison moved to the integration test, because the filter is now SQL.

## Risks

- Not tested end to end with a real Better Auth authorize and consent round trip (the hook wiring has unit coverage only).
- A first consent can leave a grant row with no consent when the user cancels. The row grants nothing, because no token refers to it.
- P1-1 also edits `auth/withAuth.ts`; expect small merge conflicts at the JWT claim block and the `oauthReferenceId` rename.
