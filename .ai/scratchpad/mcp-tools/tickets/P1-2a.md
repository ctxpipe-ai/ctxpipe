# P1-2a Multi-org grant: storage and per-call check

## What

- Table `oauth_grant_organizations (grant_id, api_key_id, organization_id, created_at)`. Each row sets exactly one of `grant_id` and `api_key_id` (check `oauth_grant_organizations_one_owner`). Unique on `(grant_id, organization_id)` and on `(api_key_id, organization_id)`. Both foreign keys cascade.
- OAuth consent: `consentReferenceId` calls `resolveOAuthGrantReference`. Better Auth calls the hook on authorize, on consent, and after sign-in.
  - Outside the consent request: the newest consent reference of the client, else the org id. No grant is made, so a first authorize leaves no orphan grant and a request with no client id cannot loop. A skipConsent client gets the legacy one-org reference.
  - In the consent request: the grant of the newest consent, or a new grant. Its org set becomes exactly the selected org. A consent request with no client id fails.
  - The client id comes from `client_id` on a GET, or from the signed `oauth_query` body field on a POST (never from the URL of a POST).
- JWT claim `https://ctxpipe.ai/grant_id` for grant ids. Legacy org-id references keep `https://ctxpipe.ai/organization_id`.
- Context variable `oauthOrganizationId` is now `oauthReferenceId` (grant id, legacy org id, or null).
- `resolveCallOrg(principal, orgSlug)` in `auth/call-org.ts` (P1-3 calls it with the tool `org` argument). The principal's org set intersected with live membership decides. Unknown and not-allowed orgs both give `org_not_found`. With no org named, a set that holds one org uses it; otherwise `org_required`.
  - Grant id: its rows. No rows (revoked or all unticked): no org.
  - Legacy reference (org id): a one-org set.
  - Personal API key: its rows; no rows: every current membership (legacy).
  - Org API key: its one org (no membership check).
  - Cookie or session token: every membership.
- `withNetworkOrgContext` uses `resolveCallOrg` with `?orgSlug=` or the path slug. This stays only until P1-3 tools take the org from their argument; tools ignore `?orgSlug=`.
- Storage helpers for P1-2b: `setOrganizations(owner, orgIds)` and `revokeOAuthGrant({ grantId, userId })`. Revoke accepts only a grant id and deletes only that user's consent and tokens.

## Why

ADR-051 and the ADR-026 amendment: one grant covers a set of orgs, each call names one org, and a set change or a membership change acts on the next call with no new token.

## Tests

- `auth/oauth-grant-consent.integration.test.ts` (2): the real Better Auth authorize, consent, and token flow. One grant after the first connect, reuse with no consent loop, and a skipConsent client with no grant row.
- `auth/oauth-grant-orgs.integration.test.ts` (25, real Postgres): set + member allowed; outside set, unknown, and foreign org give the same `org_not_found`; set member without membership denied; membership removed mid-session; untick with no new token; revoked grant; legacy reference; one-org default and `org_required`; org key naming another org; personal key with and without a set; session; check constraint and uniqueness; consent reference rules (no grant outside consent, no client id, exact org set, legacy consent); revoke scope; over HTTP with opaque tokens and personal keys.
- `auth/oauth-organization.test.ts`: claim mapping and client id parsing (a POST ignores the URL).
- `auth/withAuth.test.ts`: four org-resolution cases moved to the integration test, because its fake DB ignores the SQL filter.

## Risks

- Outside the consent request, a returning user reuses the newest consent of the client, whatever org is active. To change orgs, the user consents again (`prompt=consent`) or edits the grant (P1-2b).
- The `?orgSlug=`-ignored rule for tools belongs to P1-3 on the real `/mcp`.
- P1-1 also edits `auth/withAuth.ts`; expect small merge conflicts at the JWT claim block and the `oauthReferenceId` rename.
