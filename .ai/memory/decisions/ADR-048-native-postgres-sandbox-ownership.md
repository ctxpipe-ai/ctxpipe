# ADR-048: Conversation sandboxes: stock providers, Postgres ownership, git as durable state

**Status:** Accepted (revised 2026-10-02) | **Date:** 2026-09-09 | **Tags:** tanstack, postgres, sandbox, chat

## Context

Every Workspace conversation runs OpenCode in its own sandbox with a checkout of the Workspace repository ([ADR-044](ADR-044-workspace-chat-stock-tanstack.md)). Backend replicas restart and scale, so sandbox ownership must live outside the process. PR 280's recovery reached that through ~9.9k lines of patches to TanStack's sandbox, Docker and OpenCode packages (custom isolation, egress proxy, runtime workspace swaps, live revision moves). This revision records what we keep and what we decided instead. Items marked *(ticket NN)* are decided but not yet shipped; see `.ai/scratchpad/pr-280-release/`.

## Decision

### Ownership

- TanStack `defineSandbox` with our Postgres `SandboxInstanceStore` (`sandbox-instance-store.ts`) and `LockStore` (`sandbox-lock-store.ts`). Keys are exact: a missing key returns null; upsert replaces that key's record.
- Locks are tenant-scoped rows with expiring owner tokens. Acquire, renew and release are each a short RLS transaction; no SQL spans provider I/O ([ADR-041](ADR-041-short-org-sql-unique-sandbox-rows.md)). Losing the lease aborts the run.
- Creating a sandbox and deleting a Workspace or conversation take the same workspace-scoped lock first, so deletion cannot race a first ensure.
- No process-owned registries or handle caches. One exception: each process caches the hosted agent snapshot id (below). A stale entry is forgotten when a start fails, so it never decides ownership.

### Providers

| Deployment | Provider |
| --- | --- |
| Hosted | `@tanstack/ai-sandbox-vercel` *(ticket 02)* |
| Self-host (Compose) | stock `dockerSandbox` against a Docker-in-Docker service. See [ADR-049](ADR-049-self-host-chat-sandbox-stock-docker.md). |
| Self-host (AWS CDK) | stock `dockerSandbox` against an always-created EC2 Graviton Docker host. See [ADR-049](ADR-049-self-host-chat-sandbox-stock-docker.md). |
| Local dev | stock `dockerSandbox` against the developer's Docker |
| Unsandboxed | explicit `SANDBOX_PROVIDER=unsandboxed` only; never chosen automatically, never recommended |

Hosted needs CPU billed only while busy (an agent mostly waits on the model), a TanStack provider, fast start and durable files. Vercel is the chosen vendor: microVM isolation, an existing vendor, and 10,000 concurrent sandboxes. Its provider gaps (start from snapshot, authenticated agent port, process kill) need no patch: our `Sandbox.create` wraps the stock `VercelHandle` (`vercel-sandbox-provider.ts`), and `Command.kill` also stops child processes.

### Isolation and egress

- In the sandbox, only stock TanStack policy: `commands`, `capabilities.fileWrite`, `capabilities.network`, `default`. No custom egress proxy, per-run grants, resource quotas, Btrfs runner or isolation patches *(ticket 01)*.
- Hosted egress is an allowlist in Vercel's firewall (enforced outside the VM): our backend and GitHub, nothing else. OpenCode comes preinstalled from the agent snapshot (below), whose builder is the only sandbox allowed the npm registry. Self-host relies on the Docker network.
- The agent's OpenCode port is authenticated (server password, sent as headers by the provider's port channel), because Vercel ports are public URLs *(ticket 02)*.

### Identity and git

- The sandbox belongs to the conversation, keyed without the commit SHA (option D, *ticket 01*). Before a turn, if the default branch moved, the sandbox fetches and rebases its session branch in place with stock `exec`. The current SHA is recorded in our sandbox row, not in the key.
- Conversation work is committed by the agent and pushed to the session branch `ctxpipe/chat/<conversation>/<n>` through the broker (the agent's tool or Commit+Push). The broker replaces the remote tip only when it is the tip ctx| pushed last; committed work is pushed before a sandbox is deleted. Git is the durable state; a sandbox is disposable and is recreated from the session branch when it is gone ([ADR-040](ADR-040-pierre-files-pane-chrome.md)).
- No credential is baked into the sandbox image, key or environment. The sandbox gets short-lived, HMAC-signed run capabilities bound to org, conversation, lock owner and revision (`workspace-chat-run-capability.ts`). It exchanges them through the backend for model access via the model proxy (`workspace-chat-model-proxy.ts`), so no model key enters the sandbox.
- **Docker (self-host): no token in the sandbox.** Agent Vault adds the GitHub read token, the model capability, and the tool bridge token in flight ([ADR-049](ADR-049-self-host-chat-sandbox-stock-docker.md), 2026-10-08). The run's GitHub token covers the Workspace repository and its linked repositories on the same connection, read-only. It is minted outside Octokit's cache and recorded in `workspace_sandbox_git_tokens` under `run:<conversation>:…` (`run-git-tokens.ts`), one per run label. Writes never use it: every push goes through the backend broker, only to the conversation's session branch. When a turn finishes, fails, or is aborted, the backend deletes the run's vault (its proxy session stops at once) and then revokes the turn's tokens (`DELETE /installation/token`), after the turn releases the conversation lock. A prepare (also the prepare of a Files write or diff) deletes its vault and revokes its own token before it releases the conversation lock. A record is removed only after GitHub confirms, so the conversation sandbox sweep retries a failed revoke. The sweep skips a conversation that a turn holds, and a token younger than 2 minutes, because a turn mints its token before it takes the lock. A revoke failure never fails the turn. Attaching to a sandbox for a Files read mints no token and opens no vault. **Local (unsandboxed)** still puts the clone token in `CTXPIPE_CLONE_TOKEN`; that mode has no isolation. Known limit: an unsandboxed run never schedules the sweep, and a token whose revoke failed stays valid until it expires (1 hour). (2026-10-08)
- **Hosted (Vercel): the token stays outside the sandbox** (decided 2026-10-03). The firewall rule for `github.com` and `api.github.com` adds the `Authorization` header, so the token is never in the sandbox's environment or files. Each sandbox keeps one token for **10 minutes**. A turn does no token work while the token is younger than that. After that, the backend mints a fresh token (bypassing Octokit's cache) and replaces the rule, off the turn's critical path. It revokes the previous token after a ~30 s grace, and revokes the current one when the sandbox stops. Vercel returns injected header values as `<redacted>`, so the token is not readable through Vercel's API, and our only copy is an encrypted row per sandbox (`workspace_sandbox_git_tokens`, AES-GCM with the connection-secrets key) holding the token and its mint time. Measured: the rule update takes ~0.4 s and applies ~0.35 s later. A hosted sandbox gets no Git run capability and no clone token, and the credential route refuses a conversation that has a hosted sandbox, so a hosted sandbox never holds a GitHub token. Hosted tokens are also minted outside Octokit's cache: a revoked token in the shared cache would reach other readers of the same scope.

### Fast start: Workspace base

- Each Workspace has a **base**: a provider snapshot of a sandbox that cloned the Workspace repository (default branch, depth 1) and ran the provider's setup. It is a row of kind `base` in `workspace_sandbox_instances` (`workspace-sandbox-base.ts`): `image` is the agent image it was built on, `revision` the commit it holds, `latest_snapshot_id` the image or snapshot, `provider_sandbox_id` the builder, `created_at` the reservation time and then the publish time, `last_heartbeat_at` the last start from it. State `building` until published.
- **Start.** A new sandbox (a new conversation, or one whose sandbox is gone) starts from the Workspace's newest ready base for the current agent image and binding. The base is chosen inside `create`, under the Workspace lock that stock `ensure` already holds. An existing sandbox is resumed whatever it started from: the base is not in the sandbox key. Stock bootstrap skips the clone when `.git` exists, so setup only fetches the desired commit if the base lacks it and checks out the session branch. A base that the provider says is gone is marked `destroy_failed`, and the start goes on without it, once. On Vercel, a create that fails on a base the provider still lists also marks it `destroy_failed`, and that start goes on from the agent snapshot, once; so a bad base never blocks new conversations until it is stale. When the provider cannot say (an outage), the start goes on without the base and the base is kept. With no usable base, or a stale one, the start requests a build (runs keyed by Workspace and 10-minute window, so concurrent starts share one); nothing waits for a build.
- **Sandbox key.** Docker: the key holds the chat image's content id, as before, so a new chat image gives new sandboxes. Vercel: the key holds one fixed value (`vercel-agent`), so an OpenCode upgrade never orphans hosted conversations; a resumed sandbox keeps the OpenCode it started with. Bases are matched to the versioned agent image (`vercel-agent/<runtime>/<OpenCode version>`). The change from the earlier key gives hosted conversations a new sandbox once, before hosted chat has launched (decided 2026-10-04).
- **Build.** The OpenWorkflow job `workspace-sandbox-base` runs durable steps ([ADR-047](ADR-047-native-durable-write-workflows.md)). `reserve` decides and records a `building` row whose id comes from the workflow run, so a retried reserve finds its own row; it writes under the Workspace lock and the org's slot lock. `build` starts the builder, clones, runs setup, captures and publishes. It runs once, with no step retries. A failed build, also one whose builder cannot start, deletes what it made and marks its row `destroy_failed` in its own catch, so it stops blocking new builds and holding a slot at once. The sweep deletes the row, and the first start of the next 10-minute window requests a new build. The `building` row is the build's lease: one hour from `last_heartbeat_at`, which the reserve sets and the build renews while the clone and setup run. One build at a time per Workspace. The lease predicate is written once, in SQL; reads return it as `leaseHeld`. The build checks again that the lease is its own right before the capture and at the publish; if the lease is gone, it stops and deletes its builder. Every write of the build (its builder, then the publish) is one conditional UPDATE that matches only while the lease holds and the row still names this builder. So a write never recreates a deleted row, and 0 rows means the lease is gone. The builder id is written as soon as it exists. The capture and `live` are one UPDATE, which also sets `created_at` to the publish time. The publish takes the Workspace lock, which a create holds while it chooses its base and records its sandbox row. So a sandbox that chose the old base is recorded before the new base supersedes it, and Vercel retention sees it. A second run of a published base returns it as it is; a row that already names a builder belongs to another run. A capture that a crash left unpublished is not in the row: the Docker image carries the row id as a label, and the host prune removes it when the row does not name it and no build of that row holds its lease, and a Vercel snapshot is deleted with its builder, whose id the row holds (deletion lists the snapshots under the builder first). However an attempt ends, its Docker builder is removed, and its Vercel builder is deleted (before publish) or stopped, with its token revoked. A build in progress takes one of the org's 50 slots while its lease holds; at the limit there is no build. A finished base runs nothing and takes none.
- **Stale.** A base is rebuilt once the default branch has moved and the base is a day old. A day of drift costs the pre-turn fetch of the changed files, which is small next to a rebuild for every push.
- **Docker** (no patch): the builder is a container of the chat image created by our code (so it carries labels) and wrapped in the stock `DockerHandle`; `docker commit` makes the base image, tagged `ctxpipe-workspace-base:<row>` and labeled `ai.ctxpipe.sandbox` (`workspace-base`; builders `workspace-base-builder`), `ai.ctxpipe.store` (hash of the database host, port and name), `ai.ctxpipe.base` and `ai.ctxpipe.org`. Conversations use stock `dockerSandbox({ image: <base> })`; their containers inherit the image's labels. No secret reaches the image: create gets no environment, the clone token travels in the clone command's environment, and the chat image's credential helper never stores (proven by scanning a base built with a token).
- **Vercel** (no patch): conversations never reach npm. Per environment, runtime and OpenCode version there is an **agent snapshot**: a `node26` builder tagged `ctxpipe=workspace-agent` (with `opencode=<runtime>-<version>`) that can reach only `registry.npmjs.org` and installs OpenCode. Each Vercel sandbox we create (conversation, base builder, agent builder) has 1 vCPU and 2 GB of memory; one constant, `VERCEL_SANDBOX`, sets the size and the runtime. A sandbox from a snapshot keeps the runtime of the snapshot. The base image key is `vercel-agent/<runtime>/<OpenCode version>`, so a new runtime builds the agent snapshot and the Workspace bases again once. Its snapshot has no expiry in production and a 30-day expiry on PR previews. Conversations without a base start from it. Workspace base builders (tagged `ctxpipe=workspace-base`) also start from it, then clone, run setup and snapshot. A base builder reaches GitHub only, with the read token in the firewall rule; it cannot reach our backend.
  - The agent snapshot is cached in the process and found through its tagged builder. If none is found, a new one is built (once per process; two replicas may each build one, and both are valid). So correctness does not depend on Vercel keeping stopped builders; losing them only costs a rebuild. A cached snapshot that fails to start a sandbox is forgotten. After a build, off any start, agent builders of other OpenCode versions and builders without a live snapshot (an hour old, so not a build in progress) are deleted.
  - Production base snapshots have no expiry and are deleted from their rows. Snapshots carry no tags, so the stopped builder is kept as the snapshot's owner: deletion removes the snapshots listed under the builder first, then the builder. The PR-close cleanup (`deletePreviewSandboxes.ts`) finds base and agent builders by environment tag; a preview's base snapshots also expire after 30 days, should a builder no longer be listed.
  - Not measured yet (the Vercel contract lane has not run): whether a sandbox survives deletion of its source snapshot (the lane asserts it), and whether a base built from an agent snapshot survives deletion of that agent snapshot. Cleanup keeps Vercel bases conservatively until the first is known (see Cleanup), and agent snapshots of the current version are not deleted. Two more gaps: a process crash during a build leaves the builder's GitHub token unrevoked until it expires (one hour at most); and a production Vercel builder that a crash leaves before its id is recorded has no cleanup path (previews have the PR-close cleanup).

### Lifecycle and limits

- An interactive sandbox stops after **5 minutes idle**; files are saved (Vercel snapshot on stop; Docker `stop`) and the next message resumes it. Idle is measured from the sandbox row's `last_heartbeat_at`, set when a turn, prepare or file read uses the sandbox and again when a turn ends (before the conversation lock is released). A sandbox is never stopped while a turn or file read holds the conversation lock `chat-thread:<conversation>`: the stop takes that lock without waiting and skips the sandbox if it is held. A stopped sandbox has row state `stopped`.
- A conversation's saved state is kept **30 days** after last use, then deleted with its row (Vercel delete also revokes the GitHub token); pushed work stays in git.
- Each organization runs at most **50 sandboxes** at once: live conversation and job rows of a running provider (Docker or Vercel), and Workspace base builds whose lease holds; finished bases run nothing and do not count. Every start (a create, or the resume of a stopped sandbox) counts them under the org lock `org-sandbox-slots`, re-reading the row inside the lock. A create first reserves its row, so concurrent starts in other Workspaces see it, and releases it at once if the create or its setup fails. A resume whose row was deleted meanwhile starts a fresh sandbox instead of reviving the row. Over the limit the start fails with `SandboxCapacityError` (code `sandbox_capacity`): HTTP 429 on prepare, Files, pull-request and MCP, an "at capacity" `RUN_ERROR` in the chat stream, and an alert when a conversation opens. Unsandboxed runs have no sandbox and no limit.
- Runs nobody is watching stop their sandbox when the run ends (success, error or abort), so they never hold a slot: MCP `ctx_advisor` turns, and HTTP or WebSocket chats whose `source` is not `ui`. Each call site wraps the run (`stopConversationSandboxes`, `stoppingSandboxWhenDone`). The Slack mention agent does not use a workspace chat sandbox.
- Opening a conversation prepares its sandbox (warm for a fast first answer) and counts as use. Reading a file never creates a sandbox.
- Cancel kills the agent process. Docker and Vercel both support it (`killableProcesses`).

### Cleanup

- There is no cron. The OpenWorkflow job `conversation-sandbox-sweep` (one org per run) stops idle sandboxes, deletes sandboxes 29 days after their last use (a day before Vercel expires saved state) or when their conversation is gone, and retries failed deletes (`destroy_failed`). Before a deletion, it pushes committed work. It keeps a sandbox while a local branch has commits that no remote has, until the saved state expires.
- One chain per org: each run first sweeps, then, in a separate step (so a retried run does not compute a second next time), schedules the next run for when a running sandbox is next due. Runs are keyed by org and minute boundary. Due times come from state (last use plus 5 minutes), and retries (a turn holds the conversation, a stop or delete failed) go to the next 5-minute boundary, so runs that compute the same next time share one run.
- Every use schedules the sweep for its own idle time: a turn's end, a prepare or file read. The worker schedules a sweep at start for every org with a sandbox row, and every Workspace tip check schedules one, so a lost chain (a failed schedule, a crashed replica) restarts.
- A stopped sandbox schedules a due time for its deletion, 29 days after its last use. Vercel expires saved state after 30 days, so the push before the deletion can still resume the sandbox. A sandbox that keeps unpushed commits waits for the next sweeps, until its saved state would expire. Retries stay inside the PR worker's 10-minute idle window.
- Rows whose Workspace is deleted go with it; Workspace and conversation deletion destroy their sandboxes first (`workspace-sandbox-cleanup.ts`). Relink and Workspace deletion destroy bases too, after the conversation sandboxes (a Docker daemon keeps an image a container uses).
- **Bases** are deleted by the org's sweep only (`collectUnusedWorkspaceBases`), under the Workspace lock that new sandboxes take to choose their base. Due: builds past their lease, failed deletes, every base but the current one (a newer base, another agent image or provider, a relinked Workspace), and the current one once no new sandbox started from it for 30 days.
  - Docker: due bases go at once. Measured: a stopped container restarts with its files after `rmi --force` of its image. A running container makes the daemon refuse (409), and the row waits for a later sweep.
  - Vercel: a due base goes only when no Vercel conversation sandbox of its Workspace was created before the base was superseded, that is before a newer base was published (or before now, for the current one). A sandbox started from the old base while the newer one was still building counts. Survival after source-snapshot deletion is not measured, so a base is kept while a sandbox that could have started from it exists. Conversation sandboxes are deleted at most 30 days after last use, so this ends.
  - Skipped when the deployment's agent image cannot be read, so a daemon blip never deletes the base that new conversations should use.
  - Each base left after a sweep schedules the org's next sweep: a live base at its retention end, a build at its lease end, a failed delete at the next retry. A Vercel base kept for a conversation sandbox waits for that sandbox's expiry (30 days after its last use, because a sandbox with unpushed commits can stay that long). A time already past becomes the next retry, because a run keyed to a past minute does not run again. So a dormant org's bases go without a new use. The worker-start backstop still schedules a sweep for every org that has any sandbox row (`orgsWithSandboxes`), in case a chain was lost.
  - Vercel: a base whose start failed is marked `destroy_failed` only when `Snapshot.get` shows the snapshot gone or not usable. The start's own error does not decide it. On any other result, that start goes on without a base, and the base is kept. A `destroy_failed` base that has a snapshot is also kept while a sandbox may use it; one with no snapshot (a failed build) is deleted at once.
- **Docker host prune** (`docker-sandbox-host-prune.ts`, OpenWorkflow job `docker-sandbox-host-prune`). Every org's sweep on a Docker deployment requests it, and runs are keyed by the 5-minute boundary that sweeps retry on. So the host is pruned once per sweep window, however many orgs sweep. The host's disk only grows while sandboxes run. The prune sweeps no org: each org's own sweep chain handles its rows (see above). It does two things:
  - It removes base images labeled with this deployment's database whose base row is gone, or whose row names another image while no build of that row holds its lease (a build that crashed between its capture and its publish).
  - It removes containers labeled with this deployment's database that no row records and that are older than `orphanAgeMs` (one hour; lost builders, containers started from a base). The base row is checked at removal, so a build that has committed but not yet published is safe.
  - It never touches images of other deployments that share the daemon, unlabeled objects, or images a running container uses. Unreachable: a container started from the plain chat image whose row was removed without destroying it. Our code never does that: a failed delete keeps the row as `destroy_failed`.
- Hosted (Vercel) has no host prune: the org's sweep deletes snapshots past retention and unused bases. The self-host design is in [ADR-049](ADR-049-self-host-chat-sandbox-stock-docker.md).

## Consequences

- Replicas can restart or hand over mid-conversation; the lock and store carry ownership, git carries the work.
- Losing a sandbox costs one cold start, never user work that was pushed.
- Isolation is whatever the provider plus stock policy gives. Vercel provides microVM isolation for hosted. Self-hosters rely on Docker.
- Semantic merge needs no sandbox: it is one schema-checked model call whose output native Git stages.
- Stock Docker passes create options, including the environment, in the request URL, so our provider wrapper (`withSessionOnlyEnv`) drops them from create and sets secrets on the session instead.

## Alternatives considered

- **Railway Sandboxes for hosted.** Rejected: capped at 100 concurrent sandboxes per environment, no TanStack provider.
- **Cloudflare Sandboxes.** Rejected: TanStack's provider only runs inside a Cloudflare Worker, files are lost when the container sleeps, no snapshots or process kill.
- **Upstash Box.** Rejected: container isolation (shared kernel across tenants), SOC 2 in progress, no custom images, despite the best price and TanStack integration.
- **E2B, Daytona.** Rejected: CPU and memory billed while reserved, not only while busy. Daytona is also closed source since June 2026, and its lower tiers cannot reach our backend.
- **Fly.io Sprites.** Fallback: microVM, durable files, idle is free, but no shared snapshot start and concurrency bought by plan.
- **ECS RunTask per conversation for AWS CDK.** Rejected: start time and per-task cost are worse than one shared Docker host.
- **sbx.** Parked: it adds a second runtime without a need stock policy leaves unmet. See [ADR-049](ADR-049-self-host-chat-sandbox-stock-docker.md).
- **Moving a sandbox between SHA-keyed records (the patched transition hooks).** Rejected in favor of option D, which needs no patch.
- **Pinning a conversation to its start commit.** Rejected: the agent would read stale knowledge.
