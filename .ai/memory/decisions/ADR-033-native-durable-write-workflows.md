# ADR-033: Native durable write workflows

**Status:** Accepted | **Date:** 2026-09-08 | **Tags:** git, openworkflow, workspaces, credentials

## Context

The accepted recovery plan's Gate 3 replaces the generic write runner, agent choreography and GitHub per-file commit exception. The locked ingest protocol still requires one concern per job, at most one commit, actual-default-branch writes, GitHub-only v1 write policy, semantic conflict resolution, paused-current-binding resume, and hydrate after push. The implementation must survive worker and filesystem loss without a second scheduler or sandbox lifecycle.

## Decision

- OpenWorkflow owns execution and retry. Each job kind has a typed registered workflow with explicit acquire, transform, stage, validate, commit, push-admission/broker, and publication steps. Ordinary pure transforms and native Git primitives can be shared; no second runner state machine is introduced.
- Deterministic transforms run against captured immutable Git data. They do not execute repository code or need an agent sandbox. The semantic conflict operation retains the isolation required by the locked ticket; no push credential enters it.
- Durable step data contains native Git objects and their immutable identity, not a worker-local directory or credentials. A shallow Git pack plus its native shallow boundary restores the acquired tree without full-history fetches. Each step may reconstruct and remove a disposable directory. Commit subject and timestamp are durable inputs so reconstruction creates the same commit.
- Completed export/extraction jobs retain their imported-object-to-Git-path assignment as durable command-result metadata. Later extraction may reuse that assignment only within the same workspace binding and while the target file exists in the acquired Git tree; file content and serving identity remain Git-owned. This prevents import-key cleanup from allocating duplicates on identical extraction.
- Extraction captures source objects, completed path assignments and migration cutover in one short repeatable-read PostgreSQL transaction. Completion atomically merges assignment metadata into one tenant-isolated row per workspace binding, serialized by the existing workspace row. Runtime reads retrieve that compact projection without traversing job history; the owner migration backfills existing completed results after the native workflow schema is available and before workers start. Historical ordering uses the matching native run completion time, falling back to immutable admission time when execution history is unavailable; mutable job update timestamps never rank assignments. This metadata remains separate from the hot workspace row and from Git-owned content. Repeated completion cannot replay old assignments over newer results. Completed export/cutover and existing export-intent lookups are scoped to the current generation, URL, connection and default branch. Import-key cleanup requires that binding’s completed export before acquisition. The export parent reads committed current files and durably reserves bootstrap/import-key follow-ups through the same capped per-concern planner, including completed replay.
- Overlapping text conflicts use an OpenWorkflow-owned TanStack provider resource with explicit plan, create, resolution and destruction steps. Provider selection and resource identity are durable before allocation; retries cannot switch providers after a lost creation acknowledgement. A bounded structured model result may replace only the conflict paths; native Git retains clean merged changes and the broker alone can publish. Mechanical transforms do not share this resource or a registry. Docker resources have a stable native container name via the pinned provider patch. That patch also honors the native create/resume abort signal across allocation calls. A planned resource has a two-minute deadline; model calls and provider allocation share that deadline. Before allocation, a separate native cleanup workflow is scheduled durably for expiry and confirms destruction after the in-flight request window. Cancellation or loss of the creating worker does not cancel this cleanup, and an expired locator cannot recreate a resource.
- A raced mechanical command delegates its exact unpublished Git delta to a native semantic child under the same job identity. The parent remains the single job/result owner; immutable handoff metadata admits only that delta and permits replacing its unpublished candidate. The child does not create a second completed job for the same change. A further native compare-and-swap race releases only the exact unpublished candidate, refreshes the revision and retries the merge up to three times, preserving one original job/result identity. It durably schedules canonical hydration even when conflict resolution preserves the current tree, except that migration export retains hydration admission in its parent: export completion must atomically project path assignments first. The export parent runs its durable hydration tail even when replay finds an already completed command.
- Job status reconciles terminal owning OpenWorkflow state in a short org SQL query, filtered by org, workspace and job identity. Native step retries remain running; no workflow catch block guesses whether a retry is terminal.
- The job-to-commit mapping is recorded before push; completed status follows successful publication. A retry checks the actual remote for the recorded commit before doing another write. Push failures do not revert Git. Hydration uses the canonical default revision containing the committed change and retries independently. A result already present on that default can complete even if write access has since become read-only; no new write credential is issued. Native ancestry recovers a lost push acknowledgement even when a subsequent writer has advanced the tip; completion requires a durable hydrate enqueue.
- Only the workflow's brokered push step obtains a repository-scoped write credential. Sandbox and codesearch consumers receive read credentials. GitHub feature-branch configuration PRs and conversation session branches remain supported, with explicit default-branch exclusion.
- Hydration captures its original planning requirement, previous revision and raw committed Markdown in native durable steps. After activation it reserves one typed maintenance intent per concern in a short PostgreSQL transaction. Job metadata carries the originating SHA, attempt and pre-write remainder across job-produced revisions; each kind stops at three attempts or a non-shrinking remainder, independently of other kinds. Replayed reservations retain their job identity. A queued job may still acquire its captured SHA after another job advances the same binding; the broker owns current-tip reconciliation.
- Broker admission reads revision and write status from the same PostgreSQL row version. Remote permission results use a compare-and-swap over generation, URL, connection, default branch and desired SHA before changing that row; a stale result cannot resume commands after relink. Final binding validation cannot combine an earlier revision with a later writable row after relink.
- Admission binds and queues every typed kind even while write access is unavailable, so a paused command has a native execution owner; unsupported non-GitHub targets are rejected before persistence. HTTP Files acceptance waits for this durable enqueue. Each typed workflow explicitly waits through native one-minute sleeps when acquisition or broker push reports unavailable write access. Its command, native owner and any prepared commit remain unchanged. A recognized default-branch protection or permission denial records the binding-fenced read-only reason; the next write intent or periodic permission probe can restore access. A paused command retains its captured tree when the same binding advances, leaving reconciliation to the broker. Protection never triggers a semantic child, force push or workaround PR. Semantic children may resume while their parent job is paused. Default protection does not revoke session-branch editing/publishing: conversation policy recognizes that specific reason, while actual repository permission denial remains read-only. Workspace API responses carry the derived conversation capability so UI controls do not interpret diagnostic prose.
- Connector parent workflows capture the bound target revision before fetching provider content, persist only content and non-secret metadata, and call the typed mirror with native `step.runWorkflow`. Native child suspension is control flow, so no outer catch may interpret it as terminal failure. Linear, Notion, Confluence and Slack parents implement this boundary. Mirror commands carry the captured config blob identity (including absence), which native acquisition, no-op/semantic reconciliation and broker publication validate. A changed config discards the stale capture instead of semantically rebasing its old scope. Slack model tools select capture intent only; deterministic provider capture and native publication have separate steps, and success is posted after the child completes. Connector finalizers compare the captured repository and branch under a row lock or update predicate; an old push cannot mark a newly rebound target live. Slack reads the owning native failed workflow-step projection to publish a terminal child failure and fallback reply while rethrowing nonterminal suspension unchanged. Full connector generation/config/provider finalization and setup failure projection remain required before acceptance.
- Preserve short org SQL transactions (ADR-027/028); no SQL connection or transaction is held across Git, provider, or model I/O. Full binding identity is checked immediately before push, and native Git rejects non-fast-forward updates. Never rewrite default-branch history or create a protection-workaround PR.

This implements the recovery plan's explicit replacement of ticket 10's generic runner, shared sandbox for mechanical jobs, and mechanical GitHub API exception. It preserves its product behavior and semantic-conflict isolation rather than applying the old orchestration literally.

## Consequences

Worker restart can reconstruct a job's Git artifacts. Durable packs add storage proportional to the acquired tree; they contain repository data but no credentials. Step identities, command admission, remote uncertainty, per-kind retry bounds, and every former default writer require native acceptance proof before Gate 3 closes.
