# ADR-033: Native durable write workflows

**Status:** Accepted | **Date:** 2026-09-08 | **Tags:** git, openworkflow, workspaces, credentials

## Context

The accepted recovery plan's Gate 3 replaces the generic write runner, agent choreography and GitHub per-file commit exception. The locked ingest protocol still requires one concern per job, at most one commit, actual-default-branch writes, GitHub-only v1 write policy, semantic conflict resolution, paused-current-binding resume, and hydrate after push. The implementation must survive worker and filesystem loss without a second scheduler or sandbox lifecycle.

## Decision

- OpenWorkflow owns execution and retry. Each job kind has a typed registered workflow with explicit acquire, transform, stage, validate, commit, push-admission/broker, and publication steps. Ordinary pure transforms and native Git primitives can be shared; no second runner state machine is introduced.
- Deterministic transforms run against captured immutable Git data. They do not execute repository code or need an agent sandbox. The semantic conflict operation retains the isolation required by the locked ticket; no push credential enters it.
- Durable step data contains native Git objects and their immutable identity, not a worker-local directory or credentials. A shallow Git pack plus its native shallow boundary restores the acquired tree without full-history fetches. Each step may reconstruct and remove a disposable directory. Commit subject and timestamp are durable inputs so reconstruction creates the same commit.
- Completed export/extraction jobs retain their imported-object-to-Git-path assignment as durable command-result metadata. Later extraction may reuse that assignment only within the same workspace binding and while the target file exists in the acquired Git tree; file content and serving identity remain Git-owned. This prevents import-key cleanup from allocating duplicates on identical extraction.
- Migration export captures legacy source objects, completed path assignments and migration cutover in one short repeatable-read PostgreSQL transaction. Completion atomically merges assignment metadata into one tenant-isolated row per workspace binding, serialized by the existing workspace row. Runtime reads retrieve that compact projection without traversing job history; the owner migration backfills existing completed results after the native workflow schema is available and before workers start. Historical ordering uses the matching native run completion time, falling back to immutable admission time when execution history is unavailable; mutable job update timestamps never rank assignments. This metadata remains separate from the hot workspace row and from Git-owned content. Repeated completion cannot replay old assignments over newer results. Completed export/cutover and existing export-intent lookups are scoped to the current generation, URL, connection and default branch. Import-key cleanup requires that binding’s completed export before acquisition. The export parent admits hydration only after completion and path assignment publication. Successful hydration reads committed current files and durably reserves bootstrap/import-key follow-ups through the same capped per-concern planner, including no-op hydration after completed export replay. Export passes a read revision to hydration; a write revision would be discarded by its binding check.
- Overlapping text conflicts use an OpenWorkflow-owned TanStack provider resource with explicit plan, create, resolution and destruction steps. Provider selection and resource identity are durable before allocation; retries cannot switch providers after a lost creation acknowledgement. A bounded structured model result may replace only the conflict paths; native Git retains clean merged changes and the broker alone can publish. Mechanical transforms do not share this resource or a registry. Docker resources have a stable native container name via the pinned provider patch. Bun 1.4.2 is the runtime floor: a native Docker exec probe fails on Bun 1.3.11 HTTP upgrade handling; allocation-acknowledgement and in-model SIGKILL recovery pass on 1.4.2 with two replacement workers and independently completed expiry cleanup. That patch also honors the native create/resume abort signal across allocation calls. A planned resource has a two-minute deadline; model calls and provider allocation share that deadline. Before allocation, a separate native cleanup workflow is scheduled durably for expiry and confirms destruction after the in-flight request window. Cancellation or loss of the creating worker does not cancel this cleanup, and an expired locator cannot recreate a resource.
- A raced mechanical command delegates its exact unpublished Git delta to a native semantic child under the same job identity. The parent remains the single job/result owner; immutable handoff metadata admits only that delta and permits replacing its unpublished candidate. The child does not create a second completed job for the same change. A further native compare-and-swap race releases only the exact unpublished candidate, refreshes the revision and retries the merge up to three times, preserving one original job/result identity. It durably schedules canonical hydration even when conflict resolution preserves the current tree, except that migration export retains hydration admission in its parent: export completion must atomically project path assignments first. The export parent runs its durable hydration tail even when replay finds an already completed command.
- Job status reconciles terminal owning OpenWorkflow state in a short org SQL query, filtered by org, workspace, job and typed workflow name/version. Native idempotency is name/key scoped; admission rejects a returned run from another version. Native step retries remain running; no workflow catch block guesses whether a retry is terminal.
- The job-to-commit mapping is recorded before push; completed status follows successful publication. A retry checks the actual remote for the recorded commit before doing another write. Push failures do not revert Git. Hydration uses the canonical default revision containing the committed change and retries independently. A result already present on that default can complete even if write access has since become read-only; no new write credential is issued. Native ancestry recovers a lost push acknowledgement even when a subsequent writer has advanced the tip; completion requires a durable hydrate enqueue.
- Conversation publication captures its sandbox handle together with URL, connection, generation, SHA and default metadata. A fresh backend Git directory fetches the common base directly, then imports a thin delta in bounded chunks. Restored shallow session branches use their locally present remote session tip as the exclusion; an unchanged published tip can proceed to PR creation without another push. After a quiet rebase, the captured default can supply the common ancestor while the remote session tip remains the force-with-lease expectation. Publication fails closed if neither base is locally available. No GitHub write credential enters agent execution. PR/branch SQL projection locks the matching binding, and saved GitHub PR numbers carry their workspace revision. Read projections hide old or unbound numbers after relink, serialize through the declared API schema and pair PR URLs with their saved revision. GitHub PR reads must match the conversation branch and recheck that binding before responding. Historical numbers remain unbound after the nullable generated migration; they are never guessed onto the new repository.
- Only the workflow's brokered push step obtains a repository-scoped write credential. Sandbox and codesearch consumers receive read credentials. GitHub feature-branch configuration PRs and conversation session branches remain supported, with explicit default-branch exclusion.
- Hydration captures its original planning requirement, previous revision and raw committed Markdown in native durable steps. After activation it reserves one typed maintenance intent per concern in a short PostgreSQL transaction. Job metadata carries the originating SHA, attempt and pre-write remainder across job-produced revisions; each kind stops at three attempts or a non-shrinking remainder, independently of other kinds. Replayed reservations retain their job identity. A queued job may still acquire its captured SHA after another job advances the same binding; the broker owns current-tip reconciliation.
- Broker admission reads revision and write status from the same PostgreSQL row version. Remote permission results use a compare-and-swap over generation, URL, connection, default branch and desired SHA before changing that row; a stale result cannot resume commands after relink. Final binding validation cannot combine an earlier revision with a later writable row after relink.
- Admission binds and queues every typed kind even while write access is unavailable, so a paused command has a native execution owner; unsupported non-GitHub targets are rejected before persistence. HTTP Files acceptance waits for this durable enqueue. Each typed workflow explicitly waits through native one-minute sleeps when acquisition or broker push reports unavailable write access. Its command, native owner and any prepared commit remain unchanged. A recognized default-branch protection or permission denial records the binding-fenced read-only reason; the next write intent or periodic permission probe can restore access. A paused command retains its captured tree when the same binding advances, leaving reconciliation to the broker. Protection never triggers a semantic child, force push or workaround PR. Semantic children may resume while their parent job is paused. Default protection does not revoke session-branch editing/publishing: conversation policy recognizes that specific reason, while actual repository permission denial remains read-only. Workspace API responses carry the derived conversation capability so UI controls do not interpret diagnostic prose.
- Connector parent workflows capture the bound target revision before fetching provider content, persist only content and non-secret metadata, and call the typed mirror with native `step.runWorkflow`. Native child suspension is control flow, so no outer catch may interpret it as terminal failure. Linear, Notion, Confluence and Slack parents implement this boundary. Mirror commands carry the captured config blob identity (including absence), which native acquisition, no-op/semantic reconciliation and broker publication validate. A changed config discards the stale capture instead of semantically rebasing its old scope. Slack model tools select capture intent only; deterministic provider capture and native publication have separate steps, and success is posted after the child completes. Connector finalizers compare the captured workspace generation, URL, GitHub connection, default branch, repository binding and provider workspace/cloud identity under short row locks; an old result cannot mark a different target live. Slack reads the owning native failed workflow-step projection to publish a terminal child failure and fallback reply while rethrowing nonterminal suspension unchanged. Each config proposal claim, config activation or explicit content retry advances a connection counter independent of credential refresh; full-content inputs and captured finalization carry that counter. Current native failed/canceled owners project setup failure on status reads. Content admission creates a generation-scoped native owner before publishing initial_sync. The owner ID and non-secret target/provider binding are persisted; the workflow repeats activation as its first durable step, recovering an admission-process crash. Repeated config events reuse the current owner while A–B–A changes get distinct generations. A lost enqueue response checks the native idempotency key before reporting failure. Generation-zero compatibility applies to old persisted inputs and cached capture results. Config workflows retain their captured binding, reject a newly loaded target mismatch after restart, recheck the admitted binding before provider synchronization, and perform explicit durable config publication/admission steps; unchanged config admits full content work for every provider. Setup reads project terminal config failures only for the captured binding and current generation. Provider identity replacement advances the counter, including legacy Forge owners. A failed older owner cannot change a newer activation. Directory projection re-reads and locks the current connection in the same SQL transaction as the directory update, so delayed callers cannot restore stale provider identity. Config proposals use the same owner-before-state protocol and repeat activation in their first native step; their scope selection is immutable native input. Failed enqueue leaves setup unchanged. Config PR finalization compares activation generation under a row lock. Failed/canceled owners are projected even before their first capture step; a delayed API activation can acknowledge a completed proposal without rewinding its child. Replaying generation-zero config owners recover only their own missing content admission. Completed legacy no-change owners use an explicit one-organization/listed-connector preview/apply recovery command (maximum 100 connectors); no global automatic migration enqueue is performed. Native finalization and admission cases cover reordered equivalent config, A–B–A generations, late owners, and provider replacement.
- Preserve short org SQL transactions (ADR-027/028); no SQL connection or transaction is held across Git, provider, or model I/O. Full binding identity is checked immediately before push, and native Git rejects non-fast-forward updates. Never rewrite default-branch history or create a protection-workaround PR.

This implements the recovery plan's explicit replacement of ticket 10's generic runner, shared sandbox for mechanical jobs, and mechanical GitHub API exception. It preserves its product behavior and semantic-conflict isolation rather than applying the old orchestration literally.

- Extract write commands carry a validated immutable extractor batch and never load content from projection tables. Only the one-time migration export reads legacy content. Extraction may read completed path identity and migration cutover metadata. Repository producer handoff now executes the real owner/index/root/extractor pipeline into a captured typed Git write; native contracts verify its instruction claim and one commit. In-flight source indexing retains the newer published files/search while an older clone finishes afterward. Git retraction has separate native capture and publication contracts.
- Configuration proposal and config-push content admission identity follow canonical provider selection semantics; list order and equivalent all-page selections do not start a new generation, while A–B–A changes do. Lifecycle storage uses provider schemas, including defaults. Superseded Notion/Confluence PR cleanup has its own durable step after a failed finalization CAS; this prevents an old owner from leaving an actionable stale proposal.

- An uncertain workspace enqueue reconciles the accepted native owner and captured command before reporting failure; recovered admission wakes the worker and returns the same acknowledgement. A rejected INSERT remains retryable without manufacturing an accepted command.
- A source refresh publishes its serving revision only when both Zoekt and SCIP complete. A search failure records its issue while preserving the prior `lastIngestedHash`, timestamp and readiness; the first failed index remains unready. Graph tools default to the authenticated captured source or current published checkout, and captured extraction cannot override that scope with a tool argument.

## Consequences

Worker restart can reconstruct a job's Git artifacts. Durable packs add storage proportional to the acquired tree; they contain repository data but no credentials. Step identities, command admission, remote uncertainty, per-kind retry bounds, and every former default writer require native acceptance proof before Gate 3 closes.

### Repository extraction producer increment

Repository ingestion captures the destination before extracting and passes its immutable output to the typed native extract child. It no longer mutates extracted objects, claims, Falkor or embeddings before Git publication; the retired LangGraph writer and its DB-write nodes are removed. Duplicate observations are merged in encounter order before persistence, preserving richer payloads when a consumer-inferred stub follows them. A pure extraction adapter resolves repository references to existing AGENTS.md or linked declarations and resolves known path identities against the acquired Git tree. Native captured-history replay proves publication after worker restart; it does not stand in for a live extractor journey. Canonical retraction, source declaration fences, bounds and remaining terminal-owner recovery are still acceptance work.

Linked extraction captures the first canonical declaration's path and Git blob before model work. Every acquisition and reconciliation validates that authority. Broker publication validates the original captured blob at the parent revision, then allows only claims metadata edits to that same canonical declaration; URL, branch, customer metadata/body and canonical path cannot change. The linked remote is never written; semantic handoffs retain the same immutable extraction identity. Source removal or branch/declaration edits reject the old capture rather than rebasing stale knowledge. The final command and each root capture are bounded to 8 MiB, 10,000 objects and 50,000 claims. Pure connector input schemas are separated from runtime binding readers to avoid admission import cycles. Retired graph reducers/channels and extraction DB-write APIs have no runtime compatibility path; historical database data is seeded only by test support for migration proof.

Extraction retraction is a Git transform over captured full/partial source scope and index observation time. It expires absent in-scope claims, preserves unrelated or unidentified evidence and owner prose, and uses the captured observation time when an expired claim is reasserted. Concrete provenance paths become canonical source links. Knowledge may retain owner-selected paths outside knowledge/; connector mirrors remain excluded. Repository-subject claims may update AGENTS.md metadata through the same owner-preserving merge; claims-only extraction edits the original YAML metadata while preserving the instruction body bytes, including whitespace and final newlines. Root capture is capped at 128 roots of at most 4096 characters, with two concurrent roots and aggregate output validation between batches. Historical oversized captures fail before fan-out.

Repository ingestion admission stores one current immutable request per repository before native enqueue; queued status is published only after OpenWorkflow accepts that key. A native first-step activation recovers API loss. Readers join the bounded current request to its native owner instead of folding historical runs or requiring a failure callback. Progress and extraction publication validate that request and source binding. A legacy child recovers request identity through persisted native parentage. A migration-only metadata backfill adopts legacy orchestrators without starting work or replacing current requests. Follow-up admission is awaited and keyed by the preceding request, allowing the native callback to retry transport uncertainty without spawning duplicate successors. Distinct claim-source histories retain separate YAML entries; URL path encoding and directory overlap preserve correct retraction scope.


Source indexing uses commit-specific repository checkouts through the existing cache and index path helpers. A source JWT authorizes only its captured repository and SHA, separately from workspace projection authority. The existing lastIngestedHash selects published immutable artifacts for ordinary file, structural, graph and lexical reads, with a fallback to the pre-upgrade default checkout only when no matching immutable artifact exists. Finishing an older index cannot replace the published commit's checkout, Zoekt or SCIP files. Extraction callbacks carry their captured source revision through a small async read context into every explorer tool; this context owns no execution or resource lifecycle. Native workflow inputs remain authoritative across restart. Immutable phase workers do not update canonical repository progress; the owning ingestion workflow performs request-fenced progress updates. Legacy native parentage can recover the same request through the producer/index child chain. A default-branch selection remains unspecified on follow-up so a changed remote default is re-resolved, while explicit branch selection remains explicit.

Repository creation and connector configuration wait for native ingestion admission before responding successfully. If native admission fails after repository persistence, the route returns a retryable error and the next request reuses the saved repository. Existing extracted subjects can receive claims without a duplicate object payload, retaining owner paths and prose. Evidence identity normalizes equivalent relative and repository URL paths before merging claims, including dot segments and repository-root paths.

Native connector and repository-ingestion ownership lookups consistently require the production default namespace, expected workflow name, and unversioned workflow spec. The same identity checks apply to returned handles, fallback key recovery, persisted pointers, activation, terminal projection, and upgrade recovery. A foreign namespace or version cannot activate setup, change repository readiness, or be adopted as a legacy owner. Tests that exercise these production ownership paths explicitly select that namespace; isolated namespace fixtures remain available for unrelated workflow tests and negative cases.

A semantic handoff committed before its native step reply is replayed from its persisted revision and delta. Recomputing after another tip advance may validate the current binding, but must not replace that handoff. The same owner/candidate/files/deletions must still match; the child owns later Git reconciliation. Pre-upgrade paused/queued intents with no native owner or prepared commit adopt their separately stored original SHA into the revision payload once, under the existing URL/generation/default checks.

An unborn Git repository has a bootstrap write binding (workspace/generation/remote/default branch), separate from WorkspaceRevision, which always requires a real commit. The same workspace-write-bootstrap workflow stages and validates a native root tree, creates its first real commit without a parent, records its candidate, and uses the broker for a normal non-force push. No fictional read SHA, seed README, GitHub auto_init or second workflow owner is introduced. Native Git clone resolves the unborn symbolic HEAD; credentials remain transient. Only the committed Git result may become a read revision and enter hydration. Completion and admission recovery retain the immutable pre-commit binding. If a human initializes the default branch first, the same owner durably adopts that real revision and continues the normal bootstrap transform; the unpublished root candidate is discarded. A verified unborn read returns no revision and preserves the empty serving store without a hydration failure. Create/select dispatches bootstrap independently of migration export and hydration. Native contracts cover empty hydration, first-writer preservation, changed permissions/generation/default during credential issuance, and SIGKILL after the first push before its reply reaches the owner; replacement workers recover one root commit.

The obsolete shared job sandbox creation/cloning/claim path is retired. Workspace Files status describes the immutable published revision. Conversation handle compatibility and pre-upgrade resource destruction remain until Gate 4 replaces their owner.

Root `AGENTS.md` and captured linked declarations share the final broker claims-only authority check against the acquired parent revision, including model-resolved conflicts. Body bytes and all non-claims metadata remain unchanged before write credentials and at the final push fence. The superseded generic intent/start/attempt model APIs are removed; typed native command persistence is the remaining writer.
