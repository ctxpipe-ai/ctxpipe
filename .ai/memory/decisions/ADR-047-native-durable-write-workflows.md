# ADR-047: Durable write workflows

**Status:** Accepted (revised 2026-10-06; amended 2026-10-13 by [ADR-052](ADR-052-ingestion-sandbox-skills-patches.md); amended 2026-11-09 by CTX-1235) | **Date:** 2026-09-08 | **Tags:** git, openworkflow, workspaces, credentials

## Context

ctxpipe writes to the Workspace repository on the user's behalf: connector mirrors, extraction, imports, renames, link/unlink, ops folder maps, claim upgrades, file edits and bootstrap. These writes must survive worker loss, never force-push, never clobber concurrent human commits, and publish at most one commit per job. A generic write runner with agent choreography and per-file GitHub commits was replaced.

## Decision

- **One typed OpenWorkflow workflow per job kind** (`apps/backend/src/openworkflow/workflows/workspace-*.ts`): acquire → transform → commit subject → prepare commit → broker push → hydrate. OpenWorkflow owns retry; there is no second runner or scheduler.
- **Transforms are deterministic** over captured, immutable git data. They never run repository code and do not need a sandbox.
- **Durable step data is git, not a directory, and not Git objects.** Steps carry commit SHAs and the target revision ([ADR-046](ADR-046-workspace-revision-projection-identity.md)); any worker fetches the commits from the Git host into a disposable directory. Commit subject and timestamp are inputs, so a replayed step makes the same commit. Credentials are issued per push and never stored in step data. See the 2026-11-09 amendment.
- **The write broker is the only pusher** (`write-broker.ts`). It checks the job's binding and the claims-only authority rule for `AGENTS.md` and linked declarations, then does a normal non-force push to the actual default branch. A successful push triggers hydrate with a read revision.
- **Concurrent tips:** when the default branch moved, the unpublished delta is replayed on the new tip. Overlapping text conflicts go to a `workspace-semantic-merge` child. It asks a model to resolve only the conflicting paths, in one schema-checked model call whose output native git stages. It uses no sandbox, and no credential goes to the model (ADR-048 Consequences; `semantic-merge.ts`).
- **Bootstrap** of an empty repository makes a real root commit through the same broker; if a human initializes the branch first, the job adopts that commit.
- **Ownership** of a run is scoped to the process OpenWorkflow namespace (`default` in production, `preview-pr-N` on previews) plus workflow name and version, so previews never adopt production work.
- **Extraction captures are stored by reference.** Each `identify:<root>` step of `repository-ingestion` writes the paid extractor output of its root to `repository_extraction_captures` (one row for each root) and returns only counts. The extraction command in the workflow input and in the write-job payload carries the source header and the capture key, not objects and claims. The transform step of `workspace-write-extract-ingest` reads the rows and builds the publishable capture. There is no size cap on a capture. The workflow input, the write-job payload, and the `identify` step outputs stay small for any repository size. The `transform` step output still grows with the capture, because one in-memory plan publishes it (ticket 14, option C is not built). Since CTX-1235, the commit steps hold only a SHA.
- **Paid roots are reused across runs.** The capture key is repository, target commit, scope (`full`, or `since:<base>` for a partial ingest), extractor version, and root. A new run with the same key reads the stored root and makes no model calls, so a failure after extraction does not make the next run pay again. Increase `EXTRACTOR_VERSION` when an extractor changes its output. A root whose extractors skipped files after a model error is not reused, and its run publishes no retraction. A capture that does not parse is deleted; a plan error or a database error keeps it. A full re-index reuses no root. After a successful publication, the parent deletes the rows of its own key and the rows stored before its run started, so a run that waits for write access keeps the rows of a newer run. The foreign key deletes the rows with their repository.
- **Amendment (2026-10-13, [ADR-052](ADR-052-ingestion-sandbox-skills-patches.md)):** a new job kind, the **ingest ref push**, lets the broker push to the run-scoped refs `refs/ctxpipe/ingest/<runId>/…` of the job's run in the job's Workspace repository. It is non-force (the push names the expected old tip), it runs the ingestion validator again, and it starts no hydrate, no CAS activation, and no default-branch change. When the sandbox-skill pipeline publishes (ADR-052 phase 4), the extraction input of `workspace-write-extract-ingest` is the tip commit of the run's assembled ref, not a capture key: the transform replays the delta from the pinned revision to that tip on the current default tip. Then the two capture items above (captures by reference, paid-root reuse by `EXTRACTOR_VERSION`) are superseded, and ADR-052 phase 5 deletes `repository_extraction_captures`.
- **Amendment (2026-11-09, CTX-1235): a step output holds a commit SHA on a job ref, never Git objects.** OpenWorkflow stores each step output in `openworkflow.step_attempts` and reads all outputs of a run again on each claim. The `stage`, `commit`, and merge steps returned a Git pack, and production stored about 150 GB of packs (CTX-1232). Now:
  - One step (`prepare-commit`; `prepare-merge-commit` for a semantic merge; `prepare-commit-unborn` for bootstrap) stages, validates, and commits in one disposable directory. It pushes the commit to the job ref `refs/ctxpipe/write/<jobId>/<sha>` in the Workspace repository, records the SHA on the job, and returns only `{ sha, tree, root, base }`. `commit-subject` runs before it on file names only.
  - The broker is the only pusher of a job ref. The job names a Workspace, never a URL; the admission reads the URL from the Workspace row and checks that the job is a job of that Workspace. The SHA is in the ref name, so a push never forces and a ref never moves: a replay pushes the same ref again, and a second execution of the run cannot replace it. The GitHub webhook ignores `refs/ctxpipe/*`. While the Workspace has no write access, the step pauses the job, as `broker-push` does.
  - Each later step (`broker-push`, `publish-result`, `capture-semantic-handoff`) fetches the commit and its parent from the Git host by SHA.
  - The semantic merge folds the merge, the model resolution, and the commit into `prepare-merge-commit`. A model can answer differently on a replay, so the step first returns the commit that the job already recorded, when the Git host has it on its job ref or on the default branch.
  - The `complete` step deletes the refs of its job, and the Workspace tip check deletes the refs of completed and failed jobs (and the refs of an unknown job after 7 days), next to the ingest ref clean-up.
  - `transform-connector-mirror-v2` returns paths only; the file contents are in the workflow input.
  - Each changed step got a new name (for example `acquire-revision-v2`), so no code reads a retired output again, and a run that was in progress at the deploy computes the new steps again. The retired names are in the CTX-1235 pull request; CTX-1236 clears their stored outputs. Steps with a small output (`commit-subject`, `broker-push`, `publish-result`) keep their names, so a run in progress keeps the push that it made.
  - A transform output still holds the content of the files that it changes, and `capture-semantic-handoff` holds the delta of a raced push. Both grow with the change, not with the repository.
- **Writes are GitHub-only in v1.** Path assignments for imported objects are kept per Workspace binding so repeated extraction reuses paths instead of duplicating files.

## Consequences

- Worker or filesystem loss resumes from the last step; reruns do not double-commit.
- A write step output is a few hundred bytes for any repository size. Each step that reads a commit fetches it from the Git host again, and a write needs a write credential before its broker push (for the job ref). A failed run can leave job refs in the Workspace repository until the next tip check.
- Every write is a normal commit on the default branch, visible in history and attributable.
- No write job uses a sandbox, also semantic merge ([ADR-048](ADR-048-native-postgres-sandbox-ownership.md)).
- A very large capture is still published as one commit from one in-memory plan; the worker memory limits its size (ticket 14, option C).
