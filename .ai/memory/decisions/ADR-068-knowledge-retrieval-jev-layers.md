# ADR-068: Knowledge retrieval: one hybrid search, Jev judges each layer, disagreements are reasoned at query time

**Status:** Accepted (the CTO, 2026-11-19; the code does not implement it yet; the evals of [ADR-069](ADR-069-knowledge-plane-evals-and-rollout.md) tune it) | **Date:** 2026-11-19 | **Tags:** knowledge, retrieval, search, graph, jev, embeddings, images, mcp

## Context

Today, `get_related` expands the graph with one Cypher query for each hop (`graph-expand.ts`). Then `graph-relevance.ts` ranks the result with these signals:

- static predicate weights;
- confidence and recency decay;
- a hub penalty;
- personalized PageRank;
- MMR.

These signals estimate relevance from the shape of the graph, because the system had no semantic signal ([ADR-051](ADR-051-mcp-read-surface.md) decision 6). Disagreements are only weights, for example `SUPERSEDES` ([ADR-033](ADR-033-graph-ontology-v2.md)).

Jev 1.14 (TypeSafe, through the OpenRouter Decisions endpoint) answers typed questions with probabilities. It takes about 100 ms for a text call. The visual critic uses it ([ADR-063](ADR-063-visual-critic-decides-with-jev.md)).

Disagreement resolution is part of the value of the product. Two items can disagree in part, and only for some questions.

The content and its tables are in [ADR-066](ADR-066-knowledge-content-in-clickhouse.md).

## Decision

1. **One hybrid search for every Workspace size,** so that one test and one eval cover all sizes:
   - **Vectors:** each text chunk stores a full vector of the text model (decision 5; about 1024 dimensions, `BFloat16`) and a binary form (1 bit for each dimension). There is one vector space. An image has no vector: the search finds it through the text that ingest writes for it (decision 6).
   - **Stage 1:** scan the binary vectors of the Workspace's chunks (Hamming distance) and keep the top 500.
   - **Stage 2:** score those 500 again with the full vectors (cosine distance).
   - **One query for both stages.** The chunks table uses `index_granularity = 64`, and the query lets ClickHouse read the full vectors of the 500 rows only (lazy materialization). The file cache uses `boundary_alignment` of 128 KiB. Without these settings, stage 2 read almost all full vectors of the Workspace. Measured on 1 million chunks in one Workspace ([CTX-1391](https://linear.app/ctxpipe/issue/CTX-1391), S3 on the same host): p50 34 ms and p95 45 ms warm, p50 126 ms and p95 209 ms cold. The PoC measures the cold path again on real S3.
   - **Lexical:** the text index selects the chunks that have a query term (`hasAnyTokens`). The score finds the matched terms with one `hasToken` filter for each term (`UNION ALL`), adds the weight of each matched term for each chunk (see **Term weight**), and adds a boost for a title match. A text function in the `SELECT` list reads the full text column (128 MiB on the test corpus), so the score does not use one. The count query read 12 MiB ([CTX-1391](https://linear.app/ctxpipe/issue/CTX-1391)). A cap applies before the score.
   - **A fixed order before each cut** (decided by the lead, 2026-11-23, [CTX-1547](https://linear.app/ctxpipe/issue/CTX-1547)). The cap of 1000 chunks for each term takes the chunks in the order of a hash of their key, and the Hamming cut at 500 decides between equal distances by the key. The lexical score is rounded to 9 decimals, because a parallel sum adds the weights in another order on each run. Before, each cut took the chunks that the parallel read gave first. Thus the same search gave other hits on each run. Two live runs of the same code had the same search hits for 0 of 82 questions. On the question set v0, the hash order gave a search recall@50 of 0.720 (dev) and 0.718 (holdout), against 0.732 and 0.718 with no order. The order of the key gave 0.711 and 0.707. The store search of the v0 questions took the same time (p50 about 830 ms against 860 ms, store only). With the order, a term branch reads the key of each chunk that has the term before the cap, not only the first 1000. Nobody measured that again on 1 million chunks: the evals on the scale corpus must measure it.
   - **Term weight** (decided by the lead, 2026-11-22, [CTX-1455](https://linear.app/ctxpipe/issue/CTX-1455)): each matched term adds its BM25 IDF, not 1. The title boost adds 4 times the same weight for each query term in the title of the document (2026-11-23, [CTX-1564](https://linear.app/ctxpipe/issue/CTX-1564)). On the question set v0, the title weight 4 gave a search recall@50 of 0.764 (dev) and 0.736 (holdout), against 0.720 and 0.718 with weight 1. The dev questions chose the weight: 2 gave 0.728, 3 gave 0.740 and 5 gave 0.772. Above 4, each step added only one gold document, and a larger weight makes the lexical order more a title search. The IDF comes from the count of the chunks of the Workspaces that have the term. The text index gives this count without a read of the text column (38 KiB against 478 KiB for a text scan on the `.ai/memory` corpus). The counts do not apply the filters of the search, because a filter through the tree view made the lexical query cost 458 ms on 1 million chunks. With the counts as they are, the lexical query took 136 ms (p50, warm) against 127 ms before, and read 46 MiB against 41 MiB (`knowledgeSearchBenchmark`, 2026-11-22, on a loaded host).
   - **Fusion:** RRF (k = 60) orders the chunks. They are grouped by `active` document, each document at the place of its best chunk, and the top 50 documents are the hits. Each hit holds its best chunks, as many as the caller reads. The vector stage still keeps the 500 closest chunks, not the closest chunks of each document: `LIMIT n BY` document stopped the lazy read of the full vectors, and the vector query then read 2,239 MiB against 227 MiB and took 595 ms against 72 ms on 1 million chunks. Thus a document with more than 450 chunks closer than all other chunks can still leave the vector order with fewer than 50 documents.
   - **Fusion weight:** A place in the lexical order has a weight of 0.4 + 0.6 × s², where s is the share of the chunk (2026-11-23, [CTX-1564](https://linear.app/ctxpipe/issue/CTX-1564)). Before, each place had the weight 1. The share counts only the uncapped query terms: the terms in 1 to 1000 chunks of the Workspaces. The cap of a term branch never cuts such a term, so the share of a chunk is the summed weight of its uncapped terms over the summed weight of all uncapped query terms, with no extra read. A common term and a term that no chunk has do not count. As for the IDF, the counts do not apply the filters of the search. A query with no uncapped term gives each lexical chunk the share 1. The questions of the question set v0 are sentences with 40 to 80 terms, and they do not use the words of the titles. The top lexical chunks of these questions had only common words of them, and they took about half of the top 50. On the question set v0, with the title weight 4, the weighted fusion gave a search recall@50 of 0.829 (dev) and 0.793 (holdout), against 0.764 and 0.736 with the weight 1. With the title weight 1, it gave 0.829 and 0.759, against 0.720 and 0.718. The query vectors of two kept runs (run-ctx1548-live and run-ctx1547-live-a) gave the same numbers. A flat weight of 0.4 gave the same recall, but it took the first lexical document out of the top 50 for 15% of the questions, against 10% with the share (0% before). A chunk with all terms of a short query keeps the weight 1, so an exact term still finds a document that the vector order does not have. A share from all the terms of the matches, after the cap, gave the same recall on v0, but it gave a lower weight to a chunk with all terms when the cap of a common term did not take it. The dev questions chose 0.4: each flat weight from 0.1 to 0.4 gave 0.829 (dev), and 0.5 gave 0.797. The two levers add no query and no read: the store search of the 82 questions took p50 963 ms with both levers and 868 ms before (host load 22 to 27).
   - **Neighbors of the best hits** (2026-11-24, [CTX-1605](https://linear.app/ctxpipe/issue/CTX-1605)). After the fusion, the store search reads the relations of the first 5 hits in both directions, except `FROM_SOURCE`, as the walk of `get_related` with no named predicate (the relations of `readFrontier`). Each neighbor that is `active`, passes the filters of the search and is not a hit is a candidate. The 10 candidates closest to the query (their closest chunk) take the last places of the 50 hits. Thus Jev still judges at most 50 documents, and the search makes no model call more. The diagnosis on the dev questions of v0 and Backstage: of 30 gold documents that the search missed, none was missing from the store, none was cut by the cap of a term, and one was cut by the Hamming cut. Seven were in the top 50 of one order, and the fusion pushed them out. Twenty-two were in the top 50 of neither order. Twelve of these were the code document of an across-sources question (an issue that names a part of the code): the question has none of its words, and its exact vector rank was 200 or more. Each of the 12 was one relation (`MENTIONS`) from a hit of the top 50, and 8 from a hit of the top 5. With the recorded query vectors of the kept G10 runs, the search recall@50 of the dev questions went from 0.760 to 0.842 (v0 0.821 to 0.882, Backstage 0.620 to 0.750), and no dev gold document left the top 50. The dev questions chose the setting: neighbors of the top 10 with 10 places gave 0.845, and of the top 20 with 15 places gave 0.867, for 3 and 5 times more candidates. Feedback of the top chunks into the query vector (Rocchio) gave 0.799 alone and 0.850 with the neighbors, but it lowered the recall@10 of the search order from 0.585 to 0.571, so its latency was not measured. A larger pool before the judge gave 0.808 (60 hits) to 0.839 (150 hits) in the search order, for 20% to 200% more Jev candidates, and Jev must still put the gold in the top 50; the offline bench cannot measure that, so it was not built. The store search reads the neighbors (step 4 of `search`, CTX-1683): one query finds the neighbors that pass the filters of the search, then two reads by file version get their closest chunks and their documents. This read runs at the same time as the read of the documents and the texts of the hits. When the time budget ends during this read, the search gives its hits without neighbors. ClickHouse evaluates a CTE again at each use, so the query uses each CTE one time. On the eval store (v0 and v1, Backstage, 241 dev and holdout questions), it gives the same 50 hits as the first design (`readFrontier` of the 5 hits, then `readEvidence`), and the neighbors add 22 ms (p50) and 36 ms (p95) to the store search, against 165 ms and 190 ms. The first design made the dev search p95 of the corpora v1 go from 1540 ms to about 1700 ms; the rest of the rise in the live runs of G11 came from the embedding calls (their p95 went from 885 ms to 1258 ms and 1395 ms).
   - **Why the term weight and the cut at 50 documents** (decided by the lead, 2026-11-22, [CTX-1455](https://linear.app/ctxpipe/issue/CTX-1455)). Before this change, the fusion kept the top 50 chunks. In the `.ai/memory` eval, the long documents of a topic filled these 50 chunks: one ADR alone had 13 of them. Thus a search gave only 7 to 23 documents, and the old stack gave 34 to 50. The holdout lookup question lost its gold document at fused chunk rank 54. The count score gave "a", "is" and "for" the same weight as "MCP", and these words are in more than half of the chunks. With both changes, each search of the eval gives 50 documents, and the gold document of that question is document 28.
   - **No ANN vector index.** It filters badly for small Workspaces, and its index must load from S3 for cold parts. If very large Workspaces become too slow, we measure first and then decide.
2. **Jev judges each layer.** One Jev call for each layer asks two yes/no questions for each candidate:
   - **p(answers):** "does this help answer the question?" It gives the final order.
   - **p(explore):** "must the traversal explore from here?" It picks the next frontier.
   - **Rejected: a third question, p(states the answer), for the "no answer" of the search** (2026-11-26, [CTX-1685](https://linear.app/ctxpipe/issue/CTX-1685); #1137, then reverted). The search call also asked "does Candidate N state the answer to the question?" for each candidate. The search said "no answer" when no hit had a p(answers) of at least `keepAt` and a p(states the answer) of at least a threshold. Why it did not pass:
     - The scores on the recorded calls do not separate the questions. On the dev split of dataset v1 (12 no-answer questions, 62 answerable questions, generation 12), the top p(answers) of the no-answer questions was 0.15 to 0.84. The answerable questions with a gold document in the top 5 had a top p(answers) from 0.43. The rules on these scores were a threshold, the gap between the first two hits, the count of kept hits, and p(explore). Each such rule that said "no answer" more often lost a true answer, or had a margin of 0.02 or less. The 0.6 threshold of [CTX-1561](https://linear.app/ctxpipe/issue/CTX-1561) was such a rule, and it lost true answers on v1.
     - A replay run with live fallback recorded the new question on the dev split. The highest p(states the answer) of a kept hit was 0.17, 0.17, 0.37, 0.52 and 0.78 for the five no-answer questions with a kept hit. For the answerable questions with a gold document in the top 10, the lowest values were 0.14 (gold at rank 1), 0.36, 0.37, 0.39, 0.40 and 0.45. Thus no threshold said "no answer" more often with no loss of a true answer:
       - 0.14 or less: no change.
       - 0.15 to 0.35: up to two more correct "no answer" (corpora-v1 4/8 to 5/8, backstage-v1 3/4 to 4/4). The rule lost the gold at rank 1 (corpora-v1 recall@5 0.754 to 0.732, nDCG@10 0.755 to 0.734).
       - 0.4: three more correct "no answer" (6/8, 4/4), and the rule lost four true answers.
       - 0.5: the same correct "no answer" as at 0.4, and the rule lost eight true answers (backstage-v1 recall@5 0.688 to 0.469, corpora-v1 0.754 to 0.703).
       - These values compare with the run that asked the question. The question alone changed the order (see the next item).
     - The question alone (with no rule) changed the order a little, because Jev reads the other questions of a call: backstage-v1 dev recall@5 0.719 to 0.688 (one question), nDCG@10 0.653 to 0.669.
     - The question cost no Jev call and about 3% more input tokens. A Jev call with 50 questions had a p50 latency of 497 ms, and one with 1 question 430 ms.
   - **The seeds of `get_related` are always the first frontier** (decided by the lead, 2026-11-22, [CTX-1455](https://linear.app/ctxpipe/issue/CTX-1455)). The caller named the seeds to traverse from them, so p(explore) picks only the frontier after layer 1. In the `.ai/memory` eval, Jev gave two seeds a p(explore) of 0.35 and 0.47. Thus the loop read no relation and did not find the superseded ADR that each seed links to.

   Each candidate goes to Jev with its text and its metadata: status, source type, dates, validity and confidence. The questions ask only for relevance and for exploration. They do not tell Jev to weigh the metadata ([CTX-1418](https://linear.app/ctxpipe/issue/CTX-1418)). Code applies the status and the validity: the store reads only `active` documents, the layers of `get_related` read only rows that are valid at `validAt` (now by default), and a search hit that is not valid at `validAt` (or now) comes after the valid hits. Code gives no verdict on a document (decision 4).
   - **Jev reads the relation that reached a candidate** (2026-11-23, [CTX-1578](https://linear.app/ctxpipe/issue/CTX-1578)). In the layers of `get_related`, the text of a candidate starts with one line: the title of its parent and the predicate, in the direction of the relation (`"<parent>" MENTIONS this document.`, or `This document OWNS "<parent>".`). A seed and a document of the bridge have no such line. Only the layer judge reads it: the disagreement step reads the evidence text with no such line. The line is in the `<data>` block, because the title is text of the content. Why: on the dev split of the kept runs of generation 10, the code document that the seed issue mentions was a candidate of layer 1, and Jev judged it low (p(answers) 0.32, p(explore) 0.39). Its text showed no sign that the issue names it.
   - **The batches follow the document keys, not the rank** (2026-11-23, [CTX-1577](https://linear.app/ctxpipe/issue/CTX-1577)). A Jev call holds at most 25 candidates. The layer judge cuts the batches in the order of the document key (a SHA-256 of the path). Thus the same candidates give the same calls in each order, and each call gets strong and weak candidates. Why: Jev reads the other candidates of a call. Before, the batches followed the search rank (hits 1 to 25, then 26 to 50), so a change of the search order moved documents to other calls and changed their p(answers). In the recorded calls of the eight live runs of the question set v0 (dev split), the same document with other neighbors had a mean |Δp| of 0.022 (maximum 0.61). The identical request sent again had 0.008. On the same documents, the order of 12.7% of the dev answers (recall@5 or nDCG@10) changed with other neighbors, and 5.5% with the identical request. Stronger neighbors also gave a lower p (slope −0.24 on their mean p). One candidate for each call removes the neighbors completely, but it costs 63% more for each question and 15 times the calls. Thus it needs a live run first.
   - The "why" path is the parent chain that the traversal records.
   - **A step to an answer is a result** (decided by the lead, 2026-11-22, [CTX-1520](https://linear.app/ctxpipe/issue/CTX-1520)). A result of `get_related` is a document with a p(answers) of at least `keepAt`, or a document on the "why" path of such a result (not a seed). A step keeps its own p(answers) as its score, so it comes after the answers. The limit of 100 results applies to an answer and its steps together, so that no kept answer loses a step. The disagreement step compares only the answers. Why: in the Kubernetes pilot, the loop explored the middle document of three chains (a high p(explore)) and found the far document through it, and then `keepAt` dropped the middle document (a low p(answers)). The traversal records one parent for each document: the relation with the highest confidence. This parent gives the "why" path.
   - **A document that Jev marks to explore is also a step** ([CTX-1534](https://linear.app/ctxpipe/issue/CTX-1534), 2026-11-22). A result of `get_related` is also a document (not a seed) with a p(explore) of at least `exploreAt`, also when no answer comes after it. The p(explore) question asks if the search must explore from the document to answer the question. Thus such a document is a needed step. After layer 1, only documents with such a p(explore) are the frontier. Thus each step on the "why" path of an answer also has such a p(explore). When the limit of 100 results applies, it takes the answers and their "why" paths first, and then the other steps, best first. The results are in the order of their score, so each step comes after each answer. Why:
     - On the dev split of the question set v0, 37 documents (not seeds) had a p(answers) under `keepAt`. Of the 11 that Jev marked to explore, 9 were gold documents (the documents that the dataset labels as the answer of the question). Of the other 26, 2 were gold documents.
     - The earlier rule lost three kinds of gold documents. The first kind is the middle document of a second path of the same length to an answer, because the traversal records one parent. The second kind is an answer at the end of a path with a p(answers) just under `keepAt`. The third kind is a step after which the loop found no answer.
     - The replay of the v0 live run made no model call. The traversal recall on the multi-hop questions went from 0.821 to 0.929 (dev) and from 0.700 to 0.900 (holdout). The hub check went from 0.032 to 0.027.
   - The budgets stay in code: depth, fan-out, time and the visited set. `validAt` filters in SQL.
   - PageRank, the intent presets, the predicate weights and MMR go away. No separate ranker runs after the layers.
3. **The tools.**
   - `search_knowledge` is the search plus layer 0.
   - `get_related` is the full loop. Each layer reads the out-relations and in-relations of the frontier in one ClickHouse query.
   - With D = 3, one retrieval is about 6 steps of ClickHouse queries and 5 Jev calls. Since [CTX-1548](https://linear.app/ctxpipe/issue/CTX-1548), a frontier read is three queries: the edges, then the neighbor documents and the mention counts in parallel. A join of the neighbors in the edge query evaluated the edges two more times (p50 390 ms for each read in the v0 run).
   - **The bridge to other sources** (2026-11-23, [CTX-1578](https://linear.app/ctxpipe/issue/CTX-1578)). Layer 1 also judges the documents of the sources of no seed that are closest to the question by vector, at most `bridgeItems` (10), in addition to `fanOut`. A source is the connector mirror root of the path (`github`, `linear`, …), or `authored`. The bridge is a search of the store with no query terms (thus only the vector order), at the `validAt` of the walk. It starts when the query vector is ready, in parallel with the read of the seeds, and it makes no model call. A document of the bridge has no parent, so its "why" path is empty. Jev can explore from it, so layer 2 follows its relations. The bridge follows no relation, so a walk of named predicates, of one direction or of a time window has no bridge. Why: an issue often has no relation to the code or the design that it is about. On the dev split of the kept runs of generation 10, each of the 8 missed traversal steps was a cross-source question. For 7 of them, the seed issue had no stored edge to the gold document (only its `FROM_SOURCE` relation), so no walk could reach it. 1 was linked, and Jev judged it low. With the recorded query vectors, the bridge put 5 of the 8 gold documents into layer 1 (4 of them new). Only a live run gives the judgments of the new candidates; it runs from `main` after the merge.
   - **The steps that do not wait for each other run in parallel** (2026-11-22, [CTX-1548](https://linear.app/ctxpipe/issue/CTX-1548)). The seeds are the first frontier, so the read of their relations starts with the query embedding, and the judge of the seeds runs with layer 1. While Jev judges a layer, the store reads the relations of all its candidates, and the next layer uses only those of the candidates that Jev explores. Thus a walk of D layers waits for D Jev calls, not D + 1, and the Jev requests and the results do not change.
   - **The disagreement facts are asked with the judge of the last layer** (2026-11-23, [CTX-1566](https://linear.app/ctxpipe/issue/CTX-1566)). The top answers come only from the answers that Jev judged before the last layer (depth D) and from the documents of the last judge. When these are at most N (decision 4), Jev answers the facts of all of them in the round of the last judge, and code reads only the facts of the top answers. Else the facts are asked after the walk, for the top answers only. Thus a walk that reaches depth D waits for D Jev rounds, not D + 1. The cost is the facts of the documents that do not answer. A walk that stops before depth D asks the facts after the walk, because only the judge tells that a layer is the last one. Why: in the dev split of the question set v0 (`maxDepth` 2, the tool default), 18 of 27 `get_related` calls judged layer 2, and 17 of them had at most 10 such documents.
   - **The query vector of an org and a text is kept** (the last 256 in the process). An agent often calls `get_related` with the query of its search, so the second call makes no embedding call. The org is part of the key, so the time of a call does not show that another org asked the same text.
4. **The claims between the top results are shown. The client agent reasons about them; code gives no verdict on a document** ([CTX-1418](https://linear.app/ctxpipe/issue/CTX-1418), the CTO, 2026-11-19; revised by [CTX-1720](https://linear.app/ctxpipe/issue/CTX-1720), the CTO, 2026-11-26).
   1. Take the top evidence set, about N = 10.
   2. Jev answers yes/no questions (Noul) about the content only. Each question asks for one judgment, and "yes" means that the condition is present:
      - for each pair: do the two items make a claim about the same part of the question; do the claims disagree; does Item a change or replace the claim of Item b (and the reverse);
      - for each item: does its claim apply only to a part of the question, for example one team, one product or one time range.

      The state holds the question and the passages. It does not hold the row data (dates, validity, source authority, stored relations, confidence). The questions go in the pair batches: for N = 10, 4 calls with at most 12 pairs each, in parallel (190 questions).
   3. A pure function in code gives the readings of each pair from the facts. A pair whose claims are not about the same part of the question, or that agree, gets no reading. Else:
      - `REPLACES` from Item a to Item b, for each direction where Item a changes or replaces the claim of Item b;
      - else, when the claims disagree: `PARTLY_CONTRADICTS` from the item whose claim applies only to a part of the question, when only one of the two items has that fact, else `CONTRADICTS`.

      The confidence of a reading is the lowest p(yes) of the facts that give it.
   4. The output is a list of claims between the top results. Each claim has its two ends (`from`, `to`), its predicate, the kind of claim (`by`), and its confidence:
      - **a stored relation** (`by: edge`) from one top result to another: also its source and its `validFrom` and `validTo`. The read of these relations starts with the judge of the last layer, as the facts do, and it uses the time filter of the walk. The confidence is the one that the file states: for a `MENTIONS` of a reference key, it is not the weight of the read ([ADR-066](ADR-066-knowledge-content-in-clickhouse.md) decision 5), which only the walk uses. A `SUPERSEDES` is such a claim, like each other relation;
      - **a reading of the model** (`by: reading`): the readings of item 3.

      A page shows the claims between its own results. Each result also shows its source type and its document times. Code does not group the results into positions, and it does not give a status (current, superseded, disputed or scoped). The calling agent compares the claims, their sources, their times and their confidence, and it writes the answer.
   5. Each fact is "yes" at a threshold that is a setting of the loop (`ORCHESTRATOR_DEFAULTS`). The function makes no call, so the evals score a change of a reading or a threshold again from the recorded answers ([ADR-069](ADR-069-knowledge-plane-evals-and-rollout.md) decision 7).

   Why the facts: Jev gives one fast judgment for each question, and the questions of one call do not see each other. A typed decision model follows the name of an option, not its definition, and the options of a Choice question compete. Thus a 5-way Choice with long definitions, or a question that weighs four factors, is not reliable. Small facts are reliable and can be tested.

   Why no verdict (the CTO, 2026-11-26): the first version gave each position a status with a fixed order of rules (a stored `SUPERSEDES`, Jev's "changes or replaces", the validity at the query time, the source authority, `observed_at`, the confidence), and the tool told the agent to prefer a current position. A status is too definitive. It loses nuance (for example, "B replaced A for one region only"), and a weak signal such as the projection time could decide it. "There can be claim that something supersedes something else, that's valid usecase. However it's claim as anything else with temporality and confidence attached to it" (the CTO, 2026-11-26). The positions also go: without a status, a position tells only that its items agree. In the kept generation 12 runs of the question sets v1 (corpora and Backstage), 95 of the 149 positions held one item, and of the 15 pairs of gold documents of two different expected positions that both had a position, 6 were in one position. A reading between two items gives the disagreement directly.
5. **One text vector space** (the CTO, 2026-11-20).
   - All searchable content is text. Images become text at ingest (decision 6), so one text-only model embeds every chunk, in large batches.
   - The first design had one multimodal space with Gemini Embedding 2. It is the only multimodal model with ZDR endpoints, but its ZDR endpoints take one input for each request. The live controls of 2026-11-20 ([#892](https://github.com/ctxpipe-ai/ctxpipe/pull/892)) showed it: its Vertex endpoints refused each request with more than one input, also with `zdr: false`, and only Google AI Studio took a batch. AI Studio has no ZDR endpoint. Thus a full rebuild needed one request for each chunk.
   - The CTO first chose two spaces (a text model for text, Gemini Embedding 2 for images), then chose images as text instead: "this whole issue makes me think about the design of directly semantically searching the images. I think we need to change the approach that during ingest we use image model to read, describe and or convert the image to mermaid and then during retreival search it as text" (the CTO, 2026-11-20).
   - All embeddings go through the OpenRouter embeddings endpoint, with one OpenAI-compatible client. The model must also be usable outside AWS, for example by a self-hoster on Azure.
   - The model and the dimension are config, and both are part of the projection version ([ADR-067](ADR-067-knowledge-projection-applies-git-diff.md)). Thus a change of model or dimension starts a full rebuild.
   - No call pins a provider endpoint (decision 7). OpenRouter can route each embedding call to any ZDR endpoint of the model.
   - Before a chunk is embedded, it gets one line of context: the title and position of its document. A search question goes as it is.
   - **Text model: OpenAI text-embedding-3-large** (`openai/text-embedding-3-large`, 1024 dimensions; the CTO, 2026-11-20, [CTX-1451](https://linear.app/ctxpipe/issue/CTX-1451)). It replaces Qwen3 Embedding 8B. The reasons:
     - The trust rule of the CTO (2026-11-20): "we still trust OpenRouter as such, but we don't trust providers outside of hyper scalers and frontier US labs + typesafe". The list: OpenAI, Anthropic, Azure, Amazon Bedrock, Google Vertex, Google AI Studio, TypeSafe. "Keep ZDR policy." Qwen3 Embedding 8B had ZDR endpoints only at Nebius, DeepInfra and SiliconFlow, and none of them is on the list. text-embedding-3-large has a ZDR endpoint on Azure.
     - The latency data of [CTX-1448](https://linear.app/ctxpipe/issue/CTX-1448) (2026-11-20, 50 calls a row, from Melbourne). The Qwen query embedding was not stable: the production request had a p95 of 47.2 s before the latency sort and 28.3 s after it, and the p95 of its pinned endpoints changed from run to run (Nebius 2.2 s, then 8.8 s). text-embedding-3-large on Azure had a stable p95 of about 1 s. The time budget of a search was 3 s then. Since 2026-11-26 it is 10 s (the CTO). At 3 s, 15% of the searches of one organization stopped at the time limit. The old search stack has a 95th-percentile latency of 5.3 s.
     - The OpenAI and Azure embeddings APIs take up to 2048 inputs and up to 300,000 tokens, summed over the inputs, in one request, and up to 8192 tokens for each input ([OpenAI API reference](https://developers.openai.com/api/reference/resources/embeddings/methods/create), [Azure OpenAI quotas and limits](https://learn.microsoft.com/en-us/azure/foundry/openai/quotas-limits)). The client has no tokenizer. Each token of the model is at least one byte of UTF-8, so a batch holds at most 2048 inputs and at most 300,000 bytes, and one input has at most 8192 bytes. A longer input loses its end; only a chunk with a very long title or many 4-byte characters is that long, because a chunk has at most 2048 characters.
     - The model takes the `dimensions` parameter and gives a shortened vector: "specify a value of 1024 for the `dimensions` API parameter" ([OpenAI embeddings guide](https://developers.openai.com/api/docs/guides/embeddings)). Thus the vectors keep the 1024 dimensions of `chunks.embedding`.
     - It needs no instruction line before a query, and the request sets no quantization filter. Qwen needed both.
     - The disadvantages: its published retrieval quality is lower than that of Qwen3 Embedding 8B, and its price is $0.13 for each million tokens (Qwen: $0.01). On 2026-11-20 the OpenRouter ZDR list had only one ZDR endpoint of the model (Azure), so no fallback inside a request exists until a second one comes. Its weights are not open, so a self-hoster cannot run it locally.
   - **Earlier choice:** Qwen3 Embedding 8B (the CTO, 2026-11-20, before the trust rule). It had the best published retrieval quality of the ZDR text models and a price of $0.01 for each million tokens. It needed an instruction line before a query and a quantization filter (`bf16`, `fp16`, `fp32`, `unknown`), so that a fallback never put a low-precision model into the space.
   - **The other text candidates:** on 2026-11-20 the ZDR list had these text models at a provider on the trust list: OpenAI text-embedding-3-small (Azure), Google Gemini Embedding 001 (Google Vertex) and Amazon Titan Text Embeddings (Amazon Bedrock). The evals of [ADR-069](ADR-069-knowledge-plane-evals-and-rollout.md) can compare them with text-embedding-3-large on our data. A change of model is a change in config with a full rebuild, never a fallback inside a request, because each model has its own vector space.
     - Perplexity pplx-embed-v1-4b and the open models (Qwen3 Embedding) have no ZDR endpoint at a provider on the trust list.
     - Models with an input limit of 512 tokens are too short for our chunks.
     - Voyage 4, Cohere Embed 5 and NVIDIA Nemotron have no ZDR endpoint.
   - Public benchmarks do not match our content (engineering knowledge). The evals of [ADR-069](ADR-069-knowledge-plane-evals-and-rollout.md) decide between the text candidates on our data.
6. **Images become text at projection time** ([CTX-1433](https://linear.app/ctxpipe/issue/CTX-1433); the CTO, 2026-11-20).
   - The projection reads each image at the tip and converts it to text in memory: a vision model gives a description, the text in the image, and the graph or the sequence of a diagram, and our code renders the Mermaid of the diagram. The text gets the chunks of the image document. No text goes into the Workspace Git: "we don't want to store that in git because that would duplicate the data and introduce whole range of inconsistency issues. We should make the process as deterministic as possible (this applies to images as well)." This replaces the plan that ingest writes a text file beside each image.
   - "diagrams is the main feature and hard requirement of image recognition" (the CTO). The model returns a structured reading (nodes, groups, edges with labels and arrowheads, direction, or participants and ordered messages), not Mermaid, so the Mermaid is always valid. The vision eval of the knowledge harness (`factory eval knowledge:vision`) scores node, edge and group F1 on made-up diagrams of each kind (architecture, flow, sequence, a dense mesh, photos, a small screenshot, swimlanes, C4, draw.io and Mermaid SVG).
   - The cache keeps each reading by blob SHA, model and prompt version ([ADR-066](ADR-066-knowledge-content-in-clickhouse.md) decision 6): "Vision model, cached by blob hash" (the CTO). A rebuild reads the cache and calls no model, so the same bytes give the same text. If the cache is lost, a rebuild calls the model again and can get other text.
   - An SVG is drawn to a PNG by the file converter, and its text labels are added to the text.
   - The image stays the source of truth.
   - Jev sees no image bytes. An image candidate goes to Jev as text, and the backend reads no image bytes at retrieval. The code has no image path to Jev and no setting to turn one on: "just not do not implement it at all. We don't need to have a feature we don't intent to turn on" (the CTO, 2026-11-20; [CTX-1432](https://linear.app/ctxpipe/issue/CTX-1432)).
   - The vision model is a ZDR model on OpenRouter, and the evals of [ADR-069](ADR-069-knowledge-plane-evals-and-rollout.md) choose it. On 2026-11-20 the vision eval (three runs of 17 diagrams) gave GPT-6.1 Terra an edge F1 of 1.00 with no failure, at about $0.005 an image and 5 s; Gemini 3.8 Flash 0.99 and Claude Sonnet 5.5 0.99. One vision model reads the images: "I don't think we need multiple models for images. We just pick one and go with that" (the CTO, 2026-11-20). The default model is in code (`openai/gpt-6.1-terra`), and operators replace it with the environment variable `MODEL_VISION_NAME`: "It should be an ENV variable so selfhosters can set whatever value they want" (the CTO, 2026-11-20). The cache key holds the model, so a change of the model gives new entries and keeps the old ones correct.
   - The projection runs only for an org whose `knowledge_plane` flag is not `off` ([ADR-069](ADR-069-knowledge-plane-evals-and-rollout.md) decision 9), so the images of an org that is `off` go to no new provider.
7. **Data receivers.** Jev receives the question and the text of the candidates. It receives no images. The embedding provider receives the text chunks and the questions. At projection time, the vision-model provider receives the images (an SVG as a PNG). All three are upstreams of OpenRouter, which our public docs list as the model sub-processor, and we reach them only through ZDR endpoints. ADR-063 accepted the Jev endpoint only for public mock screenshots. For customer content:
   - Every Jev call, every embedding call and every vision call sets `provider.data_collection: "deny"` and `provider.zdr: true`. Our public docs promise ZDR endpoints for hosted model calls. On 2026-11-20, the OpenRouter ZDR list (`GET /api/v1/endpoints/zdr`) had TypeSafe Jev 1.14 (provider `typesafe`) and text-embedding-3-large (`azure`).
   - No call pins its upstream provider: "don't pin models to specific providers, we need fallback. openrouter already optimises latency for us" (the CTO, 2026-11-20). A call sets no `provider.order`, and it keeps the default `allow_fallbacks: true`. It sets `provider.only` only to the allowlist of the operator ([ADR-070](ADR-070-model-calls-go-only-to-trusted-providers.md), which makes this decision the rule for each model call). With `zdr: true`, OpenRouter routes and falls back only among the ZDR endpoints of the model.
   - The query embedding of a search also sets `provider.sort: "latency"`, and it makes one attempt with no retry ([CTX-1448](https://linear.app/ctxpipe/issue/CTX-1448)). OpenRouter balances by price when a request sets no sort. Thus OpenRouter sent most queries to an endpoint that answered most calls with HTTP 429, and the retries with backoff gave a p95 of 47 s against the time budget of a search (3 s then). The sort keeps the fallback and pins no provider. A failed query embedding makes the search partial, as the end of the budget does. The ingest path sets no sort and keeps its retries, because it has no time budget.
   - These request settings are the guard. No written confirmation from a provider gates the flag (the CTO, 2026-11-19).
   - ADR-063 decision 6 records that nobody has confirmed that OpenRouter applies these settings on the alpha Decisions endpoint. Before the first org leaves `off`, an automated probe with a real call confirms it. An agent runs the probe, and no person is necessary.
   - The probe reads the ZDR list at its run. Each check passes only when the answer names a provider of a ZDR endpoint of the model. The check "refused without a ZDR endpoint" sends the request of the client to a Decisions model with no ZDR endpoint. A refusal with `zdr: true`, after the same request with `zdr: false` is served, proves that the ZDR filter holds with fallback. The vision checks do the same for the vision request: the vision model must answer at a ZDR provider, and the same request to a vision model with no ZDR endpoint must be refused.

## Consequences

- **Better ranking signal:** the ranking comes from the question, not from the graph shape. We no longer tune the intent presets and the predicate weights.
- **Latency:** about 500 ms of Jev time for `get_related` at D = 3, plus the ClickHouse queries. Each query makes one embedding call and one vector scan. The v0 run measured about 450 ms for each Jev call, also with 2 questions: the count of Jev calls in series sets most of the time of `get_related`. About 2% of the Jev calls take 1.1 to 2.1 s, also small ones, and these slow calls set the p95. Thus a Jev call with no answer after 700 ms sends a second copy of the same request, and the first copy that ends gives the result (a hedged request, [CTX-1590](https://linear.app/ctxpipe/issue/CTX-1590)). The requests and the answers do not change, and the copies add about 2% more calls. The scan grows with the size of the Workspace: 1 million chunks is about 128 MB of binary vectors for each query.
- **Cost:** each retrieval has a model cost (Jev and the query embedding). Ingest has a model cost for each new or changed image.
- **Open: what happens when Jev fails or is slow** (return the search order, or fail the call). The PoC decides it.
- **Facts to verify:**
  - how many Jev questions fit in one call (50 candidates × 2, or 12 pairs × 4 and the items);
  - the speed of the binary scan from real S3 (the measurements of decision 1 used S3 on the same host).
- **Amends** ADR-051 decision 6 (graph relevance) and section 8 (data layer) for orgs on the new plane. Until the rollout ends, the old ranking serves the other orgs.
