# ADR-063: The visual critic decides with Jev only

**Status:** Accepted | **Date:** 2026-11-13 | **Tags:** visual-review, critics, factory, models

## Context

The visual critic (`critics.json`, entry `visual`) judges each changed baseline screenshot of a PR with `pnpm visual:review` ([CTX-1178](https://linear.app/ctxpipe/issue/CTX-1178)). Until this ADR, it sent each screenshot to a Sonnet-class LLM through OpenRouter, and it blocked on a `regression` with severity `major` or `blocker` (an owner decision). The bake-off of the critic ([CTX-1202](https://linear.app/ctxpipe/issue/CTX-1202); first in `packages/visual-review/evals/critic/`, now `factory eval`, see rule 17) compares the judges on labeled screenshot pairs. Its selection rule picks the cheapest arm with a recall of 0.9 or more and a precision of 0.7 or more on the hold-out set.

Bake-off run 43202777292 used the page-story dataset ([CTX-1249](https://linear.app/ctxpipe/issue/CTX-1249)). A judge panel (Opus 5.5, GPT-6.1-Sol, Gemini 4 Argon, plain 2-of-3 majority) labeled the real changes. The panel agreed with the known label on 105 of 119 synthetic cases. The 5-hour job limit stopped the run before each arm judged each hold-out case. The table below uses the 27 hold-out cases (19 `regression`, 8 `intended`) that every arm judged, with 1 run each. Correction: the hold-out set has 47 cases. On all 47 cases, a later Jev-only run (43360812931) gave the old rubric a recall of 0.79, a precision of 0.90 and an unsure rate of 0.38 (see rule 8).

The product owner decided on 2026-11-13: "Use Jev for this capability and just finish it, don't rerun others now. We want the visual diff critic functional now and we can improve the performance later."

## Decision

1. **Jev decides.** The `visual` entry runs `visual:review --judge jev`. Jev 1.14 (`typesafe/jev-1.14`, OpenRouter Decisions API, `judgeWithJev`) gives the final verdict of each changed screenshot. A new screenshot (no base image) goes to Jev too (`judgeNewWithJev`). No LLM changes the verdict. Since rule 13, an LLM explains a Jev `regression`. `--judge model` (an LLM, with an optional `--filter jev`) and `--judge agent` stay for a person or a fork.
2. **Thresholds.** For a change, Jev answers one question for each area and each quality of the rubric (better, same or worse), one defect question, and one box question for the region. For a new screenshot, each question asks whether the screenshot breaks a rule. Since rule 15, Jev gets no literal yes/no question for one defect.
   - A worse (or broken) area or quality with a probability of 0.5 or more is a `regression` with severity `minor`. Since rule 18, the severity is `major` from 0.8 on a new screenshot, and from 0.9 on a changed screenshot (CTX-1493). An area needs the region of the box; without a box, the verdict is `unsure`.
   - A worse `density` is never a `regression` on its own. It counts only for `unsure`, and the summary says so (rule 10).
   - A highest probability from 0.2 up to 0.5, or a question with no answer, is `unsure`.
   - Else the verdict is `intended` when the brief or the source diff explains the change, and `unsure` when nothing explains it.
   - An image pair in the tolerance of the visual check is `noise`, and a removed screenshot is `unsure`. Neither calls Jev.
3. **A Jev result is feedback, never a block** (owner decision, 2026-11-13). Each Jev `regression` has severity `minor`, so the factory makes it a nit, and the critic passes. The visual critic is a feedback loop for the implementing agent, not a gate that needs an override. On the 27 cases that every arm judged, Jev with the first rubric found 18 of the 19 regressions (recall 0.95), but its precision was 0.90: it also flagged 2 of the 8 intended changes. With the rubric of rule 8, the precision on all 47 hold-out cases is 0.83. A block on each of those needs an override; feedback does not. Rule 18 changes this rule: a strong flag is a should-fix, which the agent fixes or overrides with a reason.
   - In `--images` mode, `visual:review --judge jev` copies the `before`, `after` and `diff` images of each suspected regression (only `after` for a new screenshot) to a new private folder of the system temporary folder, which the command keeps. The summary of the verdict names the area or quality, the probability of Jev, the region when Jev placed one, and the paths of these copies. The factory shows the summary in the finding.
   - The agent looks at the images of each suspected regression. It fixes the defect, or it says in the PR description why the change is intended.
   - The shared store keeps only the verdict word and the severity. A reused verdict has no image paths. Then the agent compares the base image (`git show <merge base>:<path>`) with the head image in its checkout.
   - A screenshot of a group that Jev did not judge gets the summary of the judged screenshot, and its own images.
4. **`unsure` stays a nit.** The factory makes `unsure` a nit, as before. The code does not change this. **The critic passes unless the run fails.** A Jev reply that is not usable (a 400 or 413 answer, a reply out of the schema), a missing key, or a spend stop gives exit code 2, and the critic gives `ERROR`, never a pass.
5. **Spend.** The spend limit of the visual critic is $1.00 for each PR, across all runs (CTO decision, 2026-11-22, [CTX-1491](https://linear.app/ctxpipe/issue/CTX-1491); it was $0.10 from 2026-11-13, and $5 before). A change of a shared component (about 166 stories) costs about $0.07. A higher spend is unusual: the critic gives `ERROR`, and a person decides with `factory check --critic-limit-usd`. The limit is `LIMIT_USD` of the factory (`machines/cli/src/command.rs`, factory PR [#172](https://github.com/ctxpipe-ai/factory/pull/172)), and `.github/merge-gate.json` pins that release. There:
   - A path with no known cost counts at $0.0005 when the branch has no known cost yet (the Jev cost of a story, rounded up). Thus a first run could take about 200 paths under the $0.10 limit, and about 2,000 under $1.00.
   - The `{budgetUsd}` of a run is rounded down to $0.0001, not to a cent. A budget in whole cents would drop up to 25 Jev calls of the limit.
   - `MAX_PATH_USD` stays $3. It only bounds a stored spend record, so that no writer can make the spend infinite, and it caps `{budgetUsd}`. A record above the limit already stops the critic, so a lower cap adds nothing.
   - In `visual:review --budget-usd`, a Jev reply with no `usage.cost` counts as $0.002 (above the highest Jev cost of the bake-off). An LLM reply with no cost still counts as $0.25. A missing cost never turns the budget off.
6. **Data receiver.** Each changed screenshot, the brief and the source diff now go to TypeSafe (Jev) through the alpha OpenRouter endpoint `/api/alpha/decisions`. Before, they went to Anthropic, and only an opt-in `--filter jev` reached TypeSafe. The request sets `provider.data_collection: "deny"`, but no one has confirmed that OpenRouter applies it on the alpha endpoint, or the retention terms of TypeSafe. The screenshots are Storybook stories with mock data, and the repository is public.
7. **Rule.** Run the bake-off again for each new decider model and for each change of the questions or the rubric. Since rule 16, the calibration part of this check reads the unseen set, not the owner examples. Since rule 17, run it on the host with `factory eval visual:bakeoff` and `factory eval visual:calibration`. It never runs in CI. `factory eval` judges with the critic of `origin/main` of the checkout, and it has no option for a branch yet. Thus, until it has one, the after run of a change runs right after the merge, against the before run of the earlier `main`. When the after run fails this rule, revert the change.
8. **Rubric update (2026-11-13).** The rubric has sharper definitions and one new area, `broken-content`, so that each Jev question names defects that a screenshot shows and ties them to our design docs. The new rules come from two design guides that the product owner recommended, [frontend-design](https://agenticskills.io/skills/frontend-design) and [Impeccable](https://impeccable.style/), with only the rules that agree with `apps/ui/DESIGN.md`. A Jev-only bake-off on all 47 hold-out cases (panel labels, 1 run) measured the change (rule 7). Before (run 43360812931): recall 0.79, precision 0.90, unsure 0.38, $0.0004 per story. After (run 43360825713): recall 0.91, precision 0.83, unsure 0.23, $0.0005 per story. Only the new rubric passes the selection rule (recall 0.9 or more, precision 0.7 or more). The lower precision is acceptable, because a Jev result is feedback that never blocks (rule 3).
9. **The critic judges with the rubric of the PR head, as data** (owner decision, 2026-11-13, [CTX-1264](https://linear.app/ctxpipe/issue/CTX-1264)). Before this rule, a PR that changed the rubric got a judgment with the old rubric of the merge base.
   - **The rule.** The rubric is data in `packages/visual-review/rubric.json`. The `visual` entry names it in `command.headFiles`, and passes `--rubric {folder}/head/packages/visual-review/rubric.json`. The code of the critic stays the merge-base code.
   - **Why the code stays at the merge base.** The factory gives `MODEL_PROVIDER_API_KEY` to the run step of a command critic. The security reviews of [CTX-1198](https://linear.app/ctxpipe/issue/CTX-1198) found that branch code could take the key, so the factory runs the command from the merge-base tree. Only data comes from the head.
   - **The trust boundary.** A head rubric is text of the PR author. The factory copies it from the object store of the head commit (no checkout read, no symlink) into the review folder, read-only: only a regular file of at most 64 KiB, else `ERROR`. `readRubric` then opens it with no symlink follow, refuses a file over 64 KiB, and validates it with a strict Zod schema (`rubricSchema`): fixed fields only, ids that match `^[a-z][a-z0-9-]{0,39}$` and are unique, a name of at most 60 characters, a definition of at most 1500, 1 to 16 areas and qualities, source paths with no `..`, and one line of printable text with no `<` or `>`. Thus a definition cannot start a new line of the prompt, or open or close a `<data>` block. The text goes only into the question text of a Jev request and into the prompt of a model, inside a JSON body. It never chooses the endpoint, the key or the model. An invalid file is exit code 2 (an `ERROR`), never a pass and never a fallback to the packaged rubric.
   - **What a hostile rubric can do.** It can weaken or change what the critic checks, for example a definition that asks Jev to find nothing worse. This is the cost of the owner decision. A Jev result never blocks (rule 3), so a weak rubric hides feedback, not a gate. The gate report (the job summary of the `Merge gate` check run) names each PR that changes the rubric file, so a person reads that change as code.
   - **Verdict reuse.** The hash of the head rubric is part of the key of a stored verdict, so a new head rubric is a new judgment.
   - **Limit.** The factory still carries a stored pass of a screenshot whose bytes did not change. A commit that changes only the rubric after the critic passed does not judge those screenshots again.
   - **Rule 7 still applies.** A PR that changes the rubric gets a bake-off, at the time that rule 7 gives. The head rubric judges that PR's own screenshots, not the bake-off.
   - **Head story files ([CTX-1311](https://linear.app/ctxpipe/issue/CTX-1311)).** The kind and the purpose of a story are also head data. A `headFiles` pattern makes the factory copy the head version of each story file that the PR changes, with the same copy rules (regular file only, at most 256 KiB, read-only, from the object store). `visual:review --head-stories` reads a story file there first, and else from the merge base. It refuses a file that is not a regular file or whose real path leaves the folder (exit code 2). It only parses the file with the CSF parser of Storybook and never runs it. The purpose goes into the prompt inside a `<data>` block, as before. A story file never chooses the endpoint, the key or the model. A hostile purpose can only ask the judge to find less, as a hostile rubric can. The changed story files are in the PR diff, and the gate section names each one.
10. **Jev questions after the first use (2026-11-13, [CTX-1262](https://linear.app/ctxpipe/issue/CTX-1262)).** On the deliberate redesign of CTX-1259, 96% of the verdicts were `unsure`, and each `regression` was a removal that the brief names. The bake-off tested other questions and thresholds on the panel-labeled cases outside the hold-out set and on the labeled redesign set of PR #717 (`redesign.json`, now in the factory harness, see rule 17: 15 regressions that the owner found after the merge, 109 intended screenshots, and the 25 fixes of PR #718). The table of the variants, with the run ids and the cost, is in the pull request of CTX-1262 and on the ticket. The bake-off now keeps the raw answers of Jev, so a threshold can be tested again with no new call.
   - **A run-together question.** Jev asks if a label puts two parts side by side with no space (rule 2). It gave 0.70 to 0.93 on the 7 redesign screenshots with a "01Connect" step label, and at most 0.41 on any page case.
   - **Density alone is not a regression.** Density never found a regression that no other question found, and it gave 12 of the 14 false flags on the redesign set: an intended removal leaves more space.
   - **The `unsure` floor stays 0.2.** On the redesign set, 14 of the 15 regressions and 94 of the 109 intended screenshots had a highest worse probability from 0.2 to 0.5. A floor of 0.3 or 0.4 made 7 or 8 of these regressions `intended`. The band does not separate them, but it is the only signal that Jev gives on them.
   - **Result** (runs 43400628954, 43400633408 and 43403029107). Hold-out set: recall 0.91, precision 0.86, unsure 0.26, as before. Redesign set: 7 of 15 regressions found (before: 0), 3 or 4 false flags (before: 14), unsure 0.91 (before: 0.88). Of the 25 fixes, Jev flagged none, but each one was `unsure`: Jev does not see the direction of a hierarchy change.
   - **The lead decided to ship it.** The variant ties the hold-out set and improves the redesign set. The later goal of the owner (catch execution regressions, with few false flags on intended changes) took the place of the rule "change only the docs when no variant beats the hold-out set". No variant had zero false flags on the redesign set and the same recall.
   - **Limits.** The run-together question came from one defect pattern, and it can be fitted to that pattern: the 7 regressions that it found all show the same "01Connect" step label. The 8 inverted title hierarchies are still `unsure` ([CTX-1266](https://linear.app/ctxpipe/issue/CTX-1266)).

13. **An explainer, a floor for a new screenshot, and kept verdicts (2026-11-14).**
    - **The explainer** ([CTX-1256](https://linear.app/ctxpipe/issue/CTX-1256), owner approval 2026-11-14). After a Jev `regression`, one call to a cheap vision model (`openai/gpt-6-luna` through OpenRouter, with a low reasoning effort; `src/explain.ts`) gets the before and after images (a new screenshot: its images), the region of Jev, the flagged rubric entries and the brief. For each flagged entry, it writes the evidence and one fix, or says that it sees no visible defect. That answer goes to the agent too. The text fills only `observations`, the `evidence` and `suggestion` of each finding, and the end of the summary (the factory shows only the summary). The verdict, the severity, the confidence and the regions stay the ones of Jev, so the verdicts are the same as with Jev alone: the cascade of the bake-off lost recall because its LLM replaced the verdict. There is no call for `intended`, `noise` or `unsure`. The explainer pass runs after all Jev calls of the run, so that a short budget goes to the verdicts first. It calls the explainer only while $0.005 of `--budget-usd` is free (a reply with no cost counts as $0.005; an estimate from the price list, not a measurement), and its spend never makes the exit code 2. A screenshot of a group, or another viewport of a new story, gets the explained summary of the screenshot that Jev judged. A failed call or a reply that is not usable keeps the Jev verdict with a sentence and no `error`; after a failed call, the cost of the verdict is unknown. The `costUsd` of a verdict adds both calls, so the spend of the factory counts the explainer. The bake-off arm is `jev-explain:<model>`. Data receiver (see rule 6): the images of each Jev regression and the brief now also go to OpenAI through OpenRouter, with `data_collection: "deny"`. The factory reviewers already get the brief. The explainer can quote the brief in the summary of the finding, which only the agent of the same PR reads.
    - **A floor for a new screenshot** ([CTX-1267](https://linear.app/ctxpipe/issue/CTX-1267)). Jev does not tell a clean new screenshot from a broken one. In the bake-off run 43400628954 (the rubric before rule 11), it gave `regression` to 8 of the 10 clean and 10 of the 10 broken new cases, and the confidence of the two groups had the same spread: clean 0.62 to 0.90, broken 0.61 to 0.96. On the owner calibration (run 43527124632), it gave `regression` to all 16 screenshots, also to the one with no issue (0.79). No threshold of the confidence separates them. Thus, on a new screenshot only, a flag whose highest probability is under 0.8 is `unsure`, with its findings and the reason in the summary. On that run, 0.8 gives 3 of 10 false alarms and keeps 5 of 10 broken cases as `regression`; the other 5 are `unsure`, which is still a nit. On the calibration run, the screenshot with no issue becomes `unsure`, and 9 of the 15 others stay `regression`. Both words are feedback (rule 3): the floor moves weak flags from "suspected regression" to "not sure", and the summary still names each flag. An `unsure` gets no image copies and no explainer call. A change keeps the threshold 0.5. The bake-off now keeps the raw answers of a new screenshot too, so a per-question threshold can be tested with no new call.
    - **Kept verdicts** ([CTX-1272](https://linear.app/ctxpipe/issue/CTX-1272)). A run that the budget stops still prints each verdict. A verdict with no `error` was judged and paid for; each other one has the error "Budget reached". The run still exits with code 2, so the critic gives `ERROR`. The factory part (store the verdicts with no error when the exit code is 2, so that a rerun judges only the rest) is in the factory repository.
    - **Limits.** The floor comes from one bake-off run with the rubric before rule 11, and 20 new cases (rule 7 asks for more). The paid measurement of this rule (the 20 new cases with 3 runs, the calibration set, and the cost of the explainer) did not run when the rule shipped: no model key was available to the builder. The explainer cost is an estimate from the price list: below $0.001 for each explained screenshot. To measure (about $0.15): write a manifest with only the 20 `new` cases of `cases.json` (for example `~/visual-eval/new-cases.json`), then run `factory eval visual:bakeoff --repo . --out <dir> -- --arms jev,jev-explain:openai/gpt-6-luna --runs 3 --cases ~/visual-eval/new-cases.json --max-cost 0.45` and `factory eval visual:calibration --repo . --out <dir> -- --arms jev,jev-explain:openai/gpt-6-luna --max-cost 0.25` (rule 17). The `answers` of the `jev` arm in `results.json` give the false alarms and the recall of each floor or per-question threshold with no new call, and `explainer.costUsd` of the `jev-explain` arm gives the cost of each explained screenshot.

It looks at how the visible content aligns with its neighbors, at the space to the edges of its container, and at how the region sits with the elements around it. It does not compare the region with the earlier version. The severity is as in rule 19. It is `major` only when a finding names a rubric principle with evidence and a fix. It is never a blocker, and the review never lowers the Jev verdict.
    - **The rule from the diff regions** (`redesigns` in `review.ts`). The interpreter of the compare engine labeled the redesigned picker of #970 a `deletion` of 248 × 52 px, because the bordered box went. It labeled the 4 px move of the send button a `content-change` of 60 × 60 px. Thus the rule uses the size, not only the type. A region qualifies when it is at least 100 × 32 px and is not a color change, a shift or noise. A small control that moves and one line of text are smaller.
    - **A size change does not qualify.** The compare engine measures no region for a screenshot whose size changed. Thus the critic cannot tell a redesign from a small change, group alike diffs, or scope the review. Jev still judges such a screenshot with the full before and after images. Such screenshots are common: #815 has 27, and #819 has 167. A review of each whole image would also pass the budget.
    - **The count.** Of the 13 good UI PRs of rule 18, 5 have a redesigned area (an offline count, with no model call): #642 (5 groups), #718 (7), #736 (1), #819 (70) and #911 (1). #970 has 17.
    - **One review for alike diffs.** Screenshots with alike regions at any position, in one scope and viewport, are one redesign. The first screenshot stands for them. When its review gives a regression, the others take that result and its text. A stronger verdict of their own stays. Then they get no feedback call of their own.
    - **At most 4 reviews a run.** #819 has 70 redesigns. At about $0.02 a review, that is $1.40. This is more than the limit of a PR, which is $1.00 across all runs (rule 5). Thus a run reviews at most 4 redesigns, the largest change first (about $0.08). The reviews run after the reviews of new stories and before the explainers of other changes, so that a short budget goes to them. When the budget has room for the explainer but not for the review, the screenshot keeps its explainer. On #970, the 4 reviews are the composer screenshots of a new conversation on desktop.
    - **The rubric.** Continuity has one more general sentence: elements align by their visible content, the text or the icon, not by an invisible box or its padding. It is not a rule for one component.
    - **A close-up.** The first replay of #970 after the merge (main 7c6258f) reviewed the 4 composer screenshots. Each review said `intended` with no finding: "the branch picker is quiet and recognizable". On the full head image of 1440 px, the picker is about 120 × 16 px, and its offset from the text above is 12 px. Thus the review also gets a close-up of the largest redesigned region with 64 px around it, at up to twice the size (Image 2). A small change far from it does not make the close-up larger. The prompt asks for three general checks there: the visible content starts on the edge of the content of its neighbors, the space to each edge of the container is the same as on the opposite side and as for the siblings, and the elements just above and below, inside or outside the container, share an edge with it or with the container and do not crowd it. The close-up is in a private folder that the run removes.
    - **The second replay** (main f4939ed, the 5 composer screenshots of #970). Each of the 4 reviews named the alignment problem, as `minor`: "the branch icon begins about 24 px from the composer's left edge, versus 16 px for the prompt", with the fix "offset the picker's horizontal button padding". None named the space to the bottom edge or the item below the composer. Thus the checks name even space on opposite sides of a container, and the elements just outside it.
    - **Measured.** With `factory eval visual:replay` right after each merge, as for rule 19. The numbers are in the descriptions of the pull requests of CTX-1509.

## Consequences

- Deterministic checks come first, and Jev is for taste. The screenshot capture measures overflow, off-axis leading markers and text contrast in the page of each story ([CTX-1277](https://linear.app/ctxpipe/issue/CTX-1277)). A failure fails the `storybook:visual` check of the story; Jev does not have to find these defects.
- A visual review costs fractions of a cent for a normal PR, and it takes seconds.
- A visual finding has an area, a region, a probability and the images. Since rule 13, an explainer adds written evidence to a `regression`, or says that it sees no visible defect. The agent decides with the images. To get a written verdict of a model, run `pnpm visual:review --judge model` or `--judge agent` on your own machine.
- No visual finding stops a merge. A real regression that the agent ignores can merge. The agent must answer each suspected regression with a fix or a reason in the PR.
- With the first rubric (27 cases), about one intended change in four got a feedback finding that the agent answers with a reason, and a quarter of the verdicts were `unsure` nits. With the rubric of rule 8 (47 cases), the precision is 0.83 and 0.23 of the verdicts are `unsure`.

## Limits of the evidence

- The arm table uses 27 of the 47 hold-out cases and 1 run. The rubric comparison of rule 8 uses all 47 cases and 1 run. No consistency figure.
- The labels of the real changes come from a judge panel, not from a person. GPT-6.1-Sol and Opus are panel members, so the labels can favor them.
- Only page stories. Most changed baselines of a PR are component stories.
- No new-screenshot case got a result, so the judgment of a new screenshot by Jev has no measurement.
- Jev does not give the same answer twice: on the same question and images, two runs differed by 0.025 on average and by up to 0.22 (rule 10). Thus a difference of a few flags between two variants of one run each is noise.
- The redesign set is one PR, and rule 10 tuned on it. Its 15 regressions are of two kinds only. The run-together question can be fitted to the one pattern that it finds.
- 563 Anthropic calls returned no `usage.cost`. The spend of the run ($62.92) is an overestimate, and the Anthropic arms show no cost per story.

## First use

The first real use of the critic was [CTX-1259](https://linear.app/ctxpipe/issue/CTX-1259) (2026-11-13): six intended visual changes across the product UI, all named in the brief.

- **Size.** 254 changed screenshots. About 150 changed only because the workspace nav group header in the sidebar went from 10 px to 12 px.
- **Spend limit.** The factory estimated $0.1280 (254 paths at $0.0005), above the $0.10 limit, and gave `ERROR` with no model call. The lead raised the limit to $0.15 for this PR.
- **Calls and spend.** The command made 148 Jev calls: 105 screenshots took the verdict of their diff group, and 1 group disagreed. It spent $0.0916, about $0.00062 for each call, in 105 s (127 s for the critic).
- **Verdicts.** 8 `intended`, 243 `unsure` (nit), and 3 `regression` with severity `minor` (nit). The highest "worse" probability of the 135 judged `unsure` verdicts was 0.20 to 0.46 (median 0.29).
- **Regression feedback.** All 3 were false flags. Two graph wait states got "missing elements" (0.52 and 0.56) for the icon tile that the brief removes. One setup page got "broken content" (0.53, defect 0.64) for the eyebrow label that the brief removes.
- **Sample of the other verdicts.** The implementing agent compared the before and after images of 2 `intended` and 2 `unsure` screenshots, one of them an `unsure` where Jev flagged a problem with no region, and the after image of 3 more. The sample found no missed regression. The flag with no region matches a long URL that runs out of an alert box, but the base image has the same defect.

Thus the critic was cheap and fast, and it missed nothing in the sample, but it gave little signal: 96% of the verdicts were `unsure`, and each `regression` was an intended removal. Follow-ups: [CTX-1261](https://linear.app/ctxpipe/issue/CTX-1261) (estimate the spend by calls, not paths) and [CTX-1262](https://linear.app/ctxpipe/issue/CTX-1262) (the `unsure` rate on an explained change).

## Alternatives considered

- **Other Jev questions and options** (CTX-1262): the intended changes of the brief as a list in the state, fewer images, a `score` question, literal yes/no questions on spacing and hierarchy, and a higher `unsure` floor. Each one lost recall, gave more false flags, or turned real regressions into `intended`. The pull request of CTX-1262 has the measurements.
- **The cascade (Jev filters, an LLM decides).** The LLM overrode correct Jev regressions, and the recall fell to 0.74. An LLM that only explains a Jev regression is rule 13.
- **Each Jev regression blocks (`major`).** This was the first version of this ADR. It matched the measured 0.95 recall, but 2 of the 8 intended changes would block and need an override. The owner chose feedback over a gate.
- **Keep the Jev severity split at 0.8** (`major` from 0.8 blocks, `minor` below is a nit). A block recall of 0.79, and the same false-block problem.
- **GPT-6.1-Sol alone.** Recall 0.89, below the rule. It is a panel member, so its numbers can be too high. It costs about 25 times more and takes about 13 times longer.
- **Elephant or Mammoth.** Recall 0.79.
