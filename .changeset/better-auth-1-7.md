fix: Update Better Auth from 1.6.23 to 1.7.25, which includes the fix for advisory GHSA-965c-763c-88jm (CVE-2026-114607). ctxpipe does not enable the Magic Link plugin, so the attack in that advisory did not apply. A new migration adds the tables and nullable columns that the Better Auth 1.7 OAuth provider needs. Better Auth 1.7 does not start before this migration runs. MCP OAuth keeps the same behavior: an MCP host that registers an `http` loopback callback without an `application_type` can still register, and every client can still ask for a token for `{AUTH_BASE_URL}` and `{AUTH_BASE_URL}/mcp`. Linking an Atlassian account that another user already linked still offers the claim of that account, and "Unlink" and the email of a linked account in the account settings still work. The Atlassian link callback now finishes a link only in the browser session of the user who started it. The API and MCP refuse a key-bound (DPoP) access token, because they check no DPoP proof. After the update, a sign-in or an MCP OAuth authorization that started before the update cannot complete. Start it again.
