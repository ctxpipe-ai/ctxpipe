# Gate 4 Spec review — `0f207a22`

## Findings

1. **P1 — A newly allocated sandbox can be keyed as one SHA while containing another.** [`tanstack-workspace-chat.ts:541`](../../private/tmp/ctxpipe-recovery-01a07aba/apps/backend/src/domain/workspaces/tanstack-workspace-chat.ts) gives native `gitSource` the default branch, not `spec.source.ref`/the captured SHA. TanStack clones that branch before setup; then [`chat-runtime.ts:40`](../../private/tmp/ctxpipe-recovery-01a07aba/apps/backend/src/domain/workspaces/chat-runtime.ts) skips the only SHA fetch/checkout whenever `.git` already exists. A default-tip advance between revision capture and allocation therefore creates newer contents under the old `WorkspaceRevision` and native key. ADR-034:17 requires: “Definition identity includes remote, connection, generation, SHA, default branch, access, and chat image identity. Revision changes allocate separately,” and the plan requires proof for “stale credential/revision after prepare” (`workspace-chat-recovery.md:676-678`). Make the actual checkout land on the captured SHA and add a branch-advance-during-allocation native case.

2. **P1 — The final publication fence deliberately ignores a SHA change.** [`conversation-publish.ts:122`](../../private/tmp/ctxpipe-recovery-01a07aba/apps/backend/src/domain/workspaces/conversation-publish.ts) replaces the expected SHA/access with the current values before `sameWorkspaceRevision`. If desired SHA advances after route planning but before the final pre-push check, the old session is pushed; only the later metadata CAS notices and returns 409 after the remote side effect. This violates the same required stale-revision proof (`workspace-chat-recovery.md:676-678`). Fence the exact captured revision or admit an explicit rebase decision, and hold a real SHA advance immediately before push.

3. **P2 — Publication selects a revision by heartbeat rather than exact identity.** [`conversation-files.ts:45`](../../private/tmp/ctxpipe-recovery-01a07aba/apps/backend/src/domain/workspaces/conversation-files.ts) sorts every live row for the conversation and returns the newest heartbeat. Since ADR-034:11 says “Different revision keys remain distinct even for one thread,” an older in-flight ensure can heartbeat after the current revision. Both publish routes then repeatedly select that stale row and reject although the current sandbox exists. Select the row matching the captured current revision/native key; prove two coexisting rows with the older revision most recently touched.
