# UI (`apps/ui`) – agent instructions

When working in **`apps/ui`**, follow these instructions in addition to the root [AGENTS.md](../../AGENTS.md).

- **Product UI skill (required for screens)**: Before creating or substantially editing user-visible product UI in `apps/ui`, read and follow **[`.agents/skills/product-ui/SKILL.md`](../../.agents/skills/product-ui/SKILL.md)** and **[DESIGN.md](./DESIGN.md)**. Identity, information design, hierarchy, and anti-slop live there — not in the React skill. Prefer named Tailwind utilities over arbitrary values; see product-ui **Build**.
- **House radius**: Use `rounded-md` (0.2rem, from the `--radius-*` tokens in `src/styles.css`) for new or touched controls, menus, cards, dialogs, and data surfaces. Keep `rounded-full` for circles only. Do not add `rounded-none`.
- **React skill (required for components)**: Before creating or substantially editing React components, hooks, or UI data flow, read and follow **[`.agents/skills/react/SKILL.md`](../../.agents/skills/react/SKILL.md)**. It starts from the official [You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect) guidance; **data fetching** is **TanStack Query only** (no `useEffect` for load/refetch). Extend that skill file as team conventions accumulate.
- **Feel fast:** selected chrome (nav, tabs, panes, switchers) must update on the click. Set it in the click handler (`useUrgentValue`); do not wait for `useSearch()` / `useMatchRoute` / `loaderDeps`. `AppShell` lives on `/$orgSlug` — do not remount it for Home / Connectors / Workspace or in-page identity. Client loaders `prefetchQuery` only (workspace landing, conversation, blob, messages); do not `await`. SSR still includes the landing region in the first HTML (workspace default: files). Local `Suspense` for the region that is loading — the fallback is a **skeleton**, not `"Loading…"`. See the React skill **Feel fast** and product-ui **Plan states**.
- **React Aria first**: Interactive chrome uses [React Aria Components](https://react-spectrum.adobe.com/react-aria/components.html) — prefer `src/components/ui/*` (already RAC) when it matches, otherwise RAC primitives (`Tabs`, `Button`, `Link`, `Dialog`, …). Do not hand-roll `<button>` / `<a>` / tablists when RAC has the pattern. See product-ui **Build**.
- **Reuse shared components**: Before you style a block by hand (an alert, a banner, a status, a card, an empty state, a dialog frame), look for the shared component that shows the same meaning in `src/components/ui/` or in the feature, and use it. When the same hand-made block is in two or more places, make it one component. If a shared component does not fit, keep the custom block and put an inline comment on it that says why. A reviewer reads that comment and decides.
- **Storybook skill**: For Storybook conventions, colocated stories, MSW, and Storybook MCP, read and follow **[`.agents/skills/storybook/SKILL.md`](../../.agents/skills/storybook/SKILL.md)**.
- **Page stories**: Every route that renders a page has a page story. Tag it `page` and name its route: `tags: ["page"]` and `parameters: { route: "<TanStack route id>" }`, in the story `meta` or in one story. A layout, a redirect relay, or an API route has no page: add it with a reason to [`scripts/ci/page-story-exemptions.json`](../../scripts/ci/page-story-exemptions.json). `node scripts/ci/check-page-stories.mjs` (a policy check in CI) fails for a route with no story and no exemption. See the Storybook skill, "Page stories".
- **Screenshot baselines**: Each story has a committed baseline PNG in a `screenshots/` folder beside its story file. When you change how a story looks, or rename or delete a story, run `pnpm visual:check`, look at the changed images in `.ci-results/visual/`, and then run `pnpm visual:update --failed`. Commit the PNGs with the change. See the Storybook skill, "Screenshot baselines".
- **UI behavior tests**: Storybook interaction tests running in its Playwright-powered browser are the primary component and page behavior tests. Exercise real production components through story `play` functions and mock only external network boundaries with MSW. Do not add jsdom/happy-dom Vitest component tests. Keep Vitest for pure, non-DOM logic and for security / request-contract regressions at non-visual seams. Use direct Playwright only for integrated product journeys that cross Storybook's boundary.
- **Responsive layout — CSS-first**: Prefer Tailwind responsive classes (`md:`, `lg:`, `max-md:`, …) for show/hide, spacing, chrome, and breakpoints. Use JS (`matchMedia`, `useMediaQuery`, resize listeners) for responsive behaviour **only when CSS cannot express it** (e.g. open/closed drawer state, one-shot reads in a click handler). See product-ui **Build**.
- **Inline prose markup**: In user-facing copy inside components, use **plain JSX** for emphasis and code snippets (`<strong className="…">`, `<code className="…">`, etc.) in place. Do **not** add tiny helper functions or wrapper components whose only job is to wrap a string (e.g. `{lbl("Settings")}` or `ghStrong("Payload URL")`) — repeat the markup so the structure stays explicit at each call site.
