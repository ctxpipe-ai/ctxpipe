---
title: Organizations and access
description: How membership, source scope, and agent access fit together in ctxpipe.
---

An **organization** is the access boundary for repositories, connections,
conversations, graph context, and MCP. People can belong to more than one
organization and switch between them in the product.

## Organization context

- Each organization has a name and a unique URL slug.
- The organization switcher changes the active product context.
- Workspace, Chat, graph, and connector pages always operate inside the
  organization shown in the URL.
- MCP uses one URL for every organization. Each tool call names its
  organization in the `org` argument. The server checks that the connection
  includes that organization and that you are a member of it.

## Workspaces

An organization contains [Workspaces](/docs/workspaces). Each Workspace has one
workspace repository of knowledge and the code repositories it links. Members
of the organization can open every Workspace in it.

## Access follows both membership and source scope

Organization membership gives a user access to the ctxpipe organization. It does
not widen the upstream source scope:

- GitHub App repository selection controls which code ctxpipe can read.
- Connector scope controls which Linear, Notion, or Confluence content is
  mirrored.
- Repository permissions control who can read connector-generated Git content.
- Slack captures require the bot to be present in the channel.

Use roles to control administration inside ctxpipe, and keep provider permissions
and context-repository audiences deliberately narrow.
