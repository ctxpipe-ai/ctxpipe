---
title: How ctxpipe works
description: How knowledge moves from your sources into a Workspace, and out to people and agents.
---

ctxpipe keeps your team's knowledge as files in git, keeps the files current,
and builds an index so that people and agents get answers with sources.

## Flow

<Steps>
  <Step>
    ### Knowledge lives in a Workspace repository

    Each [Workspace](/docs/workspaces) has one git repository of Markdown
    knowledge. You and your agents change it like any other repository. Its
    files, and the links and claims in them, are the source of truth.
  </Step>

  <Step>
    ### ctxpipe keeps it current

    Background jobs commit to the Workspace repository for you:

    - [connectors](/docs/connections) mirror the Linear, Notion, Confluence,
      PagerDuty, and GitHub pull request content that you selected, and capture
      Slack threads when someone mentions the bot;
    - [linked repositories](/docs/workspaces/linked-repositories) are indexed
      again after each push, and ctxpipe writes the services, APIs, and
      libraries that it finds back as knowledge files.

    Each job makes one small commit to the default branch, with a clear
    message. You can review or revert each one.
  </Step>

  <Step>
    ### ctxpipe indexes each new commit

    When the default branch changes, ctxpipe reads the files and rebuilds the
    search index and the knowledge graph of the Workspace. This step never
    changes your files. The previous index serves until the new one is ready.
  </Step>

  <Step>
    ### People and agents ask

    [Workspace chat](/docs/workspaces/chat) answers from the knowledge, the
    graph, and the linked code, and proposes changes as a pull request. Coding
    agents read the same context through the [ctxpipe MCP](/docs/mcp/mcp-docs).
    The MCP tools return sources, not answers. Your agent reasons with its own
    model.
  </Step>
</Steps>

## Check important answers

Answers come from retrieved files, graph claims, and code search. Before an
important change, ask for the files behind an answer and read the current code.

<Callout title="Self-hosting">
  A self-hosted deployment works the same way, with your own backend, worker,
  codesearch, Postgres, graph database, and chat sandboxes. See
  [Self-hosting](/docs/self-hosting).
</Callout>
