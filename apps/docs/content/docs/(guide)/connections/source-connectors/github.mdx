---
title: GitHub connector
description: Why GitHub is the foundational source connector for ctx| and where to manage repositories.
---

GitHub is the first source connector most teams set up. It gives ctx| access to
the repositories your organization chooses, and those repositories become the
base for code search, file reads, knowledge graph ingestion, and agent context.

GitHub also supports other connectors. When a source like Confluence, Linear, or
Notion needs to become visible and reviewable, ctx| syncs selected content into a
GitHub repository first, then ingests it through the same Git-backed pipeline.
For Linear and Notion, the configuration pull request branch is the draft scope
and the target branch becomes the live scope after merge.

You can connect GitHub during onboarding, or later from the **Connectors** page.

<Callout title="Hosted and self-hosted Apps are different">
  Hosted ctx| supplies the managed GitHub App. A self-hosted deployment must
  create and own its own App, private key, webhook secret, and installation.
  Operators should complete [Self-host GitHub](/docs/self-hosting/github) before
  users follow this page.
</Callout>

## Setup flow

<Steps>
  <Step>
    ### Start the GitHub connection

    Start from onboarding if you are setting up ctx| for the first time. If your
    organization already exists, open **Connectors** and choose GitHub.
  </Step>

  <Step>
    ### Authorize GitHub access

    GitHub asks you to install or authorize the ctx| GitHub App for a GitHub
    account or organization. You may need a GitHub organization owner to approve
    the installation if you do not have permission to install apps yourself.
  </Step>

  <Step>
    ### Choose access in GitHub

    GitHub asks which repositories the App may read. That grant is access only.
    You can start narrow and expand the App's repository access later.
  </Step>

  <Step>
    ### Choose a workspace

    After the App is installed, create a workspace or open an existing one.
    Link repositories from that workspace's Settings. ctx| ingests a repository
    when you attach it, so it can power search, Chat, MCP, and the knowledge
    graph.
  </Step>
</Steps>

## What GitHub enables

- Single-repo and cross-repo code search.
- Repository ingestion into your organization's knowledge system.
- Repo-native docs, ADRs, `AGENTS.md`, skills, and standards as agent context.
- Target repositories for synced sources such as Confluence and Linear.
- Pull requests for ctx| configuration, including MCP setup where supported.
- Optional mirroring of **merged** pull requests (conversation, reviews, and
  changed paths — not diffs) into your context repository. After ingest, the
  knowledge graph locates each changed path as a `File` (shared with
  source-repository extract) and records `ADDED` / `MODIFIED` / `REMOVED` /
  `RENAMED` edges from the pull request dated at merge, `PullRequest TARGETS`
  the source repository, `File PART_OF` the owning service when that
  repository is already classified, and `PullRequest REFERENCES Issue` when
  the title, body, or branch names a Linear issue.

Selecting GitHub repositories also captures **merged** pull requests into the
organization context repository (`ctxpipe-context`, or the repo already used
by Linear, Notion, or Slack). ctx| writes `github/config.yaml` and backfills
up to 200 newest updated merged pull requests per selected repository. No
separate toggle. If the organization has no context repository yet, capture
starts when one is bound.
