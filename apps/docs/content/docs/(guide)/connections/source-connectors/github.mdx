---
title: GitHub connector
description: Why GitHub is the foundational connector for ctx| and what it enables.
---

GitHub is the first connector most teams set up. The ctx| GitHub App hosts
your [Workspaces'](/docs/workspaces) repositories and gives ctx| access to the
code repositories you link for search and extraction.

Other connectors build on it. Confluence, Linear, Notion, and PagerDuty write
selected content into a Workspace's GitHub repository. Their configuration
pull request is the draft scope; the default branch becomes the live scope
after merge.

You can connect GitHub during onboarding, or later from the **Connectors** page.

<Callout title="Hosted and self-hosted Apps are different">
  Hosted ctx| supplies the managed GitHub App. A self-hosted deployment must
  create and own its own App, private key, webhook secret, and installation.
  Operators should complete [Self-host GitHub](/docs/self-hosting/github) before
  users follow this page.
</Callout>

## Setup flow

<Steps>
  <Step>
    ### Start the GitHub connection

    Start from onboarding if you are setting up ctx| for the first time. If your
    organization already exists, open **Connectors** and choose GitHub.
  </Step>

  <Step>
    ### Authorize GitHub access

    GitHub asks you to install or authorize the ctx| GitHub App for a GitHub
    account or organization. You may need a GitHub organization owner to approve
    the installation if you do not have permission to install apps yourself.
  </Step>

  <Step>
    ### Choose access in GitHub

    GitHub asks which repositories the App may read. That grant is access only.
    You can start narrow and expand the App's repository access later.
  </Step>

  <Step>
    ### Choose a workspace

    After the App is installed, create a Workspace or open an existing one.
    Link code repositories from that Workspace's **Settings**. ctx| indexes a
    repository when you link it, so it can power search, chat, MCP, and the
    knowledge graph.
  </Step>
</Steps>

## What GitHub enables

- Workspace repositories that ctx| can read and write.
- Code search and extraction across linked repositories.
- Repo-native docs, ADRs, `AGENTS.md`, skills, and standards as agent context.
- Pull requests for connector configuration, Workspace chat changes, and MCP
  setup.
- Mirroring of **merged** pull requests (conversation, reviews, and changed
  paths, not diffs) into a Workspace. After indexing, the
  knowledge graph locates each changed path as a `File` (shared with
  source-repository extract) and records `ADDED` / `MODIFIED` / `REMOVED` /
  `RENAMED` edges from the pull request dated at merge, `PullRequest TARGETS`
  the source repository, `File PART_OF` the owning service when that
  repository is already classified, and `PullRequest REFERENCES Issue` when
  the title, body, or branch names a Linear issue.

### Merged pull requests follow linked repositories

Linking a GitHub repository to a Workspace is the only setup. Its merged pull
requests are written under `github/pulls/<owner>/<repo>/` in that Workspace's
repository:

- **When you link** the repository, ctx| backfills up to 200 of its most
  recently updated merged pull requests.
- **After that**, each merged pull request, and each later review or comment on
  it, is mirrored as GitHub reports it.
- **Several Workspaces** can link the same repository. Each one gets its own
  copy of the pull requests.
- **When you unlink** the repository, new pull requests stop arriving. Files
  already mirrored stay in the Workspace's git history and tree until you
  delete them.

Draft and unmerged pull requests are not mirrored. There is no toggle and no
configuration file.
