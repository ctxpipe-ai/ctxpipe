---
title: GitHub connector
description: Why GitHub is the foundational connector for ctx| and what it enables.
---

GitHub is the first connector most teams set up. The ctx| GitHub App hosts
your [Workspaces'](/docs/workspaces) repositories and gives ctx| access to the
code repositories you link for search and extraction.

Other connectors build on it. Confluence, Linear, Notion, and PagerDuty write
selected content into a Workspace's GitHub repository. Each Workspace holds a
source file for each source, at `sources/<provider>/…md`. The pull request that
adds the source file is the draft scope. The default branch has the live scope
after the merge.

Connect GitHub from the **Get started** guide on Home, or from the **Connectors** page.

<Callout title="Hosted and self-hosted Apps are different">
  Hosted ctx| supplies the managed GitHub App. A self-hosted deployment must
  create and own its own App, private key, webhook secret, and installation.
  Operators should complete [Self-host GitHub](/docs/self-hosting/github) before
  users follow this page.
</Callout>

## Setup flow

<Steps>
  <Step>
    ### Start the GitHub connection

    In a new organization, select **Connect GitHub** in the **Get started**
    guide on Home. You can also open **Connectors** and choose GitHub.
  </Step>

  <Step>
    ### Authorize GitHub access

    GitHub asks you to install or authorize the ctx| GitHub App for a GitHub
    account or organization. You may need a GitHub organization owner to approve
    the installation if you do not have permission to install apps yourself.
  </Step>

  <Step>
    ### Choose access in GitHub

    GitHub asks which repositories the App may read. That grant is access only.
    You can start narrow and expand the App's repository access later.
  </Step>

  <Step>
    ### Choose a workspace

    After the App is installed, create a Workspace or open an existing one.
    Link code repositories from that Workspace's **Settings**, under
    **Sources**. Each link is a source file at
    `sources/github/<owner>/<name>.md`. A pull request adds it. After you merge
    it, ctx| indexes the repository, so it can power search, chat, MCP, and the
    knowledge graph.
  </Step>
</Steps>

## What GitHub enables

- Workspace repositories that ctx| can read and write.
- Code search and extraction across linked repositories.
- Repo-native docs, ADRs, `AGENTS.md`, skills, and standards as agent context.
- Pull requests for source changes, Workspace chat changes, and MCP setup.
- Mirroring of **closed** pull requests, merged or not (conversation,
  reviews, and changed paths, not diffs), into a Workspace. After indexing,
  the knowledge graph records `PullRequest TARGETS` the source repository and
  `PullRequest REFERENCES Issue` when the title, body, or branch names a
  Linear issue. For a merged pull request, the graph also locates each changed
  path as a `File` (shared with source-repository extract) and records
  `ADDED` / `MODIFIED` / `REMOVED` / `RENAMED` edges from the pull request
  dated at merge, and `File PART_OF` the owning service when that repository
  is already classified. A merged pull request `RESOLVES` an issue in place of
  `REFERENCES` when its branch names the issue, or when a closing keyword
  (`fixes`, `closes`, `resolves`, `completes`, and their other forms) comes
  directly before the issue identifier or its Linear URL. A pull request
  closed without a merge changed nothing, so it has no `File` edges.

### Closed pull requests follow linked repositories

Linking a GitHub repository to a Workspace is the only setup. Its closed pull
requests, merged or not, are written under `github/pulls/<owner>/<repo>/` in that Workspace's
repository:

- **When you link** the repository, from **Settings** or by adding its source
  file with Git, ctx| backfills up to 200 of its most recently updated closed
  pull requests.
- **After that**, each pull request that closes, and each later review or
  comment on it, is mirrored as GitHub reports it. The file records `merged`
  and `mergedAt`, so you can tell a merge from a close without a merge.
- **Several Workspaces** can link the same repository. Each one gets its own
  copy of the pull requests.
- **When you unlink** the repository, new pull requests stop arriving. Files
  already mirrored stay in the Workspace's git history and tree until you
  delete them.

Draft and open pull requests are not mirrored. There is no toggle and no
configuration file.
