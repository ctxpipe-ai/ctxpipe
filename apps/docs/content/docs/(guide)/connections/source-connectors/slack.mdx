<Callout title="Fully managed app flow">
  This page covers the fully managed ctx| app, where one Slack app is owned by
  the deployment. Self-hosted operators must create and configure their own Slack
  app first. See [Self-host Slack](/docs/self-hosting/slack).
</Callout>

The **Slack connector** lets you push **specific engineering conversations** into
repo-backed context for ctx|. It does **not** mirror whole channels, index the
workspace, or sync banter in the background.

Connect Slack to ctx|, bind a context repository, then trigger the bot in Slack
when a thread is worth keeping — for example `@ctxpipe please capture this
thread`. ctx| snapshots that thread as Markdown under `slack/channels/` and
ingests it through the normal repository pipeline.

## Two ways to work with Slack

| Approach | Job |
| --- | --- |
| **ctx\| Slack connector** (this page) | Durable, reviewed context: capture chosen threads into git for indexing |
| **[Slack MCP server](https://docs.slack.dev/ai/slack-mcp-server)** | Query-time access: search and read the workspace from your developer agent |

If you want general access to your Slack workspace from tools such as Cursor or
Claude, add Slack’s MCP server to your developer environment. See Slack’s
[Guide to Model Context Protocol in Slack](https://slack.com/help/articles/48855576908307-Guide-to-Model-Context-Protocol-in-Slack).
ctx| does not replace Slack MCP, and Slack MCP does not create the same
git-native, ingested context that the connector does.

## Prerequisites

- An active GitHub connection in ctx|.
- A context repository (we recommend [`ctxpipe-context`](/docs/connections/context-repository)).
- Permission to install the ctx| Slack app in the workspace.
- Ability to `/invite` the bot into any channel where you will capture threads.

## Setup flow

<Steps>
  <Step>
    ### Start from Connectors

    Open **Connectors**, choose **Add connection**, then **Slack**.
  </Step>

  <Step>
    ### Authorise the workspace

    Complete the Slack OAuth popup. ctx| stores an encrypted bot token for that
    workspace connection.
  </Step>

  <Step>
    ### Bind a context repository

    Select the repository that should receive captured threads. ctx| uses its
    default branch. Prefer a separate private repo when captures may include
    sensitive private-channel content. The ctx| GitHub App must have access to
    the selected repository and permission to write contents.
  </Step>

  <Step>
    ### Capture threads in Slack

    In each channel where you want capture, run `/invite @ctxpipe`, then mention
    the bot in the thread (or on the message that should start a one-message
    thread):

    ```text
    @ctxpipe please capture this thread
    ```

    ctx| replies in the thread with **ctx| agent capturing engineering
    context…**, then updates that message to **Engineering context captured**
    when the snapshot is committed. Later replies are not mirrored unless you
    mention the bot again on that thread.
  </Step>
</Steps>

## What is captured

- Thread-first Markdown under `slack/channels/<slug>--<channelId>/threads/…`
- File and image attachments as Markdown links to the Slack permalink (no binaries in git)
- The in-thread status reply is excluded from the snapshot

## What is out of scope (v1)

- Continuous channel mirroring or history backfill
- Direct messages and multi-party DMs
- Automatic refresh when someone replies after a capture
- Writing conversational replies back to Slack
- Full video or file binary archival (attachments are permalink stubs)

## Troubleshooting

### Capture does nothing

Confirm the connector status is **Connected** (repository bound), the bot is
invited to the channel (`/invite @ctxpipe`), and you used an `@` mention of the
bot (not only the word “ctxpipe” in plain text). Self-hosted operators should
confirm Event Subscriptions include **`app_mention`** — see
[Self-host Slack](/docs/self-hosting/slack).

### Private channel

Private channels work only after the bot is a member. Direct messages are not
supported in v1.
