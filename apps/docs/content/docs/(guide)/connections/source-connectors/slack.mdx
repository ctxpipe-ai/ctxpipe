<Callout title="Fully managed app flow">
  This page covers the fully managed ctx| app, where one Slack app is owned by
  the deployment. Self-hosted operators must create and configure their own Slack
  app first. See [Self-host Slack](/docs/self-hosting/slack).
</Callout>

The **Slack connector** promotes **durable engineering context** — decisions,
incidents, and design debates — from Slack into a [Workspace](/docs/workspaces).
It does **not** mirror whole channels, index the workspace, or sync banter in
the background. Captures are **auditable** (git history records who captured,
when, and which Slack thread), not a reviewed pull-request gate. The channel
list of a Workspace is the reviewed part: a pull request adds it.

Connect Slack to ctx|, add it to a Workspace with the channels to capture, then
**@mention** the bot in Slack. Mentioning the bot starts a small in-thread agent. Ask it to **capture
this**, or mention it with no extra text, to snapshot the thread as Markdown
under `slack/channels/<channelId>/` in each Workspace that has the channel. Later mentions on the same thread **update the same
file**. Other intents get a short capability reply; v1 does not answer product
questions in Slack.

A Slack workspace can be connected to **one** ctx| organization.

## Two ways to work with Slack

| Approach | Job |
| --- | --- |
| **ctx\| Slack connector** (this page) | Durable, auditable context: capture chosen threads into git for indexing |
| **[Slack MCP server](https://docs.slack.dev/ai/slack-mcp-server)** | Query-time access: search and read the live workspace from your developer agent |

If you want general access to your Slack workspace from tools such as Cursor or
Claude, add Slack’s MCP server to your developer environment. See Slack’s
[Guide to Model Context Protocol in Slack](https://slack.com/help/articles/48855576908307-Guide-to-Model-Context-Protocol-in-Slack).
ctx| does not replace Slack MCP, and Slack MCP does not create the same
git-native, ingested context that the connector does.

## Prerequisites

- An active GitHub connection in ctx|.
- A [Workspace](/docs/workspaces) whose repository the ctx| GitHub App can write
  to. The repository must use format 2 or higher. If it does not, the Workspace
  shows **Upgrade this Workspace first**. See
  [Upgrades](/docs/workspaces/settings#upgrades).
- Permission to merge the pull request that adds the source.
- Permission to install the ctx| Slack app in the workspace.
- Ability to `/invite` the bot into any channel where you will capture threads.

## Setup flow

<Steps>
  <Step>
    ### Start from Connectors

    Open **Connectors**, choose **Add connection**, then **Slack**.
  </Step>

  <Step>
    ### Authorize the workspace

    Complete the Slack OAuth popup (**Authorize Slack workspace**, then
    **Connect Slack**). ctx| stores an encrypted bot token for that workspace
    connection. One Slack workspace maps to one ctx| org. The connection holds
    authorization only. If GitHub is not connected, the wizard shows **Connect
    GitHub** next.
  </Step>

  <Step>
    ### Choose Workspaces

    The next step is **Choose Workspaces**. Select the Workspaces that get
    captured threads. Then select the channels for each Workspace. When you
    select more than one Workspace, choose **Same scope for each Workspace** or
    **A different scope for each Workspace**. Prefer a separate Workspace with a
    private repository when captures can include private-channel content.

    Choose **Add to Workspaces**. ctx| opens one pull request for each
    Workspace. Each pull request adds `sources/slack/<name>.md` with the channel
    ids. The dialog shows **Merge the pull request** (or **Merge the pull
    requests**). After each merge, it shows **Pull request merged**.

    A capture starts only after the merge. Until then, a mention in a new
    channel replies that no Workspace has the channel.
  </Step>

  <Step>
    ### Capture threads in Slack

    In each channel where you want capture, `/invite` the bot (use its Slack
    **@handle** from the connector card), then mention it **inside an existing
    thread** — a channel-top-level mention is refused:

    ```text
    @your-bot-handle capture this
    ```

    A bare mention with no extra text also captures. ctx| replies in the thread
    with **ctx| agent working…**, then updates that message (or posts a new
    reply if the update cannot land) to **Engineering context captured into**
    and a link to each Workspace that got the thread. The link opens the
    captured thread file in that Workspace, where you can edit it. If you asked
    for something else, ctx| gives a short capability reply. Later replies are not mirrored unless you mention the bot
    again on that thread (that recapture overwrites the same snapshot).
  </Step>
</Steps>

## What is captured

ctx| saves a thread to each Workspace whose Slack source, with the status
**OK**, has the channel of the thread. It writes one commit for each Workspace.

- Thread-first Markdown at
  `slack/channels/<channelId>/threads/<yyyy>/<mm>/<threadTs>/thread.md`
- Frontmatter identity: `captured_at`, Slack permalink, channel and thread ids,
  and `captured_by` handle + name (never a Slack user id)
- Readable names for message authors and inline user mentions
- Files and explicit embedded media copied into the thread's `assets/` directory
  with relative Markdown links. Private, signed, and expiring download URLs are
  never written to git.
- Assets over 25 MiB, a thread over its 100 MiB asset budget, or unsafe/failed
  downloads leave a source permalink or textual stub instead
- The in-thread status reply is excluded from the snapshot
- Threads longer than 500 messages are truncated (oldest kept); Slack status
  calls that out. Hosted deployments share one Slack app quota.

## What is out of scope (v1)

- Continuous channel mirroring or history backfill
- Direct messages and multi-party DMs
- Automatic refresh when someone replies after a capture
- Slack Q&A / retrieval in-thread (future tool on the same agent)
- Deleting git history when you uninstall Slack. Uninstall marks the connection
  revoked; captured files stay in the repository.
- Deleting captured threads when you remove a channel from a source. Captured
  threads stay, because ctx| cannot fetch a thread again.

## Troubleshooting

### Capture does nothing

Confirm the connector status is **Connected**, a source with the status **OK**
lists the channel, the bot is invited to the channel, and you used Slack
autocomplete to **@mention** the bot. If no Workspace has the channel, the bot
replies "Nothing captured: no Workspace has this channel." Add the channel to a
Slack source in the Workspace **Settings**, merge the pull request, then mention
the bot again.
Bare mention or “capture this” snapshots the thread. Self-hosted operators
should confirm Event Subscriptions include **`app_mention`** and that
`MODEL_PROVIDER*` is set so the mention agent can interpret extra text — see
[Self-host Slack](/docs/self-hosting/slack). If the Slack app's bot scopes were
changed after installation, re-authorize the workspace; existing bot tokens do
not gain new permissions automatically.

### The source shows a status other than OK

Each source row in **Settings** shows **OK**, **Not valid**, **Connection
missing**, or **Out of access**, with a reason. See
[Source status](/docs/workspaces/settings#source-status). A source stays **OK**
when the bot is not in a channel yet. The reason tells you to invite the bot.

### Private channel

Private channels work only after the bot is a member. Direct messages are not
supported in v1.
