---
title: Connections
description: How connections and sources bring content from your tools into a Workspace as Markdown files that you can review.
---

A **connection** gives ctxpipe access to one of your tools. A **source** tells
one [Workspace](/docs/workspaces) what to read through a connection. ctxpipe
writes the content into the Workspace repository as Markdown files, so you can
read, review, and keep each file that ctxpipe and your agents use.

- A **connection** holds only the authorization: the OAuth grant, API access token, or GitHub
  App installation, and its webhooks. An organization owner or admin adds it
  one time for the organization, on **Connectors**.
- A **source** is one Markdown file in a Workspace, at
  `sources/<provider>/<name>.md`. It names the connection, the scope (for
  example Linear teams or Notion pages), and an optional description.

One connection can feed many Workspaces. Each Workspace has its own source file
and its own scope.

## Available connectors

| Connector | Type | What enters the Workspace | Scope |
| --- | --- | --- | --- |
| [GitHub](/docs/connections/source-connectors/github) | Git source | Linked repositories, indexed for code search and extraction, and their issues and closed pull requests | One repository, and an optional `ref` |
| [Linear](/docs/connections/source-connectors/linear) | Scoped mirror | Issues, projects, cycles, and related content | Teams and projects |
| [Notion](/docs/connections/source-connectors/notion) | Scoped mirror | Pages and databases | Pages and databases |
| [Confluence](/docs/connections/source-connectors/confluence) | Scoped mirror | Spaces and pages | Spaces, with all pages or a page list |
| [PagerDuty](/docs/connections/source-connectors/pagerduty) | Scoped mirror | Incidents of the selected services | Services |
| [Buildkite](/docs/connections/source-connectors/buildkite) | Scoped mirror | The latest 25 finished builds of the selected pipelines | Pipelines |
| [Slack](/docs/connections/source-connectors/slack) | Capture on request | One thread at a time, when someone mentions the bot | Channels |
| [Plain git](/docs/workspaces/linked-repositories#plain-git-repositories) | Git source | A public repository on any git host, with no connection | A URL |

ctxpipe indexes the docs in linked repositories with the code: README files,
`docs/**`, ADRs, `AGENTS.md`, and skills.

The important difference is the scope. A scoped mirror keeps an approved
subset current. Slack has no history backfill and no channel mirror: a person
captures one thread when the team needs it later.

## Connect GitHub first

The ctxpipe GitHub App lets ctxpipe read and write Workspace repositories,
index linked code repositories, and open the pull requests for source changes,
upgrades, and Workspace chat. The other connectors write into a Workspace
repository on GitHub, so they need it too. See the
[GitHub connector](/docs/connections/source-connectors/github).

## Add a tool to a Workspace

Before you start, make sure that:

- you are an organization owner or admin;
- the ctxpipe GitHub App can write to the Workspace repository, and the
  repository uses format 2 or higher (see
  [Upgrades](/docs/workspaces/settings#upgrades));
- you can merge pull requests in the Workspace repository.

<Steps>
  <Step>
    ### Connect the tool

    Open **Connectors**, choose **Add connection**, then choose the tool.
    Follow the authorization steps for the tool. Buildkite uses an API access
    token. The connector page has the details for each tool.
  </Step>

  <Step>
    ### Add it to Workspaces

    The next step is **Add to Workspaces** (**Choose Workspaces** for Linear and
    Slack). Select the Workspaces, then select the scope. For more than one
    Workspace, choose **Same scope for each Workspace** or **A different scope
    for each Workspace**. Then choose **Add to Workspaces**.

    You can do this later. Expand the connector on **Connectors** and choose
    **Add to a Workspace** (or **Manage**), or use **Add** under **Sources** in
    the **Settings** of a Workspace.
  </Step>

  <Step>
    ### Merge the pull requests

    ctxpipe opens one pull request for each Workspace. Each pull request adds the
    source file. Review the scope and who can read the repository, then merge.
    The source does not sync before the merge.
  </Step>

  <Step>
    ### Wait for the first sync

    After the merge, ctxpipe makes the first mirror. The Workspace then indexes
    the new files like any other knowledge file.
  </Step>
</Steps>

To change what a Workspace reads, edit, rename, or remove its source. See
[Workspace settings](/docs/workspaces/settings#sources).

## How content stays current

- **Webhooks.** Linear, Notion, Confluence, and PagerDuty tell ctxpipe when
  content changes. ctxpipe updates the files of the sources whose scope
  includes the change. Events that arrive before a source is live are skipped.
- **Buildkite webhooks.** A finished build starts a full sync after a 10-minute
  window. More events in that window share the same sync.
- **Daily full sync.** Once a day, ctxpipe syncs each connection that has a
  source with the status **OK**. This sync finds content that the provider
  deleted, and content that a webhook missed.
- **Sync now.** The menu of the connector on **Connectors** has **Sync now** for
  Confluence, Linear, Notion, PagerDuty, and Buildkite. It starts the same full sync at
  once. Only an owner or admin sees it.

Do not edit mirrored files by hand. The next sync overwrites them. When you
remove a source, the next sync deletes its files in one commit. Git history
keeps them.

**Remove connector**, in the same menu, removes the authorization. The sources
of the connection stop syncing. The source files and the files that ctxpipe
committed stay in git.

## Git is the review boundary

A source file changes only through a pull request that a person merges. The
pull request is the review of the scope. No agent can add or change a source
without that review.

- **Scoped mirrors** write Markdown under the folder of the provider, for
  example `linear/` or `notion/`, in each Workspace repository.
- **Slack** captures commit directly to the default branch of each Workspace
  that has the channel. The mention in the thread is the approval, and git
  history records it.

Each person who can read the Workspace repository can read its mirrored
content. Use separate Workspaces when different sources need different
audiences.

## Scope limits

Each source has a maximum number of items, so that one sync stays inside the
API rate limits of the provider. For more items, add a second source with the
same connection.

| Source | Maximum in one source |
| --- | --- |
| **Confluence** | 100 spaces, and 500 selected pages in one space (select all pages for more) |
| **Slack** | 100 channels |
| **Linear** | 50 teams and 100 projects |
| **Notion** | 100 root pages and 100 databases |
| **PagerDuty** | 100 services |
| **Buildkite** | 50 pipelines |

A GitHub source holds one repository, so it has no limit.

## Troubleshooting

| Problem | What to do |
| --- | --- |
| Authorization fails | Allow popups and try again. On a self-hosted deployment, ask the operator to check the OAuth app of the provider and its callback URL. |
| **Add to Workspaces** shows an error | The message names the cause: **Upgrade this Workspace first** (see [Upgrades](/docs/workspaces/settings#upgrades)), **This Workspace is read-only** (see [Write access](/docs/workspaces/settings#write-access)), or **Ask an admin to choose what this source syncs** (your role). |
| No pull request appears | Make sure that the GitHub App can write to the Workspace repository. Close the dialog and try again. |
| The source status is not **OK** | Read the status and the reason in **Settings**. See [Source status](/docs/workspaces/settings#source-status). |
| Changes in the tool do not arrive | Choose **Sync now**. If changes still do not arrive, ask the operator to check the webhook of the provider. |
| A sync fails | Choose **Sync now**. If it fails again, ask the operator to check the worker logs, the GitHub write access, and outbound access to the API of the provider. |
| The authorization was revoked | Reconnect the tool from its connector card. Updates stop until you do. |

## More connectors

We plan more connectors for engineering systems, for example Jira and Sentry.
On a self-hosted deployment, the operator must configure the OAuth app and the
webhooks of a provider before its connector works. See the source connector
pages under [Self-hosting](/docs/self-hosting). Buildkite uses a token for each
connection. See [Self-host Buildkite](/docs/self-hosting/buildkite).

## Agent access is separate

MCP clients are not connections. Claude Code, Cursor, CI agents, and other MCP
clients connect to ctxpipe through the MCP endpoint. See
[Connect your agent](/docs/mcp/mcp-docs).
