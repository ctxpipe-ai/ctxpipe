---
title: How indexing works
description: What ctx| builds after content reaches a Workspace, and how to read indexing states.
---

**Indexing** turns a Workspace's files and linked code into something chat,
search, the graph, and MCP can use. It runs in the background after every
change, so new content can take a few minutes to show up in answers.

## Two kinds of indexing

<Steps>
  <Step>
    ### The workspace repository

    When the workspace repository's default branch changes, ctx| reads the
    knowledge files at that commit and rebuilds the Workspace's index: units,
    links and claims for the graph, and embeddings for search. It never edits
    files and never calls an extraction model at this step. The previous index
    keeps serving until the new one is ready.
  </Step>

  <Step>
    ### Linked repositories

    When a linked repository changes, ctx| checks out its default branch,
    builds code search and code navigation, and uses models to extract
    services, APIs, libraries, infrastructure, and instructions. The extracted
    knowledge is committed to the workspace repository as knowledge files,
    which triggers the first kind of indexing.
  </Step>
</Steps>

## Read the status

**Settings** in each Workspace shows whether the Workspace index is ready and
the status of each linked repository:

| Status | Meaning | What to do |
| --- | --- | --- |
| **Pending** | Linked, not yet indexed. | Wait. |
| **Indexing** | ctx| is building search and extracting knowledge. | Answers may be incomplete. |
| **Indexed** | The current commit is indexed. | Ask a known question in chat or MCP. |
| **Indexed with issues** | Search works, but part of the index failed. The reason is shown. | Check the reason. A push to the repository re-runs indexing. |

A Workspace index that fails keeps serving the last good version. Fix the
cause, often malformed front matter or lost repository access, and push again.

<Callout type="warn" title="Indexed does not mean infallible">
  Indexing builds search and graph data from files and model-extracted claims.
  It does not certify an answer. Ask for files and verify risky decisions
  against current source.
</Callout>

## Three layers

Content in a Workspace lives in three layers:

1. **Files**: the bytes in git, in the workspace repository or a linked
   repository.
2. **Search**: the text and code index over those files. Chat and MCP can
   retrieve anything here.
3. **Graph**: typed nodes and relationships from links, claims, and `kind`
   front matter. Mirrored connector content becomes `Issue`, `Thread`,
   `PullRequest`, and similar nodes. It is never treated as instructions.
   Cross-tool links are joined by URL or identifier, not guessed.
