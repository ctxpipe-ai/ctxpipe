---
title: Workspace settings
description: Manage the sources of a Workspace, and read its write access, upgrade, and status messages.
---

Open a Workspace and choose the **Settings** tab. The pane has two tags at the
top and these groups:

| Part | What it holds |
| --- | --- |
| Write access tag | Whether ctx\| can save changes. See [Write access](#write-access). |
| Hydrate tag | The state of the last read of the repository. See [Hydrate and skipped files](#hydrate-and-skipped-files). |
| **General** | **Name** and **URL name**. |
| **Repositories** | The **Context repository** and the **Root folder**. |
| **Sources** | The source files of the Workspace, grouped by provider. |
| **Upgrades** | The repository format and the upgrade items. |
| **Danger zone** | **Delete Workspace**. |

## General

- **Name**: shown in the sidebar and to your team. ctx| stores it in `AGENTS.md`.
- **URL name**: used in the web address of the Workspace. If you change it, old
  links stop working. ctx| does not keep the old name as an alias.

Choose **Save** to apply a change. The message "Workspace updated" confirms it.

## Repositories

- **Context repository**: the GitHub repository where the Workspace keeps its
  files. It is also called the Workspace repository. This page says "the
  context repository". Choose the edit button (**Edit context repository**) to
  change it. The dialog **Context repository** says "You keep this Workspace
  and its conversations. Files in the old repository stay where they are." It
  has the same tabs as
  [Create a Workspace](/docs/workspaces/create-workspace): **Select GitHub**,
  **Create on GitHub**, and **Paste URL**. Choose **Save**. Until the new
  repository finishes loading, the pane says that answers still come from the
  old repository.
- **Root folder**: the folder of the repository that holds the Workspace. Choose
  **Save root folder** to apply a change. The message "Root folder saved"
  confirms it. See [Root folder](/docs/workspaces/create-workspace#root-folder).

## Write access

ctx| writes to the context repository through the ctx| GitHub App. The tag at
the top of the pane shows the result of the last check. The tag next to it shows
the [hydrate status](#hydrate-and-skipped-files).

| Tag | Meaning |
| --- | --- |
| **Can save changes** | The GitHub App can push to the repository. |
| **Changes by pull request** | The default branch is protected. A conversation pushes its own branch and opens a pull request. Source changes use pull requests too. This is a normal state, not a fault. |
| **Checking write access** | ctx\| is checking whether the GitHub App can push. The pane checks again by itself. |
| **Could not check write access** | GitHub returned an error or a rate limit. Choose **Check again**. |
| **Read-only** | ctx\| cannot write. Search, chat, and the graph keep working on the latest commit. The pane shows the reason. |

If the check takes longer than usual, the pane shows **Still checking write
access** with the text "The check takes longer than usual." and **Check again**.

A **Read-only** Workspace shows an alert with one of these reasons:

| Reason | What to do |
| --- | --- |
| "This remote is not GitHub. v1 can hydrate, search, and chat, but cannot commit or push. Relink to a GitHub repository the App can write." | Select a GitHub repository as the context repository. |
| "GitHub is not connected for this organization. An owner or admin must install the GitHub App and add this repository to the installation." | Connect GitHub on **Connectors**. Then choose **Select the repository again** in the alert. |
| "This repository is not in the GitHub App installation. An installation owner or admin must add it, then refresh." | Add the repository to the installation in GitHub. |
| "The GitHub App cannot write to this repository. Grant Contents: write so ctxpipe can push a conversation branch." | Grant **Contents: Read and write** to the GitHub App. |
| "This Workspace needs a newer ctx\| version. ctx\| can read it, but it cannot write to it until you upgrade ctx\|." | The repository format is newer than this ctx\| version. Upgrade ctx\|. See [Repository format](#repository-format). |
| "The file .ctxpipe/workspace.yaml is not valid. ctx\| can read this Workspace, but it cannot write to it until the file is repaired." | Repair the format file in the repository. |

For a **Read-only** reason, the alert adds: "After you fix it, reload this page.
ctxpipe checks again at most once a minute." The button **Check again** shows
on the alert **Could not check write access** and on the alert **Still checking
write access**. It does not show on a **Read-only** alert.

## Hydrate and skipped files

Hydrate is the step where ctx| reads the files of the context repository at a
commit and builds the search index and the graph. The second tag at the top of
the pane shows its status:

| Tag | Meaning |
| --- | --- |
| **Ready** | ctx\| read the latest commit. |
| **Hydrate pending** | ctx\| did not start yet. |
| **Hydrating** | ctx\| is reading a commit. The previous index keeps serving. |
| **Loading failed** | ctx\| could not read the repository. |

Before the first hydrate ends, the Workspace page shows **Preparing** and the
name of the Workspace, with the steps **Fetching repository** and **Reading
knowledge**. If ctx| does not know
the latest commit, the page says so and shows **Try again**. If the first read
fails, the page shows **Prepare failed** and **Could not prepare the Workspace**
with the reason and **Try again**. When the reason starts with "ctx| has no access
to this repository.", the alert also has **Open Connectors**.

When ctx| skips files, **Settings** shows **Hydrate skipped N files** (or **1
file**) with the text "Chat, MCP, search, and the graph do not use these files.
Fix each file and push the change to the default branch." Each row gives the path
and the reason. Select the path to open the file in **Files**. For the reasons,
see [Knowledge files](/docs/workspaces/knowledge-files#skipped-files).

## Sources

A source tells the Workspace what to read through a connection. Each source is
one Markdown file at `sources/<provider>/…md` in the context repository. The
file holds the provider, the connection, and the scope in its front matter. The
body is an optional description. The path of the file is the identity of the
source.

The file on the default branch is the live scope. The file on the branch of an
open pull request is a draft scope. ctx| keeps no second copy of the scope
outside Git.

The **Sources** group shows one line of summary, for example "3 sources from 2
connectors · 1 needs attention · 1 change awaiting merge". The note "Saved as one
file for each source in `sources/`" names the folder. The table has the columns
**Source**, **Connection**, **File**, and **Status**. Each provider that has a
connection or a source has its own group. **Add another connection** opens
**Connectors**.

When the Workspace has no source and no connection, the group shows "No sources
yet. Connect a tool under Connectors, then add it to this Workspace." Choose
**Add connection** to open **Connectors**.

Each change to a source is a pull request that a person merges. No agent can
change `sources/` without that review. The buttons show only when ctx| can
open a pull request: the Workspace must have a connected GitHub repository and
must allow edits. See [Write access](#write-access). A context repository
that is below format 2 refuses each change with **Upgrade this Workspace first**.
See [Upgrades](#upgrades).

### Add a source

<Steps>
  <Step>
    ### Open the dialog

    In the group of the provider, choose **Add** (**Add repositories** for
    GitHub). The button shows only when the organization has a connection of
    that provider.

    You can also start from **Connectors**. See
    [Connections](/docs/connections).
  </Step>

  <Step>
    ### Fill in the fields

    The dialog title names the provider, for example **Add Linear source**. It
    has these fields:

    - **Connection**: shown when the organization has more than one connection
      of the provider.
    - The scope editor of the provider, for example the teams of Linear or the
      channels of Slack. Only an organization owner or admin can list the content
      of most providers. A member sees "Ask an admin to choose what this source
      syncs." The exception is Confluence: any member can list Confluence
      spaces.
    - **File name (optional)**: the name of the file. The hint shows the result,
      for example `sources/linear/linear.md`. A name has lowercase letters,
      digits, `.`, `_`, and `-`. It starts with a letter or a digit and has at
      most 100 characters. Without a name, ctx| names the file from the
      provider, with the next free number (`linear`, `linear-2`). A GitHub source is
      always `sources/github/<owner>/<name>.md`.
    - **Description (optional)**: what the source is for. People and agents read
      it.
  </Step>

  <Step>
    ### Open the pull request

    Choose **Open a pull request**. The message "Pull request opened. The
    change applies after the merge." confirms it. The group shows **New source**
    with an **Awaiting merge** link to the pull request. After you merge the
    pull request, the source syncs.
  </Step>
</Steps>

### Add source shows an error

- **Upgrade this Workspace first.** The context repository does not use one file
  for each source yet. An owner or admin starts the upgrade in **Upgrades**.
  Merge the pull request, then add the source again.
- **This Workspace is read-only.** ctx| cannot open a pull request. See
  [Write access](#write-access).
- **Ask an admin to choose what this source syncs.** Only an owner or admin can
  list the content of this provider.

### Edit a source

Choose the pencil button of the row (**Edit sources/…md**). The dialog **Edit
Linear source** (the title names the provider) says "The change goes to sources/…md." It has the same fields as the
add dialog, with no file name. Choose **Open a pull request** to save.

The row has no edit button when the source has no connection (a plain git
source), or when the row is not a source file. For a plain git source, change the
file with a pull request in Git.

### Rename a source

Choose the rename button of the row (**Rename sources/…md**). The dialog
**Rename sources/…md** says "The change moves the file. Each file that lists this
path in its sources gets the new path in the same change." It has one field,
**File name**, with the hint "Saved as sources/…md". The folder stays, so the
provider cannot change. The name has lowercase letters, digits, `.`, `_`, and
`-`. **Open a pull request** is not available until the name is valid and
different.

The pull request moves the file. It also updates the `sources` list of each
knowledge file that names the old path. A rename keeps the pin of a GitHub
source. The next sync of a connector writes the new path into its mirror files.
A rename that you make in Git gets the same update in a follow-up commit.

### Remove a source

Choose the remove button of the row (**Remove sources/…md**). The dialog **Remove
sources/…md?** says "The change deletes the source file. After it lands, the sync
deletes the files that the source wrote. Git history keeps them." Choose **Open a
pull request** to confirm, or **Cancel**. A Slack source is the exception: ctx|
keeps the threads that it captured.

For a GitHub repository, choose the unlink button (**Unlink owner/name**). See
[Linked repositories](/docs/workspaces/linked-repositories).

### Pull requests that wait for a merge

A row with an open pull request shows a link to it:

| Link | The pull request |
| --- | --- |
| **Awaiting merge** | Adds or edits the source. |
| **Rename awaiting merge** | Moves the source file. |
| **Removal awaiting merge** | Deletes the source file. |

The link opens the pull request on GitHub in a new tab. After the merge, the page
reads the sources again by itself, and the row can take a few seconds to
update. On **Connectors**, the
**Used in** list of the connector shows the same pull requests with an **Open
pull request** link.

### Source status

Each row has one status. The reason shows under the row.

| Status | Meaning |
| --- | --- |
| **OK** | ctx\| read the file, and the connection and the scope work. The source syncs. |
| **Not valid** | The file does not parse, has a wrong shape, or breaks a rule. The sync skips it. The reason names the problem. |
| **Connection missing** | The connection of the source was removed. The file stays. |
| **Out of access** | The connection cannot reach the scope, for example a GitHub repository that is not in the GitHub App installation. Add the repository to the installation. ctx\| checks again later. |

A file under `sources/` that has an unknown provider or a path that breaks the
rules shows in the group **Files not valid**. The reason names the problem. A row
that shows "This row is not a source file. Edit the file that defines it." comes
from the older `.ctxpipe/sources.yaml` format. The pane shows "The legacy sources
file is not valid" when that file does not parse.

These rules apply across files:

- Two GitHub sources cannot name the same repository. The second file is **Not
  valid**.
- A GitHub source cannot name the context repository.
- Two sources cannot write to the same folder. A source that already syncs keeps
  its place.
- A file larger than 64 KiB, or a file that is not text, is **Not valid**.

### Source file format

Each file has the front matter key `provider`. Each file except a plain git
source has `connection`. The scope keys depend on the provider. An unknown key
makes the row **Not valid**.

| Provider | Path | Scope keys |
| --- | --- | --- |
| GitHub | `sources/github/<owner>/<name>.md` | `repository` (`owner/name`), optional `ref` (branch or tag) |
| Linear | `sources/linear/<name>.md` | `teams` (team keys), `projects` (project ids), optional `customerRequests` (`exclude` or `limited`). At least one team or project. |
| Notion | `sources/notion/<name>.md` | `pages` and `databases`, each a list of `id` and `title`. At least one of them. |
| Confluence | `sources/confluence/<name>.md` | `spaces`: a list of `key` and `pages` (`all` or a list of page ids) |
| Slack | `sources/slack/<name>.md` | `channels`: a list of channel ids |
| PagerDuty | `sources/pagerduty/<name>.md` | `services`: a list of service ids |
| Buildkite | `sources/buildkite/<name>.md` | `pipelines`: a list of pipeline slugs |
| Plain git | `sources/git/<host>/<name>.md` | `url` only |

Each path segment after the provider folder matches
`[a-z0-9][a-z0-9._-]{0,99}`. `id` and `kind` are not allowed in the front
matter. Do not repeat the front matter in the body.

## Upgrades

The **Upgrades** group says: "Upgrades move your Workspace repository to the
layout that this version of ctx| reads. Nothing changes until you merge the pull
request." Every member can read the group. Only an organization owner or admin
can start an item. A member sees **Ask an admin** in place of the button.

The first line is the health line. It compares the repository format with the
format that ctx| reads:

| Health line | Meaning |
| --- | --- |
| "The repository uses format N. It is up to date." | The repository has the newest format. |
| "The repository uses format N. ctx\| reads format M." | An upgrade is available. |
| "The repository uses format N. ctx\| reads format M. This Workspace needs a newer ctx\| version." | The repository is newer than ctx\|. The Workspace is **Read-only**. |
| "The format file in the repository is not valid." | Repair `.ctxpipe/workspace.yaml`. The Workspace is **Read-only**. |
| "ctx\| has not read the repository format." | The first hydrate did not finish. |

When nothing is pending, the group says "No upgrades are pending." Items that are
done show under **History**. The Home page shows one alert for each Workspace
that has an item to finish. It names the Workspace and reads "has N upgrades to
finish". **Review upgrades** opens this group.

### Upgrade items

There are two kinds of item.

- **Upgrade to format N** moves the layout of the repository. The card says
  "Format A to format B. ctx| opens one pull request. Nothing changes until you
  merge it." It lists its steps, with the commit of each step after the run.
- **Fresh re-ingestion of the source repositories** reads each source repository
  again and publishes the new knowledge to the Workspace. It needs format 3.

Each item shows one status:

| Status | Meaning | What to do |
| --- | --- | --- |
| **Ready to start** | ctx\| found the upgrade. It waits for a start. | An owner or admin chooses **Start**. A member sees **Ask an admin**. |
| **Queued** | The start is recorded. The run did not begin. | Wait. |
| **Preparing the pull request** | The run builds the commits. | Wait. |
| **Waiting for merge** | The pull request is open. | Review and merge it. If the card does not change after a few minutes, an owner or admin chooses **Check again**. |
| **Applied** | The upgrade is done. | None. |
| **Failed** | The run stopped. The card shows "The upgrade failed" and the reason. | Fix the cause, then an owner or admin chooses **Start again**. |
| **Blocked** | ctx\| cannot start the item. The card shows a title and a reason. | Remove the cause. See [Blocked items](#blocked-items). |

Nothing starts by itself. This is true for hosted and for self-hosted
deployments.

### The merge step

A format upgrade is a pull request:

1. An owner or admin chooses **Start**. The message "The upgrade is queued. ctx|
   prepares a pull request." confirms it.
2. ctx| opens one pull request on the branch `ctxpipe/upgrade/format-<target>`.
   It holds one commit for each step that changes a file. The last commit
   writes `.ctxpipe/workspace.yaml`. ctx| never pushes to the default branch.
3. The card links to the pull request (**Pull request #N**) and says "ctx| waits
   for you to merge pull request #N on GitHub. After the merge, ctx| reads the
   new format of the repository. This takes a few minutes. This page updates by
   itself."
4. Review and merge the pull request. The merge lands the files and the new
   format together. If the card does not change after a few minutes, an owner or
   admin chooses **Check again**. The message "ctx| is reading the repository
   now. This takes a minute." confirms it.

If someone closes the pull request without a merge, the item goes back to
**Ready to start** with a note.

The card can show **Notes**. An arrow marks each action that you must do, and a
warning marks each risk. **Details** has the lines of the pull request report.
Read the notes before you merge.

### Re-ingestion

When you choose **Start** on a re-ingestion, the message "The re-ingestion is queued. ctx| reads each source repository
again." confirms it. A re-ingestion opens no pull request when it
starts.

For the spend, the throttle, and the restart rules, see
[Upgrade a Workspace](/docs/self-hosting/upgrades#upgrade-a-workspace).

### Blocked items

A blocked card shows a title and a reason. The title tells the cause:

| Title | Item | Cause |
| --- | --- | --- |
| "ctx\| cannot open the upgrade pull request" | Format upgrade | ctx\| has no write access through the GitHub App. See [Write access](#write-access). |
| "ctx\| cannot publish the re-ingestion" | Re-ingestion | ctx\| has no write access through the GitHub App. See [Write access](#write-access). |
| "Apply the format upgrade first" | Re-ingestion | The repository is below format 3. Merge the format upgrade. An owner or admin chooses **Check again** on the card. |
| "This deployment cannot run the re-ingestion" | Re-ingestion | The deployment has no ingest sandbox. The operator must configure one. |
| "The re-ingestion cannot run here yet" | Re-ingestion | ctx\| has not read a valid format file of this Workspace. |

### Repository format

Each context repository holds `.ctxpipe/workspace.yaml`, below its root folder.
The file has one key:

```yaml
format: 3
```

The format is the version of the repository layout. ctx| reads the file at each
hydrate. The **Upgrades** health line shows it.

| Format | Layout |
| --- | --- |
| 0 | No format file: a repository from before Workspaces. |
| 1 | The knowledge that fresh ingestion cannot rebuild is exported. The sources are in the older `.ctxpipe/sources.yaml`. |
| 2 | One Markdown file for each source under `sources/`. |
| 3 | The ownership front matter that ingestion writes in each knowledge file. This is the current format. |

- Only the setup commit of a new Workspace and an upgrade pull request write the
  file. No agent or chat write can change it.
- A change that needs a newer layout refuses on an older repository. A source
  change on a repository below format 2 shows **Upgrade this Workspace first**:
  "Its repository does not use one file for each source yet. Run the Workspace
  upgrade, then try again." Ingestion needs format 3.
- A repository with a format that this ctx| version does not know, or a format
  file that does not parse, is **Read-only**. Reads continue.

## Danger zone

Choose **Delete Workspace**. The dialog **Delete Workspace?** asks you to type the
name of the Workspace to confirm. The deletion removes the Workspace and its
conversations from ctx|. Your GitHub repository and its files stay.
