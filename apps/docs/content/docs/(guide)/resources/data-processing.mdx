This page is about **hosted ctxpipe**. On a self-hosted deployment, you choose
the providers and the retention. The model calls go from your deployment to the
provider that you configure. The ctxpipe team never sees your prompts or your
model traffic.

## What ctxpipe reads

- The git repositories that you link to a Workspace, and the Workspace
  repository itself.
- The content of the sources that you add. This is:
  - Linear, Notion, Confluence, PagerDuty, Buildkite, and Plain mirrors.
  - The issues and closed pull requests of linked GitHub repositories.
  - The Slack threads that a person captures.

  ctxpipe writes this content into the Workspace repository, which you control.
  Then it indexes the content.

ctxpipe reads nothing that you did not connect.

## What you control

- You create each Workspace, link each repository, and approve each source scope
  in a pull request. ctxpipe ingests nothing without one of these actions.
- ctxpipe writes only to Workspace repositories. It never writes to your code
  repositories. See
  [What ctxpipe writes](/docs/workspaces#what-ctxpipe-writes).
- You can unlink a repository, remove a source, or delete a Workspace at any
  time. This stops new indexing. The indexed data can stay until the deletion
  process of your organization is complete.
  [Get in touch](/docs/getting-started/get-in-touch) for the details.
- The data of your organization is separate from the data of other
  organizations.
- If you stop using ctxpipe, your Workspace repositories stay with you, with
  their full history.

## Where your data is

Hosted ctxpipe runs in one AWS region: **us-west-2** (Oregon, United States).
The database, the indexes, the sandboxes, and our own observability are all in
that region. Requests in transit pass through the Cloudflare edge, and model
calls go to the model providers. Both can process data outside us-west-2.

## Sub-processors

| Provider | Purpose |
| --- | --- |
| Amazon Web Services (AWS) | Compute, the Postgres database, storage, and the isolated sandboxes (microVMs) for Workspace chat and for ingestion. A sandbox holds a copy of the Workspace repository, or of the linked repository that it ingests. AWS also runs our own observability (logs, traces, and model traces). |
| Cloudflare | The network edge: DNS, TLS, protection against attacks, and the private connection to AWS. Requests to ctxpipe go through Cloudflare. |
| OpenRouter | Model routing, only to zero data retention endpoints |
| Vercel | The ctxpipe marketing site and this documentation only. Vercel does not process your Workspace data or model traffic. |
| Anthropic and OpenAI | The model providers of the AI agents that the ctxpipe team uses to operate and debug the service. These agents read our logs and traces, which can hold the prompts and outputs of model calls. See [Retention](#retention). |

## How ctxpipe uses models

- **Workspace chat.** Your messages, and the context that the agent retrieves
  (search results, file excerpts, and graph context), go to the model. See
  [Where the agent runs](/docs/workspaces/chat#where-the-agent-runs).
- **Ingestion.** ctxpipe uses models to extract knowledge from parts of the
  linked repositories, in a sandbox with a closed network. See
  [Where extraction runs](/docs/workspaces/indexing#where-extraction-runs).
- **MCP tools.** The tools call no model. They search and read your data. Your
  coding agent uses its own model.

ctxpipe does not send a whole repository to a model in one request. Retrieval
and tools select the context.

On hosted ctxpipe, each model call of the product goes through OpenRouter to
[zero data retention (ZDR)](https://openrouter.ai/docs/guides/features/zdr)
endpoints only. Our OpenRouter account enforces this, so the model providers do
not store your prompts or train on them. See the
[OpenRouter privacy policy](https://openrouter.ai/privacy).

## Retention

We do not publish fixed retention periods for indexed data yet. Two exceptions:

- ctxpipe deletes the saved sandbox files of a Workspace chat conversation 29
  days after the last use of the conversation. The branch of the conversation
  in your repository stays.
- Our own observability (HyperDX) keeps logs and traces for 30 days. A trace
  of a model call holds the prompt and the output of that call. AWS CloudWatch
  keeps the raw service logs for 1 day.

The ctxpipe team uses AI agents to operate and debug the service. These agents
read logs and traces, so this content also goes to the model providers of the
agents (Anthropic and OpenAI). These calls do not go through OpenRouter, so the
zero data retention rule above does not apply to them. The retention terms of
the API of each provider apply.

For deletion times, export, or a DPA,
[get in touch](/docs/getting-started/get-in-touch).

## What we do not do

- We do not train models on your content.
- We do not share data across organizations, and we do not sell it. The
  sub-processors above only operate the product.
- We do not ingest sources that you did not connect.

## Certifications

SOC 2 and ISO 27001 for ctxpipe are on the roadmap. Our infrastructure
sub-processors publish their own compliance and security documents.

For questions about your data, sub-processors, or contracts,
[get in touch](/docs/getting-started/get-in-touch).
