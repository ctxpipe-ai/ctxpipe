ctx| uses [Better Auth](https://www.better-auth.com) for identity management.
All browser sign-in, provider callbacks, sessions, and MCP OAuth flow through the
same public backend origin.

## Required auth boundary

| Variable | Requirement |
| --- | --- |
| `AUTH_SECRET` | A stable random value of at least 32 characters. Generate with `openssl rand -hex 32`. |
| `AUTH_BASE_URL` | The public HTTPS backend origin users and providers can reach. |
| `AUTH_ALLOWED_ORIGINS` | Optional comma-separated extra browser origins. Keep this list narrow. |
| `SMTP_CONNECTION_URL` | Required for email verification, password reset, and invitation email delivery. |
| `EMAIL_FROM_ADDRESS` | The sender address for transactional email. |

`AUTH_SECRET` protects sessions and encrypted auth material. Do not generate a
new value on every deploy. Rotating it can invalidate sessions and prevent
existing encrypted signing keys from being read; treat rotation as a planned
operational change.

<Callout type="warn" title="One public origin">
  Open the product through `AUTH_BASE_URL`. Do not send browser users directly
  to the private UI service. Provider callbacks, MCP OAuth, cookies, and the API
  rely on a consistent origin.
</Callout>

## Email and password

Email/password sign-in is available by default. Configure SMTP before inviting a
team so verification, invitation, and password-reset messages leave the
deployment reliably.

With SMTP and `EMAIL_FROM_ADDRESS` set, new email/password accounts verify
their address before they can sign in. An unverified account that signs in is
sent a fresh link. Resetting a password also verifies the address, and signs
out the account's other sessions. Without SMTP, messages are only logged, so
verification is not required and the backend logs a warning at startup.

## Social providers (OAuth)

ctx| supports GitHub, Google, and Microsoft social sign-in.
Each provider is enabled conditionally - if the corresponding client ID and
secret are set in the backend environment, the sign-in option appears.

| Provider | Env vars required |
|---|---|
| GitHub | `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` |
| Google | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` |
| Microsoft | `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` |

<Callout type="info">
  GitHub social sign-in credentials are separate from the deployment-owned
  [GitHub App](/docs/self-hosting/github) used for repositories and connector
  writes.
</Callout>

Register each provider callback under `AUTH_BASE_URL`. Test sign-in through the
same public origin users will use in production.

## Passkeys and two-factor authentication

Passkeys are available on compatible browsers and platforms. Users can also
enable TOTP two-factor authentication with a standard authenticator app. Verify
both through your production TLS domain; WebAuthn credentials are origin-bound.

## MCP OAuth and API keys

ctx| is an OAuth provider for downstream MCP clients. It supports discovery,
dynamic client registration, and device authorization for compatible headless
clients.

Configure the client with:

```text
{AUTH_BASE_URL}/mcp
```

Each OAuth grant holds a set of organizations. The user selects the organizations
on the consent screen, and the user can change the set later on the
**Connected apps** page (`/.auth/account/connected-apps`). Each tool call names
one organization with the `org` argument. The server allows the call only when
the organization is in the grant set and the user is still a member of it.

The `?orgSlug=` URL parameter no longer selects the organization. The server
accepts it and ignores it, so old client configurations keep working.

OAuth is the normal MCP flow for people. The scopes are `ctxpipe:read` and
`ctxpipe:write`. Legacy grants and API keys count as read.

Dashboard API keys are stored in this deployment's Better Auth database; there
is no extra operator secret to configure. Send `x-api-key` when the client
supports custom headers. Bearer-only MCP hosts may instead send
`Authorization: Bearer <api-key>` to `/mcp`; OAuth credentials are resolved
before that API-key fallback, and REST does not accept Bearer API keys.
Personal keys live under **User account → API Keys** and still authenticate
REST as that user through `x-api-key`. A personal key reads the organizations
that its user is a member of. Organization keys live under
**Organization settings → API Keys** and authenticate MCP only (one
organization per key; the `org` argument of each tool call must name that
organization). `--auth api-key` writes an interpolation of `CTXPIPE_API_KEY`, never
the secret. Set that variable in the MCP client environment. `npx ctxpipe
doctor mcp` sends `x-api-key` when `CTXPIPE_API_KEY` is set in that process.

See [Remote MCP](/docs/mcp/mcp-docs#api-key-auth) for user vs organization keys
and the API-key CLI path, and [MCP diagnostics](/docs/self-hosting/mcp) when
discovery or authorization fails.

## Production checks

- `AUTH_SECRET` is stable across backend instances and deploys.
- `AUTH_BASE_URL` exactly matches the browser origin.
- Provider callbacks use HTTPS and the same host.
- Extra trusted origins are explicit rather than wildcarded.
- SMTP can deliver invitation and reset messages.
- Passkey registration and TOTP sign-in work on the production domain.
- An MCP client can discover OAuth and complete authorization.
