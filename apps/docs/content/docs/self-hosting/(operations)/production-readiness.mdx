---
title: Production readiness
description: Checklist for running ctxpipe behind a real public origin.
---

Use this checklist before making a self-hosted deployment available to a team.
The reference Compose stack is a starting point; production deployments should
make the network boundary, persistence, secrets, and rollback process explicit.

## Public origin

ctxpipe expects a single public backend origin for browser, REST, auth, and MCP
traffic.

| Check | Why it matters |
|---|---|
| `AUTH_BASE_URL` is the public HTTPS origin | Better Auth callbacks, generated links, OAuth issuer values, MCP auth, and connector callbacks depend on this value. |
| `CTXPIPE_PUBLIC_APP_URL` matches the public backend origin | The UI uses this value at build time. |
| Browser users enter through the backend | The backend proxies the UI, keeping auth and API requests on the same origin. |
| `AUTH_ALLOWED_ORIGINS` includes only required extra origins | Avoid broad CORS allowances. |

## TLS and proxying

Put a TLS-terminating proxy or platform load balancer in front of the backend.
Expose only the backend origin publicly unless you have a specific operational
reason to expose other services.

| Service | Public exposure |
|---|---|
| `backend` | Public HTTPS |
| `ui` | Private; backend proxy should serve it |
| `worker` | Private |
| `codesearch` | Private |
| `postgres` | Private |
| `falkordb` or graph database | Private |
| `dind` (Docker Compose) or the AWS sandbox host | Private. Do not publish the Docker API or other unauthenticated services on a host that runs chat sandboxes. |

The backend refuses a webhook body above its limit with `413`: 25 MiB for
GitHub, 5 MiB for Linear, and 1 MiB for Slack, Notion, PagerDuty, and
Atlassian. If your proxy has a lower body limit, set it to at least 25 MiB
for `/api/v1/webhook/github` and 5 MiB for `/api/v1/webhook/linear`.

Telemetry export is outbound only. There is no collector to expose. Set
`OTEL_EXPORTER_OTLP_*` to your own endpoint when you want traces, logs, or
metrics to leave the app containers.

## Callback URLs

Register callback and webhook URLs against your public origin.

| Integration | URL shape |
|---|---|
| Atlassian OAuth | `{AUTH_BASE_URL}/api/v1/integrations/atlassian/callback` |
| Linear OAuth | `{AUTH_BASE_URL}/api/v1/integrations/linear/callback` |
| Linear webhook | `{AUTH_BASE_URL}/api/v1/webhook/linear` |
| GitHub App webhook | `{AUTH_BASE_URL}/api/v1/webhook/github/<connectionId>` |
| Slack OAuth | `{AUTH_BASE_URL}/api/v1/connectors/slack/oauth/callback` |
| Slack Events API | `{AUTH_BASE_URL}/api/v1/webhook/slack` |
| Notion OAuth | `{AUTH_BASE_URL}/api/v1/connectors/notion/oauth/callback` |
| Notion webhook | `{AUTH_BASE_URL}/api/v1/webhook/notion?provisioningToken=...` |
| PagerDuty OAuth | `{AUTH_BASE_URL}/api/v1/integrations/pagerduty/callback` |
| PagerDuty webhook | `{AUTH_BASE_URL}/api/v1/webhook/pagerduty` |
| MCP | `{AUTH_BASE_URL}/mcp` |
| App auth | `/.auth/*` routes under `AUTH_BASE_URL` |

## Persistence

Do not treat the reference Compose volumes as disposable in production.

| State | Production expectation |
|---|---|
| Postgres | Managed backups, restore test, monitoring, and storage alerts |
| Graph database | Backup or snapshot according to provider guidance |
| `repo_cache` | Persistent volume if recloning large repositories is expensive |
| `zoekt_index_deploy` | Persistent volume if rebuilding indexes is expensive |
| Secrets | Stored in a secret manager or platform secret store, not committed files |

## Codesearch capacity

Keep `codesearch` at **one replica**. Zoekt shards, git clone cache, and SCIP
artifacts are process-local. Extra worker replicas do not raise ingest
throughput unless codesearch memory and the injected
`OPENWORKFLOW_CONCURRENCY` / `CODESEARCH_INDEXER_CONCURRENCY` /
`CODESEARCH_INDEX_PIPELINE_CONCURRENCY` values also grow. Compose `deploy`
uses the small pair (indexer 1, pipelines 1, worker concurrency 6). AWS CDK
injects the matching pair for `small` / `medium` / `large`.

## Worker memory

The worker starts with a Node heap limit of about 55% of the memory its
container may use, up to 12 GiB. Native memory, Git, and the sandbox SDKs
use the rest. The AWS CDK worker task (1, 2, or 4 GiB for `small`, `medium`,
`large`) and a Compose host therefore get a limit that fits their memory. No
setting is needed.

To use another limit, set `--max-old-space-size=<MiB>` in `NODE_OPTIONS` on
the worker. The worker keeps your value. Keep it below the container memory.

The worker also starts with `--heapsnapshot-near-heap-limit=1` and
`--diagnostic-dir=/tmp/heap`. If the heap nears its limit, Node writes one
`.heapsnapshot` file to `/tmp/heap` before the process exits. The file is lost
when the container restarts, unless `/tmp/heap` is on a volume.

Writing the snapshot pauses the worker. It needs extra memory and disk space,
and the file can be larger than the heap. On a small task the write can fail,
and the platform can then stop the process. The result is the same crash as
without the snapshot. To turn the snapshot off, set
`--heapsnapshot-near-heap-limit=0` in `NODE_OPTIONS` on the worker.

The worker logs its heap limit at start (`heapLimitMib` in the
`openworkflow.config-loaded` line).

## Secret handling

Protect and rotate:

- `AUTH_SECRET`
- `CONNECTION_SECRETS_ENCRYPTION_KEY`, if set
- GitHub App private keys and webhook secrets
- Atlassian OAuth client secrets and Forge tokens
- Slack client secret, signing secret, and stored bot-token encryption material
- Linear OAuth client and webhook secrets, or the shared encryption key used to decrypt connection-stored Linear app secrets
- Notion OAuth client and webhook secrets
- Model provider API keys
- SMTP credentials
- OTLP exporter credentials

## Roll AUTH_SECRET and the encryption key

The database keeps connector secrets (GitHub App keys, webhook secrets, OAuth
tokens, Slack bot tokens) encrypted with `CONNECTION_SECRETS_ENCRYPTION_KEY`.
When that variable is not set, the key comes from `AUTH_SECRET`. Two-factor
(TOTP) secrets and backup codes are encrypted with `AUTH_SECRET`.

To change one or both secrets, do these steps:

1. Write down the old values. Keep them in your secret store until step 7 is
   complete.
2. Set the new values on the backend, the worker, and codesearch at the same
   time. Codesearch uses `AUTH_SECRET` to check the tokens of the backend.
   - `AUTH_SECRET`: a new value from `openssl rand -hex 32`.
   - `CONNECTION_SECRETS_ENCRYPTION_KEY`: a new value from
     `openssl rand -hex 32`. We recommend an explicit key, so that the next
     change of `AUTH_SECRET` does not change it.
   - `CONNECTION_SECRETS_PREVIOUS_KEYS`: the old
     `CONNECTION_SECRETS_ENCRYPTION_KEY`, if it was set. If you did not
     complete an earlier roll, keep its keys too, comma separated.
   - `PREVIOUS_AUTH_SECRET`: the old `AUTH_SECRET`, as one value (a comma in
     it is safe). Set it when you change `AUTH_SECRET`, because the
     two-factor secrets need it. Also set it when no explicit
     `CONNECTION_SECRETS_ENCRYPTION_KEY` was set before, because then the old
     connector key comes from it.
3. Deploy the backend, the worker, and codesearch. Connectors continue to
   work, because the backend tries the previous keys after the current key.
   All users must sign in again.
4. Do a dry run of the re-encrypt command in a backend container. It shows
   counts and changes nothing:

   ```bash
   docker compose --profile deploy exec backend \
     bun run apps/backend/src/scripts/reencryptSecrets.ts --dry-run
   ```

5. Run the command without `--dry-run`. It encrypts each stored value again
   with the current key, for all organizations. For each group, it shows the
   number of rows that it rewrote, the number of rows that were current, and
   the ids of the rows that stay on an old key, with a reason. It never shows
   a secret. You can run it
   again at any time; it skips current values. `--dry-run` is the only
   option.
6. Make sure that all the old backend and worker instances have stopped. Then
   do the dry run of step 4 again. A connector token refresh that read a row
   before step 5 can write a value with the old key back.
7. Remove `CONNECTION_SECRETS_PREVIOUS_KEYS` and `PREVIOUS_AUTH_SECRET` only
   when the dry run of step 6
   shows `"rewritten": 0` and `"failed": []` for all three groups. If it does
   not, do step 5 and step 6 again. Then deploy again and destroy the old
   values.

Each row in `failed` has a reason:

- `decrypt`: no configured key decrypts a value in the row. Find the key that
  encrypted it and add it, or connect that integration again (for a
  two-factor row, the user sets up two-factor sign-in again).
- `changed`: the row changed during the run. Run the command again.
- `write`: the UPDATE failed. Make sure that the database is available, then
  run the command again.

Users with two-factor sign-in cannot sign in between step 3 and step 5. Run
step 5 immediately after the deploy.

If an attacker possibly has the old secret and access to the database, new
encryption does not protect the values that were already read. Also rotate the
connector credentials at each provider.

These steps use Docker Compose. On another host, run the same command in a
backend container with the same environment. The `@ctxpipe/aws-cdk` stack
does not set `CONNECTION_SECRETS_ENCRYPTION_KEY`,
`CONNECTION_SECRETS_PREVIOUS_KEYS`, or `PREVIOUS_AUTH_SECRET` yet.

## Connector readiness

Before inviting users:

- Create or configure at least one GitHub App connection.
- Confirm GitHub webhook delivery reaches the public backend origin.
- If using Confluence, configure Atlassian OAuth and Forge install/provisioning.
- If using Slack, set all three Slack app secrets, verify the OAuth callback and
  Events Request URL, and test installation in a non-development workspace when
  multi-workspace distribution is required.
- If using Linear, register a Linear OAuth application (in the product UI, or
  optionally via `LINEAR_*` on backend and worker) and register the exact OAuth
  callback and webhook URLs.
- Confirm backend and worker can reach `api.linear.app`.
- If using Notion, configure `NOTION_CLIENT_ID` and `NOTION_CLIENT_SECRET`,
  register the exact OAuth redirect URL, and set `NOTION_WEBHOOK_SECRET` after
  the first webhook delivery.
- If using PagerDuty, register the exact OAuth callback. Either save the
  client id and secret in the connector wizard, or configure
  `PAGERDUTY_CLIENT_ID` and `PAGERDUTY_CLIENT_SECRET` on backend and worker.
  ctxpipe creates the webhook subscription after authorization.
- Confirm backend and worker can reach `identity.pagerduty.com` and
  `api.pagerduty.com` or `api.eu.pagerduty.com`.
- Confirm the worker can run connector jobs.
- Confirm `codesearch` can clone the expected repositories.
- Confirm model provider credentials work for both chat and embedding calls.

## Preflight checklist

- `curl https://<public-origin>/.status` returns JSON with `status: "ok"`.
- Sign-in works using the enabled auth method.
- A user can create or select an organization.
- A repository can be added and reaches indexed state.
- Chat or MCP can answer a question grounded in the repository.
- A Workspace chat answers in a sandbox, and `SANDBOX_PROVIDER` is not
  `unsandboxed`. See [Operations](/docs/self-hosting/operations) for the
  sandbox checks.
- Backend, worker, and codesearch logs are collected.
- Postgres and graph database backups are configured.
- Upgrade and rollback steps are written down for the current deployment shape.
