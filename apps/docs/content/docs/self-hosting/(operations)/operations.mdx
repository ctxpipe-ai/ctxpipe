Operations docs assume the deployment is already configured. Use this page to
keep a running instance healthy and to diagnose component-level failures.

## Health checks

| Check | Command or route | Expected result |
|---|---|---|
| Backend status | `GET /.status` | JSON response with `status: "ok"` and `timestamp` |
| Postgres in Compose | Docker health check uses `pg_isready` | Service is healthy before migrations and app services start |
| UI through backend | Open `AUTH_BASE_URL` | App loads from the backend origin |
| MCP route | `npx ctxpipe doctor mcp --url "$AUTH_BASE_URL/mcp?orgSlug=..."` then an OAuth-capable MCP client | Doctor reports `ready-for-oauth`; client OAuth then succeeds |
| Codesearch | Add or reindex a repository | Repository reaches indexed state; backend can call `CODESEARCH_URL` |
| Graph database | Open graph page or use graph-backed chat/MCP | Graph responses succeed; backend does not return graph connectivity errors |

<Callout title="Codesearch health">
  The reference codesearch service does not expose a separate public health
  endpoint. Treat successful repository clone/index/search operations as the
  practical health signal.
</Callout>

## Migrations

The Compose `deploy` profile starts a `migrate` service before backend, worker,
UI, and codesearch. Migrate uses the owner URL and provisions `ctxpipe_app`.
App processes use the app-role `DATABASE_URL`. The migrate container runs:

```bash
bun run apps/backend/src/db/migrate.ts
```

Migrations are idempotent. Drizzle tracks applied migrations in the
`drizzle_migrations` table and skips migrations that already ran.

For non-Compose deployments:

1. Back up Postgres first.
2. Run migrations once against the production database.
3. Start the new backend, worker, UI, and codesearch versions after migrations
   complete.

## Logs

ctx| writes structured application logs through evlog. Without an OTLP logs
endpoint, logs go to stdout.

| Component | Useful signals |
|---|---|
| `backend` | auth failures, REST errors, MCP requests, graph read failures, connector callbacks |
| `worker` | ingestion jobs, Confluence, Linear, and PagerDuty sync, Forge provisioning, background workflow failures |
| `codesearch` | clone failures, indexing failures, Zoekt errors |
| `postgres` | connection limits, slow queries, disk pressure |
| `graph database` | connection failures, memory pressure, query errors |

Configure `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`,
`OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`, and `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`
on the app services when you want telemetry to leave stdout and reach your
observability backend. See
[Configuration](/docs/self-hosting/configuration) for headers, service names,
and Langfuse. ctx| does not run a collector for you. Export failures are
visible in your collector or vendor, not in a bundled collector container.

## Backups

Back up before upgrades, secret rotation, connector migrations, and storage
changes.

| Data | Backup guidance |
|---|---|
| Postgres | Required. Use managed database backups or `pg_dump`/physical backups. Test restore regularly. |
| Graph database | Back up or snapshot according to provider guidance. |
| `repo_cache` | Optional but recommended for large/private repositories. Rebuildable by recloning. |
| `zoekt_index_deploy` | Optional but recommended for large deployments. Rebuildable by reindexing. |
| Secrets | Export from your secret manager or platform. Keep historical values needed for rollback. |

## Chat sandbox host (AWS)

`@ctxpipe/aws-cdk` runs Workspace chat sandboxes on one EC2 Docker host (see
[AWS: Chat sandbox host](/docs/self-hosting/deployment/aws#chat-sandbox-host)).
It holds no data you need to back up: a replaced host starts empty and
conversations continue from their git branch.

Find the instance from the `SandboxHostAutoScalingGroupName` stack output and
open a shell with Session Manager (no SSH key or open port is needed):

```bash
aws ssm start-session --target <instance-id>
```

| Check | Command on the host | Expected result |
|---|---|---|
| Docker is up | `sudo systemctl is-active docker` | `active` |
| Docker volume | `df -h /var/lib/docker` | Below 80% used. The disk alarm fires at 80%. |
| What uses the disk | `sudo docker system df` | Images, containers, and build cache sizes |
| Sandboxes | `sudo docker ps -a` | One container per recent conversation; stopped ones are idle sandboxes |
| Memory cap | `systemctl status ctxpipe-sandboxes.slice` | Memory in use stays below the slice limit (85% of host memory) |
| Chat image | `sudo docker image ls ghcr.io/ctxpipe-ai/chat-sandbox` | The tag the backend's `SANDBOX_CHAT_IMAGE` names, after the first chat of a release |
| Boot log | `sudo tail -n 100 /var/log/cloud-init-output.log` | Ends with the CloudFormation success signal |

Sandboxes stop after 5 minutes idle and are removed 30 days after last use;
an organization runs at most 50 at once. If the volume still fills, check
`docker system df` for what grows, then raise
`sandboxHost.dockerVolumeSizeGiB` and run `cdk deploy`; the new size replaces
the host. Do not run `docker system prune` while conversations are active: it
deletes stopped sandboxes that conversations would resume.

## Chat sandboxes (Docker Compose)

The Compose deploy profile runs Workspace chat sandboxes inside the `dind`
service (see [Docker: Chat sandboxes](/docs/self-hosting/deployment/docker#chat-sandboxes)).
Its `sandbox_docker` volume holds no data you need to back up. Run these from
the repository root:

| Check | Command | Expected result |
|---|---|---|
| Daemon is up | `docker compose --profile deploy ps dind` | `healthy` |
| Chat image | `docker compose --profile deploy logs chat-sandbox-image` | Ends with the image ID (`sha256:…`) |
| Sandbox disk | `docker compose exec dind df -h /var/lib/docker` | Room left on the host disk that holds the Docker volumes |
| What uses the disk | `docker compose exec dind docker system df` | Images, containers, and build cache sizes |
| Sandboxes | `docker compose exec dind docker ps -a` | One container per recent conversation; stopped ones are idle sandboxes |
| Memory cap | `docker compose exec dind cat /sys/fs/cgroup/ctxpipe-sandboxes/memory.current /sys/fs/cgroup/ctxpipe-sandboxes/memory.max` | Memory in use stays below the cap. Missing on hosts without cgroup v2 (`dind` logs a warning). |
| Metadata block | `docker compose exec dind iptables -t raw -S PREROUTING` | Includes `-d 169.254.169.254/32 -j DROP` |
| No published data stores | `docker port $(docker compose ps -q postgres falkordb)` | Prints nothing |
| No host socket | `docker inspect --format '{{range .Mounts}}{{.Source}} {{end}}' $(docker compose ps -q backend worker)` | No `/var/run/docker.sock` |

Sandboxes stop and are removed on the same schedule as on AWS. To free disk
without touching sandboxes, remove superseded chat images and build cache:

```bash
docker compose exec dind docker image prune -f
docker compose exec dind docker builder prune -f
```

`docker image prune` keeps every image a container still uses. Do not run
`docker system prune` or `docker container prune` inside `dind` while
conversations are active: they delete stopped sandboxes that conversations
would resume.

## Recovery runbooks

### Workspace chat fails to start on Docker Compose

- A 503 saying the Docker daemon is not reachable means `dind` is down:
  confirm it is healthy (`docker compose --profile deploy ps -a`) and check
  `docker compose logs dind`.
- A 503 saying the chat sandbox image is missing means `chat-sandbox-image`
  has not finished or failed (for example a package mirror was unreachable,
  or the `sandbox_docker` volume was removed). Check its logs and rerun it:
  `docker compose --profile deploy up -d chat-sandbox-image`.
- Check backend logs for Docker TLS errors. After the `sandbox_ca` volume is
  removed, restart `backend` and `worker` so they read the new certificates.
- `dind` needs a privileged container. On a host that refuses one, see the
  last-resort option in [Docker: Chat sandboxes](/docs/self-hosting/deployment/docker#chat-sandboxes).

### Workspace chat fails to start on AWS

- Confirm the sandbox host instance is `InService` in its Auto Scaling group.
- Check backend logs for Docker connection or TLS errors. Backend and worker
  reach the host at `sandbox-host.ctxpipe.local:2376`; the host registers that
  name when it finishes booting.
- If the backend reports that the chat sandbox image is missing, the host
  could not pull `ghcr.io/ctxpipe-ai/chat-sandbox`. Check the host's outbound
  access to `ghcr.io` through NAT.
- Terminate the instance to get a fresh host. The Auto Scaling group replaces
  it in a few minutes and reuses the stored TLS certificates.

### App loads but sign-in fails

- Confirm `AUTH_BASE_URL` matches the browser origin.
- Confirm `AUTH_SECRET` is present and stable.
- Confirm provider callback URLs use the public backend origin.
- Check backend logs for Better Auth or OAuth provider errors.

### Repository never becomes indexed

- Check `codesearch` logs for clone/index errors.
- Confirm GitHub App permissions and installation scope.
- Confirm `CODESEARCH_URL` points at the codesearch service from the backend.
- Reindex after fixing credentials or network access.

### MCP discovery or OAuth fails

- Confirm `GET /.status` returns `{ "status": "ok" }`.
- Run `npx ctxpipe doctor mcp --url "$AUTH_BASE_URL/mcp?orgSlug=<slug>"`.
- A `ready-for-oauth` result means routing, the Bearer challenge, and OAuth
  discovery are coherent. It does not prove authenticated `tools/list` or
  `ctx_advisor`.
- Confirm `AUTH_BASE_URL` matches the public origin clients use, including TLS.
- Confirm the MCP URL includes `orgSlug`.
- For authenticated OAuth, `tools/list`, and `ctx_advisor`, use a version-pinned
  MCPJam client against a test organization. See
  [MCP](/docs/self-hosting/mcp).

### Chat or MCP returns weak context

- Confirm repositories are indexed.
- Confirm graph extraction has completed for the repository.
- Check model provider credentials and rate limits.
- Check backend and worker logs around code ingestion and graph projection.

### Knowledge graph fails to load

- Confirm `GRAPH_DB_URI` and provider credentials.
- Confirm the graph database is reachable from backend and worker.
- Check backend logs around graph snapshot/read operations.
- Re-run repository ingestion if graph data needs to be rebuilt.

### Confluence setup stalls

- Confirm Atlassian OAuth callback URL.
- Confirm Forge install URL or provisioning token.
- Confirm the worker can run Forge provisioning and Confluence sync jobs.
- See [Confluence & Atlassian](/docs/self-hosting/confluence-atlassian).

### Linear setup stalls or content becomes stale

- Confirm a Linear OAuth application is registered in the wizard or that
  `LINEAR_*` is present on backend and worker.
- Confirm the Linear webhook secret is saved on the connection or
  `LINEAR_WEBHOOK_SECRET` is present on backend, and signed requests reach
  `/api/v1/webhook/linear`.
- Confirm the selected GitHub App installation still has write access and that
  merge pushes reach `/api/v1/webhook/github/<connectionId>`.
- Check worker logs for `linear-sync-config`, `linear-sync-content`, or
  `linear-sync-incremental` failures.
- Use the setup dialog's configuration or content retry action after fixing the
  underlying credential, network, or permission failure.
- See [Linear](/docs/self-hosting/linear).

### PagerDuty setup stalls or incidents become stale

- Confirm PagerDuty OAuth credentials are present on backend and worker.
- Confirm the connection is live and the incident's service is listed in the
  merged `pagerduty/config.yaml`. There is no shared webhook secret; ctx|
  stores the per-subscription secret on the connection.
- Confirm signed requests reach `/api/v1/webhook/pagerduty` and merge pushes
  reach `/api/v1/webhook/github/<connectionId>`.
- Check worker logs for `pagerduty-sync-config`, `pagerduty-sync-content`, or
  `pagerduty-sync-entity` failures.
- Use the setup dialog's configuration or content retry action after fixing the
  underlying credential, network, or permission failure.
- See [PagerDuty](/docs/self-hosting/pagerduty).
