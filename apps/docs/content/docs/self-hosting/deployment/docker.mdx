Docker is the reference self-hosted path. It is best for evaluation, local
production-style testing, and small internal deployments where a single Compose
project is acceptable.

## What the deploy profile starts

The Compose `deploy` profile starts:

| Service | Purpose |
|---|---|
| `migrate` | Runs database migrations as the Postgres owner, then GRANTs `ctxpipe_app` |
| `backend` | Public API, auth, MCP endpoint, callbacks, and UI proxy |
| `ui` | Product web app, proxied through the backend |
| `worker` | Background workflows for ingestion and connector jobs |
| `codesearch` | Repository clone cache and Zoekt indexes. Stay at one replica. |
| `postgres` | Primary application database (no host port) |
| `falkordb` | Default graph database (no host port) |
| `dind` | Docker daemon for Workspace chat sandboxes (stock `docker:dind`) |
| `chat-sandbox-image` | One-shot: builds the chat sandbox image inside `dind` |

## Start the stack

From the repo root:

```bash
cp docker-compose.env.example .env
```

Set at least:

```bash
AUTH_SECRET=<32-plus-character-secret>
AUTH_BASE_URL=https://ctx.example.com
CTXPIPE_PUBLIC_APP_URL=https://ctx.example.com
MODEL_PROVIDER_API_KEY=<model-provider-key>
```

Compose wires two Postgres URLs for you: migrate uses `POSTGRES_USER`
(default `ctxpipe`); backend, worker, and codesearch use `ctxpipe_app` at
`DATABASE_APP_PASSWORD` (defaults to `POSTGRES_PASSWORD`). You do not add a
second secret name in `.env` unless you change those passwords.

Then start the deploy profile:

```bash
pnpm start
```

`pnpm start` is the repository shortcut for
`docker compose --profile deploy up -d`.

For a local evaluation, `AUTH_BASE_URL` and `CTXPIPE_PUBLIC_APP_URL` can point at
`http://localhost:3000`. For team use, put a TLS-terminating proxy in front of
the backend and use the public HTTPS origin.

OpenTelemetry is optional. Leave `OTEL_EXPORTER_OTLP_*` unset and the stack
does not export traces, logs, or metrics. To send them to your own collector
or vendor, set the variables in [Configuration](/docs/self-hosting/configuration).
The deploy profile does not run a collector.

Optional connectors use additional values from the same `.env`. Slack requires
`SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET`, and `SLACK_SIGNING_SECRET`; see
[Self-host Slack](/docs/self-hosting/slack) before exposing its OAuth and Events
API callbacks.

## Chat sandboxes

Each Workspace conversation's agent runs in its own container. The deploy
profile runs those containers in `dind`, a Docker-in-Docker daemon next to the
app, and wires the backend and worker to it. It needs no settings.

| Piece | Behavior |
|---|---|
| Daemon | Stock `docker:dind`. It is the only privileged container in the stack; sandboxes are not privileged. The backend never mounts the host's Docker socket. |
| Docker API | Port 2376 inside Compose with mutual TLS. `dind` creates its certificates on first start; backend and worker read the client certificates from the `sandbox_client_certs` volume. The API is not published on the host. |
| Network | `dind`, `backend`, and `worker` share a separate `sandbox` network. Sandboxes follow the [chat sandbox network policy](/docs/self-hosting/architecture#chat-sandbox-network-policy): the deploy profile never publishes Postgres or FalkorDB, and `dind` drops traffic to instance metadata. |
| Isolation | Each agent port needs a per-conversation password, and sandboxes cannot reach each other over the bridge. |
| Limits | On cgroup v2 hosts, all sandboxes share one cgroup capped at 85% of the memory `dind` may use, and 8192 processes. Without cgroup v2 the caps are skipped and `dind` logs a warning. Container logs rotate at 3 × 10 MB. |
| Chat image | `chat-sandbox-image` builds `scripts/chat-sandbox` inside `dind` on every `pnpm start`, from the same checkout as the other images. Builds after the first are cached. Nothing waits for it: until it exists, chat answers 503 and the rest of the app works. Once the published `ghcr.io/ctxpipe-ai/chat-sandbox` image is public, Compose will pull it instead. |
| Storage | The `sandbox_docker` volume holds sandboxes and the chat image. It is disposable: conversations keep their work in their git branch. |

<Callout type="warn" title="The Docker client certificate is root on dind">
  Anyone with the files in `sandbox_client_certs` can start privileged
  containers on `dind`, which amounts to root on the Docker host. Only
  `backend` and `worker` mount that volume; do not mount it anywhere else or
  copy it off the host.
</Callout>

To cap sandboxes below the host's memory, limit `dind` in a
`docker-compose.override.yml`; the sandbox cap follows at 85% of it:

```yaml
services:
  dind:
    mem_limit: 8g
```

If `dind` stops, chat answers 503 until it is back; it never falls back to
running agents without a sandbox. When `dind` restarts, running sandboxes stop
with it. The next turn of each conversation starts its container again, or
creates a new one from the conversation's git branch if the container is gone.

<Callout type="warn" title="Unsandboxed chat is a last resort">
  If your Docker host cannot run privileged containers, the backend can run
  chat without a sandbox: set `SANDBOX_PROVIDER: unsandboxed` on `backend` and
  `worker` in a `docker-compose.override.yml`. The backend logs a warning at
  startup. The agent then runs as a process inside the backend container with
  the backend's network access and credentials. Use it only where
  Docker-in-Docker cannot run at all, and treat every Workspace user as
  trusted with the backend.
</Callout>

## Persistent state

Do not treat these as disposable once users depend on the deployment:

| State | Where it lives by default |
|---|---|
| Postgres data | Compose-managed Postgres volume |
| Graph data | FalkorDB container storage |
| Repository clone cache | `repo_cache` volume |
| Zoekt index | `zoekt_index_deploy` volume |
| Secrets | `.env`, or your platform secret store |

Postgres and FalkorDB have no host ports in the deploy profile. Reach them
through Compose, for example
`docker compose exec postgres pg_dump -U ctxpipe ctxpipe > backup.sql`.

`sandbox_docker`, `sandbox_ca`, and `sandbox_client_certs` need no backup.
Removing `sandbox_ca` makes `dind` issue new certificates; restart `backend`
and `worker` afterwards.

## Operational checks

- `docker compose --profile deploy ps` shows healthy app services and a healthy `dind`.
- `curl https://<public-origin>/.status` returns an `ok` status.
- Sign-in works through the public origin.
- A repository can be connected and indexed.
- A Workspace chat answers; `docker compose exec dind docker ps` shows its sandbox.
- MCP can reach `{AUTH_BASE_URL}/mcp?orgSlug=<org-slug>`.
- Backend, worker, codesearch, Postgres, and graph database logs are collected.

See [Operations](/docs/self-hosting/operations#chat-sandboxes-docker-compose)
for sandbox disk and health checks.
