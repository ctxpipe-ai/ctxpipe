The repo includes a Terraform stack in `infra/` for managed infrastructure. It
currently models the ctxpipe Railway and Neon deployment path, with app services
pulling versioned images from GitHub Container Registry.

## What the included stack manages

| Area | Terraform shape |
|---|---|
| App platform | Railway project, environment, services, variables, and volumes |
| Database | Neon Postgres 17 project, branch, endpoint, database, owner role, and the `ctxpipe_app` password |
| App images | `ghcr.io/ctxpipe-ai/backend`, `worker`, `ui`, and `codesearch` tagged by commit SHA |
| Graph database | Railway service for FalkorDB |
| Secrets | Not in Terraform: CI writes them straight to the Railway service variables |

## Initialize state

`infra/backend.tf` expects an S3-compatible backend. The checked-in README shows
Cloudflare R2 as the reference backend. Initialize from the repo root:

```bash
terraform -chdir=infra init
```

For production state, pass backend settings at init time and keep credentials out
of the repo.

## Plan and apply

The stack has no secret input, so the state holds no app secret. Review the
plan:

```bash
terraform -chdir=infra plan
```

Apply only after the plan matches the intended environment:

```bash
terraform -chdir=infra apply
```

## Secrets

Keep each app secret in your CI secret store. Before the images start, the
deploy writes them to the Railway service variables with
`scripts/railway-sync-variables.mjs`, which lists each secret and the services
that get it. An optional connector (Slack, Linear, PagerDuty) is on when you set
its secrets. Each provider still requires its operator-side App, OAuth,
callback, and webhook configuration.

## Image rollout

The deployment path expects CI to build and push app images, then pass the image
tag into Terraform:

```bash
terraform -chdir=infra apply -var="image_tag=<commit-sha>"
```

This keeps infrastructure changes and application rollouts reviewable in the
same workflow.

Terraform generates the `ctxpipe_app` password, and migrate creates the role in
SQL with it. A role from the Neon API is a member of `neon_superuser`, which has
`BYPASSRLS`, so migrate refuses it. Railway `DATABASE_URL` on backend, worker, and
codesearch is the app-role pooler URL. Migrate / `PRODUCTION_DATABASE_URL` stays
the owner. Do not collapse those two identities.

## Chat sandboxes

The module runs Workspace chat in Vercel Sandbox (`SANDBOX_PROVIDER=vercel`).
The deploy writes the Vercel token (`VERCEL_TOKEN`) from the CI secret store. The Vercel team and
project are set to ctxpipe's own values, so a fork must change them. See
[Configuration](/docs/self-hosting/configuration#chat-sandboxes).

## Observability

This stack is the hosted Railway layout. It does not deploy Langfuse or
ClickStack. The module always sets `OTEL_EXPORTER_OTLP_*` from
`otel_otlp_endpoint`, which defaults to ctxpipe's hosted collector
`https://telemetry.ctxpipe.ai`. The deploy writes `OTEL_EXPORTER_OTLP_HEADERS`
from the CI secret store. If you reuse the module, override both; to disable
export, remove `otel_shared_env` from the module. See [Configuration](/docs/self-hosting/configuration).

## When to customize

Fork or extend the Terraform module when you need:

- A different container platform.
- A different Postgres provider.
- Externalized graph database infrastructure.
- Separate environments for staging, preview, and production.
- Provider-specific secrets, logging, or networking controls.
